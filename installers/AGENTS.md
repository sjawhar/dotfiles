# installers

Per-tool install scripts. The root `install.sh` sources the ones it lists, in order, and runs `agent-secrets-local.sh` as a command; machine installers run the role-specific ones.

## Key files

- **`lib.sh`** — shared helpers sourced by every installer: `ensure_link` (symlink; replaces a plain file only when it is identical to the source, and fails on a differing file or a real directory), `ensure_clone` / `ensure_vendor` (shallow git clone; `ensure_vendor` also follows the URL and converges a pinned ref), `ensure_command` (install a binary if absent, ignoring shims), `ensure_json` (idempotent jq patch), `arm_user_timer <unit-dir> <name>` (a watch installer's timer: refuses inside an agentbox and when either `~/.dotfiles/<unit-dir>/<name>.{service,timer}` is missing, links both from `~/.dotfiles` rather than `DOTFILES_DIR`, runs `daemon-reload` and `enable --now`, and proves the timer in `list-timers`; the installer keeps its own preconditions). Also exports `DOTFILES_DIR` and prepends `bin`/`~/.local/bin` to `PATH`.
- **Tool installers** — `shell.sh`, `mise.sh`, `docker.sh`, `sops.sh`, `jj.sh`, `tmux.sh`, `nvim.sh`, `claude.sh`, `omp.sh`, plus others (`ghostty.sh`, `voxtype.sh`, `knives.sh`, `agent-browser.sh`). `omp.sh` also clones the `vendor/` checkouts behind `skills-sources.json`. `agent-browser.sh` downloads the Chrome for Testing build the mise-pinned `agent-browser` drives. `docker.sh` installs Docker Engine from Docker's own repo and puts the login user in the `docker` group — never Ubuntu's `docker.io`, whose `containerd` conflicts with `containerd.io` and which ships no buildx or compose plugin. Group membership is what SSH-driven tooling (Pulumi's docker provider, the envoy deploy) needs, since it gets no tty for sudo.
- **Role-specific installers** — invoked as commands by machine installers, never by root `install.sh`, because the role must be explicit. The one exception is the secrets broker's helper, whose role is the machine's `env.local`: the root installer runs `agent-secrets-local.sh` on every machine, and it installs the helper only where `env.local` names a broker. `forward.sh` resolves `forward/hosts.toml` through `tailscale ip -4` at install time and atomically generates literal-address config at `~/.config/forward/config.toml` for the tailnet devbox pairs. It rejects `XDG_CONFIG_HOME` unless unset, empty or exactly `$HOME/.config`, before writing files or changing services. `serve` requires a host in `dev_vms`, listens on its own tailnet IPv4, trusts the laptop, and stops and disables any installed or loaded `pcscd-bridge.service` before taking its PC/SC socket, retaining the bridge's unit file. `serve` on oryx is refused because `laptop/oryx-tunnel-setup` writes its loopback configuration. `daemon` installs one `forward-daemon.service` plus the browser relay, preserves `forward-daemon@oryx` and `forward-tunnel@oryx`, and disables other legacy `forward-daemon@…` and `forward-tunnel@…` instances only when deliberately run. Every deliberate install restarts its role's units, even with unchanged config, so retrying after a service failure applies the generated peer set. No per-pair config, template unit or SSH artifact is deleted; `forward/migration.md` gives the five migration steps and release prerequisites. `omp-embed.sh` (devbox): runs one `text-embeddings-inference` Docker container (`omp-embed`, model `BAAI/bge-base-en-v1.5`, `127.0.0.1:8087`, `--restart unless-stopped`, `--cpus 16` so an embedding burst cannot take the whole host; `OMP_EMBED_CPUS` overrides) and writes `~/.config/omp-embed/endpoint`; `shims/omp` exports `MNEMOPI_EMBEDDING_API_URL` from that file whenever the server answers, so no session spawns its own ~1 GB `__omp_worker_mnemopi_embed`. Re-running it is safe: same image → `docker update --cpus` then `docker start`, with no restart of a running container; new image → recreate.
- **`agentbox-host-ssh.sh`** (devbox role installer) — creates a missing per-host key and pins the host key for SSH from a box. New authorized-key entries add no source or forwarding restriction. `--unrestrict-existing` removes only this installer's old three-option prefix. With `--key-fingerprint SHA256:...`, it selects an existing cross-host key without transferring a key and also removes that key's source-only prefix. This mode generates no key and performs no network setup. Other entries, key bytes, file mode, and ownership remain unchanged. Box startup leaves shared host SSH files unchanged and generates private system defaults.
- **`agent-secrets.sh`** (run by `devbox/install.sh`, and by the root `install.sh` through `agent-secrets-local.sh` where `env.local` sets `AGENT_SECRETS_URL`) — links, enables and starts the secrets broker's host helper (`agent-secrets/`). An unchanged re-run of a running helper makes no enable or start call; a stopped one is started. A machine without the helper's unit keeps secretsd alone: its shells get no `AGENT_SECRETS_HELPER_SOCK` (`.bashrc`) and its sessions are not registered (`scripts/agent-secrets-session`). That is the unit's absence, not `env.local`'s: a unit already linked stays when `env.local` names no broker. It restarts the helper only when the pinned version or the helper's files changed, never while host sessions are registered (unless `AGENT_SECRETS_HELPER_RESTART_WITH_SESSIONS=1`), and records the restart only once it succeeded; a refused restart is a warning, not a failed install. A run that starts the helper itself records the installed version without a restart, because the helper it started already runs it. It also does not restart, whatever that variable says, when `agent-secrets-helper sessions` fails or times out: it warns, and the next install retries.
- **`agent-secrets-local.sh`** — reads `env.local` alone, ignores an inherited URL, and prints no URL. When `env.local` sets no broker, it never installs or changes a unit. It drops `AGENT_SECRETS_HELPER_RESTART_WITH_SESSIONS`, so restarting over registered sessions requires a direct run of `agent-secrets.sh`.
- **`gcloud-box.sh`** (devbox, role installer; `devbox/install.sh` runs it) — on a Google VM (`scripts/on-google-vm`; sami-devbox, dispatch://INFRA-993), makes the VM's attached account (the metadata server's default email, `dev-sjawhar`) the account of gcloud's active configuration `box` (project `autoformalization`) with no credential file at all: it removes `box_credential_config.json`, an external_account well-known ADC file and a stored Azure external_account entry (`scripts/gcloud-drop-azure-credential`; all three what a config dir carried over from an Azure box holds, and each would win over the metadata server), leaves every other stored login alone, and fails, keeping the file, when the well-known ADC is a person's login. On an Azure VM whose IMDS token belongs to the managed identity `box-sjawhar` (theorem-labs/agent-infra `box-identity/`), it makes the service account `dev-sjawhar` gcloud's active configuration `box` (project `autoformalization`) and the application default credentials, through a generated workload-identity credential config in the gcloud config dir. On any other machine it changes nothing. Its first line says which branch ran. It creates no configuration for a person's login: an agent applies in CI or as agent-infra's applier, impersonated from this identity, and a step only a person can make is on agent-infra's `docs/break-glass.md`. Every other configuration that exists, and its `legacy_credentials/`, are never touched. On Azure a user ADC it replaces is kept once as `application_default_credentials.json.pre-box`. Honours `CLOUDSDK_CONFIG`, so a throwaway dir tests it; `GCE_METADATA_HOST` and `GCLOUD_BOX_IMDS_URL` override the two metadata addresses (`scripts/tests/test_gcloud_box.py`).
- **`gcloud-boxid.sh`** (devbox, role installer; `devbox/install.sh` runs it after `gcloud-sdk.sh` and `gcloud-box.sh`) — on a Google VM with `/mnt/nvme/<user>`, makes the two box-identity paths that scripts written on sami-rocqperf name, so they run on sami-devbox unchanged: `/mnt/nvme/<user>/boxid/gcloud-box`, a gcloud config dir made by `gcloud-box.sh`'s Google branch (`CLOUDSDK_CONFIG` set to it: configuration `box`, the VM's attached account, no stored credential), and `/mnt/nvme/<user>/boxid/infra-kubeconfig`, the context `gke_theorem-agent-infra_us-west1_dispatch` of `~/.kube/config` alone (`kubectl config view --minify --flatten`; gke-gcloud-auth-plugin, no credential). sami-rocqperf's own copies were made by hand and hold the Azure federation credential, which breaks gcloud on a Google VM, so the copy to sami-devbox leaves them out. A box gets them with `--dir /mnt/nvme/<user>/boxid`; `devbox/sami-devbox-check`'s box half reads through both. Elsewhere it changes nothing. `GCLOUD_BOXID_DIR` overrides the directory.
- **`gcloud-metadata.sh`** (devbox role installer) — on a machine that is not a Google VM, links and starts `devbox/gcloud-metadata.service`. The loopback service supplies the box account's cached token to Delta readers. A Google VM gets no local service. An existing disabled, inactive service stays stopped. No metadata-host environment variable changes.
- **`gh-app-host.sh`** (devbox role installer) — on a Google VM, sets `gh-app.host-profile = agent` in the machine's own git config. Host git then uses the GitHub App through `shims/gh`, including SSH-form GitHub remotes rewritten to HTTPS. This is credential routing, not a box mount filter. It neither removes SSH keys nor deletes a CLI login. Other hosts are unchanged (`shims/tests/test_gh_host_credential.py`).
- **`ssh-known-hosts.sh`** (devbox, role installer; `devbox/install.sh` runs it) — sets the kernel's append-only attribute (`chattr +a`, through `sudo -n`) on `~/.ssh/known_hosts`, the file every session on the machine shares, so ssh and other appenders still add keys but no non-root process can truncate, replace or remove it. It first installs `/etc/ssh/ssh_config.d/50-known-hosts-append-only.conf` (`Match localuser <user>`, `UpdateHostKeys no`), because ssh's UpdateHostKeys rewrites the file and the refusal would print two error lines on each connection. Not Linux, or no passwordless sudo: it says so and changes nothing. To remove a stale key: `sudo chattr -a ~/.ssh/known_hosts && ssh-keygen -R <host> && sudo chattr +a ~/.ssh/known_hosts`.
- **`sysbox.sh`, `tailscale.sh`** (root-level role installers; `devbox/gce-host.sh` sources them with sudo on a Google VM devbox, before `install.sh`) — `sysbox.sh` installs Sysbox CE (the agent-box runtime) from its pinned release `.deb` with its sha256, after Docker, since the package registers itself with Docker. `tailscale.sh` installs Tailscale's pinned `.deb` with its sha256 and joins the tailnet as Sami's own untagged node (`tailscale up --hostname=<name> --ssh --advertise-tags=`, adding `--force-reauth` when the node still carries a tag): it prints the login URL `tailscale up` gives and waits until Sami signs in there, so no auth key and no client id is stored (dispatch://INFRA-1099); it skips the join when the node is already up, untagged, under its name. Both refuse to run as anyone but root.
- **`omp-box-memory-guard.sh`** (devbox role installer; `devbox/install.sh` runs it) — static memory configuration for a machine that runs agent sessions, all of it idempotent and reboot-surviving: swap on the big disk (skipped where `devbox/gce-disks.service` owns it), the reclaim sysctls (`devbox/sysctl-memory-guard.conf` → `/etc/sysctl.d/70-omp-memory-guard.conf`), `MemoryMax=92%` on `user-<uid>.slice` (`devbox/user-slice-memory-guard.conf` → `/etc/systemd/system/user-.slice.d/60-omp-memory-guard.conf`), and — on a machine with at least 512 GiB of RAM — `MemoryHigh=192G` / `MemoryMax=256G` on every login session scope (`devbox/session-scope-memory-guard.conf` → `/etc/systemd/system/session-.scope.d/60-omp-memory-guard.conf`, the truncated-prefix drop-in directory that reaches each `session-<N>.scope` logind creates). The slice ceiling is an aggregate and one unbounded login can reach it alone: on 2026-11-06 a single plain-ssh session scope on sami-devbox held 684 GiB, took MemAvailable to 8%, and earlyoom answered with about 500 SIGTERMs across the fleet. Each drop-in's header has its numbers and why they are what they are. The session cap reaches the sessions that are **already logged in**, at the installing `daemon-reload` (measured on sami-devbox 2026-11-06T20:14Z: session-10548.scope, long-running, showed `MemoryMax=256G` straight after it) — so the installer reads every live `session-*.scope`'s `MemoryCurrent` first and refuses to write the file at all, naming the scope and its size, while one of them is already over the ceiling; capping such a session OOM-kills the work inside it. No service and no timer: this is configuration applied at provision.

## Conventions

- Start each script with `#!/bin/bash`, `set -euo pipefail`, and `source "$(dirname "${BASH_SOURCE[0]}")/lib.sh"`.
- Use the `lib.sh` helpers instead of hand-rolling symlinks, clones, or JSON edits.
- Keep installers idempotent — running twice must be safe.

## How changes take effect

Root `install.sh` sources its listed installers, except it runs `agent-secrets-local.sh`
as a command. Machine-specific setup belongs in the corresponding `devbox/install.sh` or
`laptop/install.sh`; those scripts can use `lib.sh` for shared installer behavior. Config symlinks apply on next
tool start; binaries install into `PATH` immediately.

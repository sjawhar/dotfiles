# omp

- Extension tests: `bun test omp/extensions/__tests__/`
- Test a condition rule with `omp ttsr test '<text>' --rule omp/rules/<name>.md --source tool --tool <tool>`. `--tool` defaults to `edit`, so a rule scoped to `tool:bash` matches nothing unless the test names `--tool bash`.
- A new extension loads only once `installers/omp.sh` links its entry file, and a pull does not run that installer: after the change merges, run `bash installers/omp.sh` on each machine.
- `omp/agents/` holds omp's agent definitions and `plugins/sjawhar/agents/` holds Claude Code's, under the same names: a change to one does not reach the other.
- A key never goes in a committed file, in a session's environment, or on an MCP server's command line, where any user on the machine can read it. `omp/mcp.json` starts a server that needs a key through `agent-secrets` or `secrets`, which put the key in that server's environment.
- A plugin pin (`package.json`, `bun.lock` or `omp-plugins.lock.json` in `omp/plugins/`) changes only by a commit. Edit `~/.dotfiles` in place, as the root `AGENTS.md` says: change the pin, install, then `jj commit` those files by name and run `scripts/dotfiles-publish`. Never leave a rewritten pin uncommitted: a plain `bun install` or `bun add` in a machine's `~/.dotfiles` rewrites the pins, and on 2026-11-03 such a rewrite, never committed, stopped `scripts/dotfiles-follow` from moving that checkout.
- A pin bump redoes each patch in `omp/plugins/patches/` (`bun patch <name>`, then `bun patch --commit node_modules/<name>`): Bun only warns about a patch whose key no longer matches, installs the package unpatched and exits 0. Drop a patch only once the pinned version carries its fix.

## Where MCP servers and skills load

- `omp/scopes.yml` names an MCP server (under `mcp:`) or a skill, by a name or a glob (under `skills:`), each with `context: personal|theorem`, `host: <short hostname>`, or both. An entry loads only where every scope it names matches. Anything it does not name loads everywhere. A server of `omp/mcp.json` goes by its key there; a plugin's server goes by `<plugin>:<server>` (the slack plugin's is `slack:slack`), and needs its own entry: a server of `omp/mcp.json` shadows the plugin's copy only where it loads.
- A session's context is its profile when that is `personal` or `theorem`. Any other profile, and the default profile, read the one word in the machine-local `~/.config/omp/context` (`$XDG_CONFIG_HOME/omp/context`), never committed. With no file, or another word, the context is unknown: every context-scoped entry loads, and `host:` entries still apply. The host is the machine's short name, `AGENTBOX_HOST` in an agent box.
- `shims/omp` applies the manifest at each launch of the default profile and of each named profile without `.no-shared-setup`. It builds the profile's `agent/mcp.json` from `omp/mcp.json` without the excluded servers and with each of them in `disabledServers`, which hides a server of that name from every source, and a settings overlay beside it, `agent/config.scopes.yml`, whose `skills.ignoredSkills` is `omp/config.yml`'s list, the local overlay's, and the excluded skills. A profile that wrote its own `mcp.json`, or changed the built one, keeps that file and gets no more scoping; delete the file to go back.

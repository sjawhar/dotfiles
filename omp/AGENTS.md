# omp

oh-my-pi (omp) configuration. The binary is mise-managed (`"github:sjawhar/oh-my-pi"` in `mise.toml`, a fork release auto-built from the fork's `sami` branch by `sami-build.yml` (which lives on the `ci` branch)); the wrapper at `shims/omp` injects secretsd keys, envoy env, the gh-app routing gitconfig, and — on a machine where `installers/omp-embed.sh` has run and its server answers — `MNEMOPI_EMBEDDING_API_URL`, so memory embeddings go to the one shared `text-embeddings-inference` container instead of a ~1 GB per-session `__omp_worker_mnemopi_embed`; then execs omp. `installers/omp.sh` wires everything below into `~/.omp/agent/`.

## Key files

- **`config.yml`** — main config: modelRoles, retry/fallback chains, task agentModelOverrides, tui settings. Not linked into `~/.omp/agent/`: `shims/omp` loads it as a read-only `PI_CONFIG_FILES` overlay, for every profile, so what is committed is what runs. omp's own writes — `/model` picks (`settings.setModelRole`), setup prompts (`setupVersion`, `dev.autoqaConsent`, `codexResets.autoRedeem`), TUI toggles — go to the profile's `~/.omp/agent/config.yml`, a machine-local real file (`installers/omp.sh` seeds `{}` on a fresh machine and copies the committed content when converging the old symlink layout), and the committed values override them wherever both set a key; a pick that should stick is an edit here. A session re-reads its global file and its overlays before every subagent spawn (`settings.reloadFromDisk`), so an edit to the committed file reaches running sessions started under the overlay at their next `task` — and a session started under the old symlink layout has no overlay and reads only the local file, which is why the converge copies rather than empties it. Precedence is `defaults <- ~/.omp/agent/config.yml <- project .omp/config.yml <- this overlay <- --config <- runtime`, so this file also beats a project's `.omp/config.yml` (none exist under `~/src` today). Roles: `default`/`plan`/`smol`/`task`/`advisor` are Anthropic (through the Hawk gateway on the devbox); `vision` is `google/gemini-3.7-flash`; `slow` and `review` are `openai-codex/*`, the ChatGPT Pro subscription, as are the `astra`, `oracle`, `deep` (`@slow`) and `sami-proxy` agents. Codex never falls to OpenAI API billing: `fallbackChains` send a Codex quota wall or outage to the Anthropic tier matching the failing model (gpt-5.5/5.6-sol/5.6-terra → opus-5, 5.6-luna → sonnet-5, never fable) rather than to `openai/*` or `opencode-zen/*`, which stay in the file commented out, and `retry.usageAwareFallback` moves off Codex before its window is exhausted. Two escape hatches have no fallback at all (an empty chain): `openai-codex/gpt-6-astra` — the `astra` and `sami-proxy` agents — and `openai/gpt-5.6-terra` — the `gpt-api` agent, the one route onto OpenAI API billing, which names its model directly; on a wall or outage they fail and the caller decides, instead of quietly answering from Anthropic. Vocabulary: a *role* (`modelRoles`) is a named model alias (`@slow`) that only `/model`, an agent's `model:` and `agentModelOverrides` can use — a session's model cannot dispatch a role; an *agent* (`agents/*.md`) is what `task` dispatches, and its `model:` names a selector or a role; a *chain* (`retry.fallbackChains`) is keyed by exact model, then `provider/*`, then role — an agent's own multi-entry `model:` list only becomes its chain when no model or wildcard key claims the model.
- **`models.yml`** — universal provider/catalog patches only (today: the `claude-opus-5` xhigh thinking patch for a stale pi-catalog). It is never what omp reads directly: `installers/omp.sh` merges it with **`omp/models.local.yml`** (gitignored, machine-local) when that exists and writes the result as a real file at `~/.omp/agent/models.yml`; no built copy lives in the repo. Anything that names one machine's network or credentials — a gateway `baseUrl`, an `!command` `apiKey` — belongs in `models.local.yml` on that machine and in no committed file. The Trajectory devbox routes the `anthropic` provider through the Hawk gateway this way (`baseUrl` = the gateway's `/anthropic` route, `apiKey: "!hawk-token"` plus `headers.X-Api-Key: "!hawk-token"` — the gateway reads the token from `x-api-key` only, omp sends a custom base `Authorization: Bearer` unless `X-Api-Key` is explicit, one command string so one cached mint, both re-run on a 401). `scripts/hawk-token` is a thin wrapper over agent-c's `hawk-token` console script (agent-c #19673: one OAuth refresh grant per run through hawk's own refresh path, so every 401 retry carries a `jti` middleman has never seen). Each mint runs the live slot's venv console script directly, without `uv run`, which reinstalled the project into the shared venv on every call. It spends one 9 s budget inside omp's 10 s `!command` limit, the first attempt taking whatever is left and a retry running only if time remains, so a machine at load 200 slows a mint (7-9 s measured) instead of emptying it; it runs the script from a private shallow checkout of agent-c main under `~/src/.hawk-token` (minting never runs git: two slots with a `current` symlink, and a stale 6 h stamp starts one detached, single-flight background build of the idle slot that is swapped in atomically only after it imports cleanly, so a refresh killed at any point leaves the live checkout intact; `~/src` is already mounted into every box, so one clone serves running sessions too) rather than `~/src/agent-c`, whose working copy is wherever the last session left it. Being untracked, `models.local.yml` is deleted from disk by checking out any commit that tracks a file at its path (a stray working-copy sweep, typically); if `~/.omp/agent/models.yml` ever comes out without the gateway block, re-create it from this paragraph and re-run the installer. Named profiles (`scripts/ompo`) do not mirror `models.yml`, so a profile reaches providers directly with its own keys.
- **`mcp.json`** — MCP servers, launched through the `secrets` CLI so tokens never sit in config, and never on a command line either, where every user can read them from `/proc/<pid>/cmdline` and any `ps` prints them: a server gets its secret from the environment `secrets` sets. A header token rides mcp-remote's own `${VAR}` placeholder, kept literal in `args` (mcp-remote 0.14.3 expands it from its environment; omp expands `${VAR}` in `mcp.json` itself only when omp's own environment has that variable, which no launcher sets); a URL that is itself the credential goes through `scripts/mcp-remote-from-env`, resolved on `PATH`. mcp-remote is pinned (`mcp-remote@0.14.3`), because npx otherwise runs whatever npm calls latest with the credential in hand.
- **`lsp.json`** — user-level language-server config, symlinked to `~/.omp/agent/lsp.json`; project `lsp.json`/`.omp/lsp.json` override per key. Two settings, both memory levers for the shared devbox: `idleTimeoutMs: 1800000` turns on omp's built-in idle reaper (off by default) so a language server nobody has asked anything in 30 min exits and respawns lazily on the next `lsp` call; `servers.pyright.disabled: true` because omp's built-in table lists `pyright` and `basedpyright` as separate entries and starts every entry whose file types match, so each Python session ran two servers — and `shims/pyright` execs basedpyright anyway. Strict JSON: no comments.
- **`WATCHDOG.yml` / `WATCHDOG.md` / `watchdog/`** — advisor roster, shared framing, and per-advisor instructions, symlinked to `~/.omp/agent/`. `AskGate` is enabled in the roster and globally through `advisor.enabled: true` in `config.yml`; it reviews `xd://dispatch_ask`, `xd://dispatch_message`, `xd://dispatch_edit_ask`, `xd://dispatch_comment`, and `xd://dispatch_doc_edit` tool calls, plus `xd://dispatch_issue` when its arguments include `spec`, against `watchdog/askgate.md`, which imports the sami-proxy skill. `General` holds the pre-roster WATCHDOG.md body (`watchdog/general.md`), paused but visible in `/advisor status`.
- **`agents/`** — agent definition files, all real files. Some originate in `plugins/sjawhar/agents/` or vendor repos; they are copied in, not linked. Update by re-copying deliberately. `opus-payload.md` names `anthropic/claude-opus-4-8` and is the lane for work that reads attack payload files once the Codex window is exhausted: newer Anthropic models refuse those reads, and Sami ruled out paid OpenAI API billing for them (agent-c AGENTC-205, 2026-09-30: "use Opus 4.8, 4.7 or even 4.6").
- **`extensions/`** — dotfiles-owned extension source only (`dotfiles-skills.ts`, `session-env.ts`, `compaction-reminder.ts` with its texts in `compaction-reminder.md` and `compaction-reminder-subagent.md`, `viewport.ts` with its windowing in `viewport-window.ts` and its selection logic in `viewport-selection.ts`, `attention-queue.ts`). Everything else reaches omp as an installed plugin (below), never as a path or symlink to a checkout. `compaction-reminder.ts` re-injects what a compaction loses, telling the two session kinds apart by `ctx.agent.kind`. A top-level session with an active `[sdd]` goal gets `compaction-reminder.md` after every compaction, committed or a successful shake. A subagent, on its first compaction of either kind, gets `compaction-reminder-subagent.md` followed, verbatim, by the assignment it was spawned with and the latest instruction it received after it. Either reminder is a persisted custom message, sent as an `aside` when the run continues past the compaction and as `nextTurn` otherwise. A successful shake, which writes no compaction entry, also appends a `compaction-marker` entry with the context size before and after it, the only record of the size a shake leaves. Why each piece holds up against shake — where the assignment and follow-up are read from, the uppercase delimiters, which shakes count — is in `compaction-reminder.ts`'s header. Edit the `.md` files to change what the model is told; a running session picks it up on its next start (extensions load once per process). `attention-queue.ts` puts the session on the tmux attention queue (`scripts/tmux-attention`) when a turn ends idle or with an error, or an ask opens, and takes it off when Sami types into the pane, the ask dialog closes, or the session exits; it replaces the three `*.notify` settings, which are off in `config.yml`. `viewport.ts` is the transcript viewport: `/viewport` or Ctrl+Alt+F toggles it, and `OMP_VIEWPORT=1` (or `OMP_FULLSCREEN=1`, which boxes launched under the mode's first name still carry) opens it at session start. It moves the transcript to the terminal's alternate screen with the composer pinned below it. PageUp/PageDown, Ctrl+Home/Ctrl+End and the mouse wheel scroll; scrolled back, the view is anchored to a transcript block and a row within it, so a frame renders only the blocks on screen and new output does not move it. A plain left drag selects transcript text (a double-click a word, a triple-click a row), draws it in reverse video and copies it on release as OSC 52 (`set-clipboard on` in `.tmux.conf` keeps it as a tmux buffer), with `copied N lines` in the footer; Alt+drag stays tmux's selection and Shift+drag the outer terminal's. A new click, a key that edits or submits, a width change or a selected block re-rendering clears it, and image rows are neither highlighted nor copied. The full behaviour, including edge scrolling and every clearing key, is in `viewport.ts`'s header. The windowing (`viewport-window.ts`, import-free) and the selection rules (`viewport-selection.ts`, which imports only the windowing) are pure modules tested by `bun test omp/extensions/__tests__/`; `viewport.ts` is the wiring. The installer links only `viewport.ts`, and its relative imports resolve against the link's real path. It uses only public extension API (a fullscreen `ctx.ui.custom` overlay), so the fork carries no viewport code; that placement is a CONSUMER verdict in the oh-my-pi fork's ledger (2026-09-26). While open it wraps `tui.showOverlay`, so dialogs opened over it (the alt+p picker, ask, confirm) stay on the alternate screen, and `tui.hasOverlay`, so the editor's app keys (Ctrl+R, Ctrl+O, Ctrl+T, Ctrl+G, Alt+L) work inside it, which got its own CONSUMER ruling (2026-09-27); `tui.mouse` stays off for the same reason. Structural couplings an omp upgrade can break: it finds the transcript among the TUI's children by duck-typing (`renderTail`, `peekReplayBatch`, `children`) and the editor as the focusable descendant with `getText`/`handleInput`, and closes with "transcript not found" if the TUI is reshaped; the scrolled-back view calls each block's `setTranscriptAllocation` and `render` and composes the rows as omp's `TranscriptContainer.renderTail` does, which drifts silently if either changes upstream; and the selection relies on pi-tui's native `sliceWithWidth` escape handling, modelled by the tests' stand-in, whose header names the omp build it was proven against and when to re-run its parity probe. History from before a compaction or handoff stays scrollable only because `config.yml` sets `display.collapseCompacted: false`.
- **`hooks/post/jj-snapshot.ts`** — the jj working-copy snapshot after each mutating tool call: fire-and-forget `jj util snapshot` with a per-repo in-flight guard, so it never blocks the tool loop. It must stay the only snapshotter, and no snapshotter may await jj: every colocated snapshot takes the repository-wide `git_import_export.lock`, shared by every workspace of that repository, so an awaited call queues behind every other workspace's snapshot and can exceed the 30 s extension-handler deadline.
- **`plugins/`** — the omp plugin tree, symlinked to `~/.omp/plugins`. `package.json` pins each plugin to a GitHub ref (`github:sjawhar/knives#<sha>`, `github:sjawhar/secretsd#<tag>`, ...) exactly like `opencode.json`'s plugin entries. `bun install` here materializes them; `omp plugin install`/`upgrade` manage the pins, and the resulting `package.json`/lockfile changes get committed.
- **`omp-billing-watch.{service,timer}`** — hourly report-only user units for `scripts/omp-billing-watch` (spend on per-token API billing), which reads `~/.omp/stats.db`; armed by `installers/omp-billing-watch.sh` on the host. A finding exits non-zero, so the unit shows `failed` and the journal holds the report; the unit sends no alert.

## Skill pools (shared with OpenCode)

Vendored/adopted skill pools are declared once in `skills-sources.json` at the dotfiles root and consumed by both harness bridges: `opencode/plugins/dotfiles-bridge.ts` (OpenCode) and `omp/extensions/dotfiles-skills.ts` (OMP, via the `resources_discover` extension event at session start and `/reload-plugins`; needs a fork build ≥ v17.3.8-sami.20260820). Marketplace-installed pools stay out of the manifest — Claude's `installed_plugins.json` is their source of truth and both harnesses ingest it natively. The old flat symlink farm (`scripts/omp-sync-skills` → `~/.omp/agent/skills/`) is retired: live sessions snapshotted farm paths, so every re-sync prune broke them mid-flight.

Slash commands take neither route. OMP loads prompt templates from exactly two hardcoded directories (`agentDir/prompts`, `cwd/.omp/prompts`) with no settings key and no plugin hook, and `Bun.Glob` does not descend into symlinked subdirectories — so the files must physically sit in one directory and no runtime bridge is possible. `~/.omp/agent/prompts` is therefore a single symlink to `plugins/sjawhar/commands`, which is the only source: a new command file is live immediately, with no sync step. The retired `scripts/omp-sync-prompts` farmed per-file links from three namespaces; legion is headless orchestration where a user-only command is incoherent, and the sentry commands were unwanted.

## Conventions

- My own repos (knives, secretsd, legion) expose their omp extensions via an `omp` manifest in the repo root `package.json` and are consumed from GitHub with a pinned ref. A path or symlink into a local checkout is a prototyping state, never a landed one.
- Nothing committed in this directory may contain an absolute path or reference a machine-local checkout.
- Config dirs hold config. Executables live in `shims/` (wrappers), `scripts/` (utilities), or come from mise — never in a `bin/` under a config dir.
- The wrapper (`shims/omp`) and `scripts/oc` must provide the same session environment: gh-app `GIT_CONFIG_*` routing, dotfiles shims first on `PATH`, envoy env. A capability added to one belongs in both.

## How changes take effect

Config files are symlinked, so edits apply on next omp start. Plugin pin changes need `bun install` in `plugins/` (or re-run `installers/omp.sh`). New fork releases: `knives release cut` in `~/oh-my-pi` (fixed scheme, `release_branch = "sami"`) advances the `sami` branch in place; pushing it triggers `sami-build.yml`, which computes the version/tag (shared `sjawhar/.github` sami-version + sami-release actions - never tag by hand) and publishes the GitHub release; `mise upgrade` then picks up `latest`. `[settings.upgrade] auto_prune = false` (mise.toml, needs mise >= 2026.8) keeps the replaced version's install dir - live sessions re-exec their own binary path for hub brokers, hub-launched apps, and mnemopi workers, so pruning it breaks them all with spawn ENOENT. Never `mise prune` or remove a version dir while a running omp process references it — new own-repos must be listed in `mise.toml`'s `minimum_release_age_excludes` or `latest` will not resolve.

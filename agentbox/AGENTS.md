# agentbox

The opt-in **agent box**: the image (`Dockerfile`, `entrypoint.sh`) and the home allow-list (`mounts`) that `scripts/agentbox` runs a session with.

One disposable Sysbox container per **agent session**, working in checkouts made for it. `agentbox new [-e NAME[=VALUE]]… <repo>… -- omp [omp args…]` names one or more canonical checkouts under `~/src` (`AGENTBOX_SRC`), makes a git clone of each at `<boxes>/<box>/<repo>` (below), and runs `scripts/agentbox-run.ts` in the first as the container's main process (`docker run --rm`), with `shims/omp` as its child; any other command after `--` runs bare. **`<boxes>` is `/mnt/nvme/<user>/agentbox/boxes` on a machine with that disk and `~/boxes` on one without** (`BOXES` in `scripts/agentbox`, `AGENTBOX_BOXES` to override), because a clone per box per repo does not fit on the root disk of sami-rocqperf: 11 GiB free of 495 GiB on 2026-10-31 against an 18 GiB floor, with 94 GiB on `/mnt/nvme`. The clone templates move with them (`AGENTBOX_CLONE_TEMPLATES`, default `<boxes>/../clones`), since a box's clone hardlinks its objects out of its template and a hardlink does not cross a filesystem. The box lives exactly as long as the session. When omp exits — clean exit, pane kill, launcher killed — the launcher releases every knives claim the session holds (`knives finish`, as that session) and removes `<boxes>/<box>`, unless a clone in it holds uncommitted changes or commits no remote has: then the directory stays in place, and the pane names each such clone and what it holds. Nothing is saved for an agent; its work is its own to push or remove (Sami, AGENTC-1420, 2026-10-02: "Just tell the agents to migrate off of the JJ workspaces, and then they can handle it").

**Restart in place.** `agentbox restart <box|session-id>… | --all` relaunches a box's omp without touching the container: the runner hangs omp up (its ordinary graceful teardown) and spawns `omp --resume <id>` again through the shim, so the new process runs the current `mise.toml` pin, plugin tree and config, while the container, its workspace, `/tmp` and anything else inside stay. The relaunch carries no prompt: omp records a positional as a user message, and the `.` it used to carry was counted as text Sami typed by the transcript store (33 moved sessions from 18:50Z on 2026-11-01, found by the librarian). Without a prompt the agent would wait at the prompt until someone typed, so the runner starts `agentbox move --wake <id> <notice>`, which waits until the new process has registered on Envoy (an update newer than the waker's start) and sends one Envoy notice that the restart is done; omp records that as a custom message, not a user one. The launch's own messages are not replayed: like omp's own `/restart` (`restartArgv` in its `cli/flag-tables.ts`), the relaunch keeps every configuration flag with its value and drops the session flags, the `--` delimiter and every positional, each already in the resumed transcript (`scripts/agentbox-run.test.ts`). Before that, a box launched as `omp "Your session was restarted in a new agentbox…"` told its agent so again on every restart and then sent `.` as a second prompt (2026-10-02). By default the host only sends the session an Envoy notice — finish the current step, start nothing long, then run `agentbox restart` (the in-box form: no arguments, restarts this session) — so the agent picks the moment; omp's own settled-boundary shutdown is not involved, the agent's judgment is. `--now` hangs omp up at once, interrupting whatever it is doing (resume replays the persisted transcript; a tool call in flight is lost). The session to resume is the file omp holds open, or the newest session file of the box's working directory (an idle session holds no writer after a resume). Nothing persists a pending restart: an agent that never runs the command keeps running until `--now`, and a replacement omp that dies on startup ends the box instead of looping. The runner appends every restart request, omp exit (exit code, signal, how long it ran) and relaunch to `~/.cache/omp/agentbox/<box>.log`, on the host through the `.cache/omp` mount, so a box that a restart ended says why: a replacement that died on startup is a `relaunched` line followed by `exited after 0s … the box ends`. Only that last line also reaches the pane, since omp owns the screen while it runs. Boxes started before a runner change keep the old runner. omp's own `/restart` cannot do this — it re-execs the versioned mise install path and so never sees a new pin. What still needs a new box: a launcher-env change (`session_env`, mounts), an image change, the runner itself.

**Moving the sessions already running on the host.** `agentbox restart` is for a session already in a box; `agentbox move` is for one that is not (dispatch://INFRA-702). `agentbox move --plan [--json]` lists every live top-level omp on this machine with the box it would get: its tmux pane, its full session id (the transcript it holds open, else its own `--resume` argument — never a prefix, and never an id another process also claims), its working directory, the `agentbox new` spec, and the disk the boxes would take against the reserve a move keeps free (20 GiB on `/mnt/nvme`, 10 GiB on the root disk). It tells five things apart and moves only the first: a `host` session, a `no-pane` top-level omp (a headless `omp -p`, a scheduler step agent — the plan names its parent and unit and leaves it to a person), one already `boxed`, one in a grading `sandbox` (a `/work` directory, a bwrap ancestor, a container that is not a box), and a `subagent` of another omp, which is not a session. `agentbox move <session-id>… | --all` sends each session the Envoy notice to run `agentbox move --self` the next time it has no jobs running, without stopping, delaying or shortening any work for it; `--now` relaunches the pane from outside instead, and `--dry-run` prints what either would do. The notice names the session's omp pid and defines "its jobs" as the processes that descend from it (`pstree -p <pid>`), which is exactly what the hang-up ends; it tells the session not to judge by `read proc://`, which under a shared omp worker broker lists the services of every session that broker serves (measured 2026-11-02: a session saw seven, none its own, and never found its moment), and not to move at all when it is finished or ending. **A move never names a repo**, and that is the whole design: `agentbox new <repo>` gives a box a clone of its own, which for a live session means a tree that is not the one it has — no uncommitted changes, no index, and none of the work of the other 16 sessions sharing that checkout. `$SRC` is bind-mounted into every box already, so the spec is `--dir <cwd>` (plus the owning checkout when the session sits in a worktree outside `$SRC`), the session resumes in the same tree, and the only new disk is the box's own sparse ext4 image: 261 MiB at the 32 GiB default, measured, against 0.02–14 GiB for a clone. `--self` refuses, naming the reason, when the session is already in a box, when a SUBAGENT runs it (its bash tool reaches its parent's omp, so the move would hang up the session that started it: omp's `PI_SESSION_FILE` is `<name>.jsonl` for a subagent and `_<id>.jsonl` for a session), when `OMP_SESSION_ID` is not the session the process census read, when the id cannot be read in full, and when the box would leave the disk under that reserve — `--force-floor` is the person's override, and it prints what it overrides. The reserve is not `scripts/disk-fill-watch`'s 84 GB alert floor: that floor tells a person early, and used as a refusal it stopped all 70 ready sessions at 17:32Z on 2026-11-01 for boxes that claim 0.3 GiB each. The relaunch itself is a detached process (`move --relaunch`, logging to `~/.cache/omp/agentbox/move-<id>.log`): `move --self` runs in the session's own bash tool and dies with the omp it hangs up. It sends SIGHUP — omp's ordinary graceful teardown, the same signal `agentbox restart` uses — waits for the process to go, and respawns the pane into `agentbox new <spec> -- omp --resume <id>` under an interactive bash that stays when the box ends. The resume carries no prompt, for the reason under "Restart in place"; beside the launcher the pane command starts `agentbox move --wake <id>` on the host, which sends the session one Envoy notice that the move is done once its new process has registered, and logs it to the same move log. Measured on two throwaway sessions on 2026-11-01: hang-up to exit 2 s, pane respawned 3 s later, both resumed under their own ids in their own boxes, the worktree box seeing the host's uncommitted file and writing to it. Measured for the wake on 2026-11-02 with throwaway session `01a19ac5`: hung up 05:41:22Z, respawned 05:41:24Z, notice sent 05:41:46Z and answered in its box, and its transcript holds one user message, the one it was started with.

**A move's paths are inferred from the session's own processes, not from its working directory.** The first window notified 32 sessions on 2026-11-01 and several answered that the box they were offered would not hold the paths they work in. That is the dangerous failure and not a cosmetic one: a path a box is not given is not absent inside it, it is silently writable into the box's own filesystem and lost when the box ends. The cwd is a poor witness. A session whose cwd is `~/src/oss-verifier` works in `/mnt/nvme/sami/oss-verifier/...`, `/mnt/nvme/sami/tmp/...` and `~/.worktrees/...`; session `01a16640`'s cwd was `~/Code/legion`, a real checkout of the same repository, while the trees it had open were `~/src/legion/.worktrees/infra-140-s5` and `/mnt/nvme/sami/worktrees/legion/stopped-tree`, so the cwd alone would have given it a box whose `git status` answers about **another** checkout. So `move_dirs_why` (`scripts/agentbox`) reads the session's own process tree — the omp and every live descendant — and takes the cwd of each, and the directory of every file one of them holds **open for writing** (`O_WRONLY` or `O_RDWR` in `/proc/<pid>/fdinfo/<fd>`; a file only read names nothing, or every library and config a tool opens would mount the host). Each path is then resolved to the root of its git working tree where it is in one — the exact boundary, and what makes the worktree of an open file arrive whole — and otherwise bounded at the first directory below the deepest root that holds many sessions' trees (`~/Code`, `~/Code/personal`, `~/.worktrees`, `/mnt/nvme/<user>` and its `tmp`, `session-tmp`, `worktrees`, `scratch` and `wt`), which are never mounted at the root. A path the box already has is left out, because naming it changes nothing: `$SRC` and the targets of its symlinks, the dotfiles, every entry of the home allow-list, and the durable directory — **a worktree under `~/src/<repo>/.worktrees/...` is in that class, so it IS visible in a box with no `--dir` at all** (measured 2026-11-01 inside `agentbox-6e431c00c973`: `/home/sami/src/legion/.worktrees` listed its trees, with `findmnt` naming the `/home/sami/src` bind). Nested paths collapse to the shallowest, except the working directory, which stays first because `agentbox new` works in its first `--dir`. `move --plan` prints every path with the reason it was chosen, and so does the Envoy notice, so a session sees its box before it moves; `agentbox move --self --dir PATH --dir PATH` adds what the inference missed, each checked exactly as `agentbox new --dir` checks it and each placed after the inferred paths. Inference is best-effort by construction — a path no process of the session had open when the plan ran is not in it — which is why the list is printed and `--dir` exists.

**An inferred path ABOVE one the box already has is dropped too, and the worktree root is one of the shared roots.** The in-box test asks whether the path is at or below something every box binds; a path above one passed it, and the roots the too-broad test looks above did not include the durable disk. So one `ls /mnt/durable` in session S2's record made the whole durable disk — every other lane's work and every other user's directory — a `--dir` of its box (2026-11-04, 8 paths in its spec instead of 7). An inferred path that is a strict ancestor of an in-box path is now too broad as well (`move_dir_above_box`), because the box has the part of it the session can use. The rule is the inference's alone: a working directory under such a root is still the box's first `--dir`, and a path a person names with `--dir` is still taken, since dropping what somebody asked for is worse than the hole it closes. That rule also reached `/mnt/nvme/<user>/wt` — one `~/src` symlink there makes the whole worktree root an ancestor of an in-box path — which 20 of this host's 44 live sessions held whole, 323 GB of every session's worktrees (PROCS's move at 07:09Z on 2026-11-03, and SQLPAGE's box carried it into every re-box). The root was missing from the shared-root list, so everything below it collapsed *into* it; it is in that list now, so those sessions get their own worktree under it instead. Measured over the fleet the day it landed: 21 specs held an ancestor of an in-box path before and none after, and the only paths any session lost from its spec were those roots themselves.

**Three things a live-process scan cannot see, and what each needs.** The inference above reads the session's live processes. That is a snapshot, and three shapes measured on 2026-11-01 defeat it, each ending with a path silently writable inside the box and lost with it. (1) A SUPERVISOR writes almost nothing itself: its subagents do, and they have exited, so a dead worker leaves no cwd and holds no open file — session `01a16220`'s live scan gave two directories and missed four it works in. (2) TRANSIENT use: session `01a16640` works in `/mnt/nvme/sami/worktrees/legion/stopped-tree` only through one-shot `cd <path> && git …` calls, so at no instant is a process there. (3) The two commands DISAGREE: at 18:48:20Z the plan gave `01a1798a` `/mnt/nvme/sami/tmp/verified-linux` because one bash held a file open there, and `move --self` minutes later gave the cwd alone, so the box lost the directory holding that session's own state. So the spec has five sources, not one: the working directory and its git tree; the live processes; **the session's own record of today** — its transcript's tool calls, the `cwd` of its bash calls, the `path` of its read/write/grep/glob calls, the `[path#tag]` headers of its edit calls, and every absolute path inside a bash `command` or an eval `code`, which is what catches `cd <path> &&` and `git -C <path>`; **what the last `move --plan` inferred for that session**, kept in one small file per session under `<boxes>/../plan/<id>` and unioned in by `--self`, so a row the plan printed is a promise it keeps; and each `--dir` the caller named. Every one is bounded the same way and must exist. `--plan` and the notice print each path with which source it came from, and a session with **no live child process** is told so in its plan row and in its notice, so a lane reading two directories knows the live scan had nothing to work from.

**A nested session's record is read through its own omp, and a set that looks short is said.** The record of a session is found in the listing of `~/.omp/agent/sessions/<bucket>/<file>.jsonl`, and when the listing does not have it, through the session's own omp (the transcript it holds open, names in `--resume` or keeps at any depth under its agent directory). The listing alone cannot see a session started from another session's turn, whose transcript sits one level deeper in that session's directory: S2 (`01a170e0`, restarted by hand at 11:44Z on 2026-11-04) had its record read from no file, and its `move --self --dry-run` at 12:52Z named its working directory and the one `--dir` it gave while its transcript named `/mnt/nvme/sami/frac-verify` 61 times that day, `gate-runs` and its tmp trees — nothing said so. `--self` and `move <id>` now also read the transcript the box will resume over the last 24 hours, bound each path its tool calls name as the inference does, and print `WARNING: the inferred set looks short` with the trees left out when at least 2 of them are outside the box and the box gets fewer than half (`AGENTBOX_MOVE_SHORT_MIN`, `AGENTBOX_MOVE_SHORT_SINCE`). It never refuses: the session decides what it still works in and adds it with `--dir`. Over the host's 35 live sessions it warned for S2 and for one session whose worktrees were the previous evening's; `move_short_set` in the script has the numbers.

**A move resumes omp with the flags it was launched with.** The respawn is `omp <its launch flags> --resume <transcript>`, not a bare `omp --resume`: S2 ran as `omp --config /mnt/nvme/sami/frac-verify/omp-bet59.yml --resume <jsonl>`, and its dry run would have brought it back on the default configuration. No list of flags to keep exists: the omp's own argv (`/proc/<pid>/cmdline`) is read and only the session source (`--resume`, `--session`, `--continue`, `--fork`, …) and positional words (omp records one as a typed message) are taken out, by `relaunchArgv` of `scripts/agentbox-run.ts`, the same rule the box runner's restart uses, run through bun. `--self` on the host and in a box, `move <id> --now`, the notice, `move --to` and its rollback all carry them, and a move that cannot read them (no bun, an unreadable argv) refuses before anything is hung up. `move --to` carries a flag as written: a file it names (a `--config`) must be on the target, and the move copies only the paths it infers.

**Nothing that dies with the omp is in a spec, and a resume goes on without a path gone since.** A box's `--dir` paths are fixed when it starts, and every later resume of that session (`omp-memory-watch`'s restarter, a move's respawn, `tmux-resurrect-omp`) replays them. The old omp's own `TMPDIR` (`/mnt/nvme/<user>/session-tmp/<pid>-XXXXXXXX`, made by `scripts/agent-session` and removed by `devbox/session-scratch-reap` once no process holds it) is gone minutes after a move hangs that omp up, so a spec that named it was refused at the next resume: `01a1798a`'s move at 10:42Z on 2026-11-02 recorded `session-tmp/53458-LivaHYZv`, and at 16:23Z its restarted pane stopped at `--dir … is not an existing directory`. So the inference never takes a path under the `session-tmp` root or under the omp's own `AGENT_SESSION_SCRATCH`, and refuses a session whose working directory or hand-named `--dir` is one. And every resume runs `agentbox new --drop-gone-dirs …`: a `--dir` after the first that is no longer a directory — removed since, or a file (a re-box's spec named `/mnt/nvme/sami/tmp/ossv172-codex-turns.md` at 10:09:59Z on 2026-11-04, the launcher refused it, and that session was dead for 20 minutes) — is left out with a line on stderr naming the path and why (the move's log and the restarter's log name it too), while a FIRST `--dir` that is not a directory, the box's working directory, is still refused. A `--dir` the box already has through another mount (under the durable disk, say) was never a refusal: it is not bound again, with a line saying so. A plain `agentbox new --dir` still refuses a missing path or a file, so a typo is never dropped in silence.

**A tree is not its objects.** `~/src/machcsl-riscv/.git/objects` on this host is a SYMLINK to `/mnt/nvme/sami/git-objects/machcsl-riscv`, and so are the task repository's, `link-eval-accept29`'s, `machcsl-riscv-experimental`'s and `ossvp-ulimit`'s. A box given the tree and not the store answers `not a git repository` for every command in it, and `knives gh` fails with it (session `01a1798a-995f`, box `agentbox-676432b23e44`). `$SRC` is in every box, so the tree is never in the spec and the store must be: for every tree a session touches, the spec follows its `.git` (file or directory), its `commondir`, its `objects` through any symlink, and every line of `objects/info/alternates`, and adds each result the box would not have. **`agentbox new --dir` follows the same four things, through the same reader** (`move_git_storage`, called by `add_box_dir_storage` for the git tree each `--dir` is in), and prints the store it adds. It did not until 2026-11-01: `move` inferred its own paths and so had to follow them, while a `--dir` was treated as one directory the caller had already thought about, so `agentbox new --dir ~/src/machcsl-riscv` built a box whose every git command answered `fatal: not a git repository` — measured in box `agentbox-a0875d5a6f7c`, with the objects symlink dangling inside it, and the workaround in use was a second `--dir /mnt/nvme/sami/git-objects/<name>` by hand. After the fix, in box `agentbox-510cd93aca54`, `git rev-parse` and `git count-objects -v` in that tree answered exactly what the host answers (`9ebc0039ad45`, 13,609,735 in-pack objects).

**A config file that names a path is followed too.** `shims/gh` refuses `gh pr edit|create|comment` unless it finds the public-text leak check, whose location is `~/.config/public-leak-check/path`, holding `/mnt/nvme/sami/frac-verify/shared/leak-check/public-leak-check.sh`. The pointer is now in the allow-list (`ro .config/public-leak-check`) and the script is on `/mnt/nvme`, outside every box, so a box had the pointer and nothing to follow it to and every public text write from it was refused. `move_config_dirs` reads each pointer file for one absolute path and puts the directory holding it in the spec; adding another pointer is one line there. `agentbox new` binds the same directories, so a box made without `move` reaches the script too: on 2026-11-01 `agentbox-d7c1bb68a0a4`, made by `new` after the move fix, had the pointer and not the script. `agentbox doctor`'s box checks now fail when either half is missing, because a box that cannot write to GitHub is a box a lead cannot work in. Measured after the fix in `agentbox-bf4ffcac537c` (made by `move`): the pointer and the 23 KB script were both present and `gh pr comment` posted and was then deleted; and in `agentbox-7bdb51c4e932` (made by `new --dir` only): `test -x` on the script passed.

**Every box has the compute ledger.** `/mnt/nvme/<user>/compute-inventory`, which `ossv-vm` writes, is bound read-write at its own path in every box and made when missing, on every host with `/mnt/nvme/<user>` (`AGENTBOX_COMPUTE_INVENTORY` overrides); `agentbox doctor` checks that the box can write it. A box without it failed `ossv-vm create`'s ledger write (2026-11-03 03:01Z).

**Every box has the grading farm.** `farm` is `~/.local/bin/farm`, which every box has through the home allow-list, and it is a SYMLINK to `/mnt/nvme/<user>/farm-pkg/bin/farm`: a box without that directory holds a dangling link, and every `farm` call in it dies `No such file or directory`. That is what every box on sami-devbox had after the 18:05Z re-box on 2026-11-04, and it stopped the release builds. So `agentbox new` binds the three paths `installers/grade-farm.sh` makes, each at its own path, on every host that has them: `farm-pkg` READ-ONLY, since its shim, its grading-tools clone and its venv are written by that installer on the host alone and a run writes nothing in it; the farm root `grade-farm` (`FARM_DIR`: fleet, boxes, ssh_config, known_hosts, the no-start switch and the ssh control sockets each run opens) and `boxid` (the box identity's ssh key and its gcloud configuration, whose token cache gcloud rewrites) read-write. Those three folders and no more — `/mnt/nvme/<user>` as a whole is never bound (Sami, dispatch://INFRA-702/comment/11d4bf79-4369-4beb-8691-ec688cee53ab) — so a lane no longer passes `--dir` for any of them, and the paths `agentbox/mounts`' `.config/grade-farm` entry names now resolve inside a box. `AGENTBOX_FARM_PKG`, `AGENTBOX_FARM_ROOT` and `AGENTBOX_FARM_BOXID` replace the paths, and a host with none of them (a machine with no grading farm) binds none. A `--dir` naming one, or a path under one, is recognised and not bound twice (`box_dir_bound_why`; docker refuses two mounts at one destination), and `agentbox move` never names one. Measured in throwaway box `agentbox-fa4707dbaae2` at 18:28Z on 2026-11-04: `farm --help` printed its usage, `findmnt` gave `/mnt/nvme/sami/farm-pkg` `ro` and the other two `rw`, a write into `farm-pkg` was refused `Read-only file system`, and one into `grade-farm` succeeded. A box started before this change gets it only when it is replaced.

**Every box has the durable disk.** New staging and caches belong on `/mnt/durable/<user>`, a network disk with about 2 TB free, not on `/mnt/nvme`, which every session, box image and clone template shares and which had 160 GB free on 2026-11-02. So `agentbox new` binds `/mnt/durable/<user>` whole, read-write, at its own path, wherever it exists, and passes its path and the host's figures for it into the box (`AGENTBOX_DURABLE`, `AGENTBOX_DURABLE_FS`). A `--dir` under it, or a `~/src` symlink whose target is under it, is not bound again, and `agentbox move --plan` never names a path under it, because the box has it already. Before this, a box bound only three subdirectories of it, so at `/mnt/durable/<user>` itself it had a root-owned 0755 directory that docker made on the box's own disk: a write there was refused, and `df` there showed `/mnt/nvme`'s free space (KNOTCURVE, 2026-11-02 16:00Z). A lane that writes there believes it wrote to the durable disk. `agentbox doctor` (and `doctor --here` in a box) checks that `/mnt/durable/<user>` in the box is the host's filesystem (same device number and size, free space within 2% of the host's) and writable, and fails a box that predates the bind: move it with `agentbox move --self` at a safe point.

**Archived transcripts reach the box too.** On this host, transcripts that have gone cold move to `/mnt/durable/<user>/omp-sessions-moved` and leave a symlink in `~/.omp/agent/sessions`. Every box has `~/.omp/agent/sessions`, but no box had `/mnt/durable`, so inside a box the symlink pointed at nothing and a resumed omp exited with `Session "<id>" not found`. On 2026-11-01 lane box h-dgn-t1 died this way three times. The durable-disk bind above includes that directory, read-write, because omp appends to its transcript through the symlink; it includes the cold trees moved to `nvme-cold` and `src-cold` the same way. The archiver also skips any session a running process names (`--resume <id>` or `OMP_SESSION_ID`), and it counts a file's ctime as well as its mtime when it judges age. Measured in `agentbox-2896707b4359`: an archived transcript's symlink was readable from inside the box.

**The disk gate's state reaches the box too.** `scripts/disk-gate` serialises every lane's large writes through one lock and one count in `/mnt/nvme/<user>/scratch/disk-gate`, and no box had that directory: in a box `disk-gate reserve` hit a root-owned stub, took no lock, counted nothing and printed an empty reserved figure (three lane boxes within six minutes of the gate's announcement, 2026-11-02). `agentbox new` now makes the directory if it is absent and binds it read-write. It binds disk-gate's DEFAULT path and never reads the caller's `DISK_GATE_STATE`: the box does not get that variable (`session_env` builds its environment from scratch), so the disk-gate inside always uses the default. The first version of this bind honoured the caller's value, and its test launches came from a shell that still exported `DISK_GATE_STATE=/tmp/dg-test-47661` after testing the gate, so each test box got that directory and not the real one. Measured in `agentbox-3628240f49c2`, launched with that variable still exported: `disk-gate reserve 1 boxprobe` answered `NO … 0 GiB is reserved by other lanes` from the host's count, and a reservation on a new state file appeared on the host while the box held it.

**The N6 farm's work root and run index reach the box too.** `bin/ossv-n6-farm` (OSS Verify) stages a run in `/mnt/nvme/<user>/ossv-n6` when disk-gate admits it there and records the run's work root in `~/.cache/ossv-n6-runs`; `collect`, `peaks` and `clean` read both later, often from another session. A box on sami-devbox saw neither (2026-11-03, `agentbox-079d42c861b6`: both absent), so a run there would stage into the box's own overlay and lose its directory when the box closed. `agentbox new` makes the work root if it is absent and binds it read-write, as it does the gate's state, and the run index is in `mounts`.

**Add or replace a box's folders at its safe point.** `agentbox move --self --dir <host path>` relaunches the session's pane through the host tmux relay into a new box with its existing `AGENTBOX_DIRS` plus the named paths. `--only-dirs` replaces the inherited list with the named paths. The host's launcher checks the paths, since a folder being added need not exist in the old box. The resumed session receives an automated Envoy wake; its waker logs to `~/.cache/omp/agentbox/move-<session-id>.log`, whose parent is created before the respawn. This shared mount survives the move; the old box's `XDG_CACHE_HOME` does not.

**Moving a session to another machine** (dispatch://INFRA-993). `agentbox move --to <machine>` is `--self` with a target machine: the session runs it from its own bash tool at its safe point, and it comes back on `<machine>` in a box, with the same id and transcript. It reaches the machine over Tailscale SSH as `sami` (`AGENTBOX_MOVE_SSH`, default `ssh -o BatchMode=yes -o ConnectTimeout=20`) and moves the session's **group**: every live host session that works in one of its git working trees, because a shared tree moves once, with all its users. Its trees are the inferred paths of `move --plan` and the trees under `~/src` its processes name, each that is a git working tree; another session works in one when one of its processes has its working directory there or holds a file there open for writing, and the group grows from each member found until nothing is added. Only the members' paths are inferred: inferring every session on this host took 221 s before the hang-up, and finding the group from the processes takes one census and one `find` over `/proc`. Every other path is copied but joins no group: on 2026-11-02 the inferred paths of this host's 46 sessions put 45 in one group, through caches (`/mnt/nvme/<user>/cache`, `gocache`, `gotmp`), a review tool's run directory (`gate-runs`, 16 sessions), `/mnt/durable` and lead roots, while their git trees alone made a group of 13 (one shared checkout), one of 2 and 31 single sessions. A working directory that is `~/src` itself or another root of many sessions' trees is neither copied nor grouped. Every session of the group runs the command at its own safe point; the earlier ones only leave a ready file, which counts for 10 minutes (a member that went back to work after it is asked again, and is never hung up on an old answer), and the others are asked over Envoy, and the last one moves them all. Then a detached relauncher checks the target again, hangs every member up, and copies with rsync, each path at its own absolute path: the transcript, the session's own directory (its subagents' transcripts) and what any symlink there points at, and the git trees as mirrors (`--delete`; what they replace on the target is kept under `/mnt/nvme/<user>/cutover/replaced/<stamp>`), and everything else as a merge (`--update`, no delete): git storage, which another moved worktree of the same checkout may have written, and every directory in no git tree, which other sessions may still be writing on either machine. A transcript the session sweep moved to Postgres has no file; omp resumes it by the path the sweep recorded (`deleted.tsv`). It writes `agentbox-moved` in each session's directory (the transcript path without `.jsonl`) and as `~/.omp/agentbox-moved/<id>`, starts each member in tmux session `moved` on the target (window = first 8 characters of the id) as `~/.dotfiles/scripts/agentbox new <its -e variables and --dir paths> -- omp --resume <transcript path>`, waits until that omp has run 30 s, and appends one line per member to the target's `/mnt/nvme/<user>/cutover/move-log.tsv`: time, session, group, from, to, result, transcript. The old pane becomes a shell that says where the session went. `scripts/agent-session` and `scripts/agentbox-run.ts` refuse to resume a session with the marker (exit 3), by path, id or id prefix, but only on the machine the marker names as `from=` (`AGENTBOX_HOST` in a box), so a copy of it that reaches the target is inert. A git tree whose repository the target already has (its own clone at the same path) goes through git, never by copying one `.git` over another: the checked-out commit is pushed into the target's repository (only the missing objects travel), the tree is registered there with `git worktree add --no-checkout`, its files are mirrored with its `.git` left out, and its index is rebuilt from HEAD, so uncommitted changes arrive as changes (staged ones arrive unstaged); the session's other local branches are pushed without force. **A move to another machine copies what the session used, no wider.** Its inference keeps the deepest directory a process used (a working directory, the directory of a file it writes) and copies a file it only read as that file, never the first directory below a shared root that a box here is given: that widening made LINUX-1248's copy all of `/mnt/nvme/sami/tmp/verified-linux` and S3's all of `/mnt/nvme/sami/frac-verify`, other agents' trees included, and joined S3's sibling `--dir` paths into their parent (2026-11-03). A group is the sessions whose LIVE processes work in a git tree of a member; a tree a session only names (by `--dir`, or in its record) is copied, through git when the target has a clone, and groups nobody. A working directory outside every git tree that holds other trees (a lead root such as `~/Code/personal/theorem`, 881 MiB of worktrees) is made empty on the target, and only the paths the session used inside it are copied there. A session that has moved its work out of a shared tree moves alone with `--cwd <its tree>` (it resumes there) and `--leave <the shared tree>` (neither copied nor a reason to group). The move refuses while one of its processes other than the omp and the move command itself holds a file open for writing in a left tree; a working directory or a pipe is not work there. A git worktree of the session's own under a root every box has (the box preamble's `/mnt/nvme/<user>/wt/<name>`, reached as `~/src/<name>`) is re-created on the target like any other git tree: mirrored, or moved through git into the target's clone. A missing `cutover/target-ready` usually means the target's health check is running (it deletes the file when it starts and writes it again only after a run with no failure, about 6 minutes), so the move waits up to 7 minutes for it and, when it gives up, says to run the move again in about 6 minutes. A dry run never waits. A mirrored git tree whose repository the target lacks is cloned there from its origin before the hang-up, so the tree goes through git and the object store stays out of the downtime; a clone that cannot be made (no origin, not GitHub, an error) is logged and that tree is copied with rsync instead, and a path that already exists there is never cloned over. While a relauncher runs, `~/.cache/omp/agentbox/move-to/active/<sid>` holds `pid=`, `target=`, `start=` and `job=` for each member: written before the hang-up and removed on every exit, so a pane restarter leaves a session whose move is in flight alone (omp-memory-watch resumed LINUX-1248 here 6 s after its 04:10Z hang-up, 2026-11-03). A relauncher stopped by a signal stops its rsync or git push, logs `stopped by signal …; state: …` and removes those files. The other local branches of a tree that goes through git are pushed BEFORE the hang-up; after it, only HEAD goes (the branch push from a blob:none clone ran 3+ minutes into LINUX-1248's downtime). The copy runs twice: the same rsyncs once before the hang-up (with the clone, the branch push and each tree's HEAD and registration) and once after it, which sends only what changed; each pass logs its time and rsync's `--stats` bytes. A failure before the hang-up refuses the move while the sessions still run. Git storage the target already has (a merged common dir whose objects are there, at the same path) is not copied, whether or not a tree of it is mirrored. A member resumes in its transcript header's cwd, which omp adopts on every resume, not the shell's; with `--cwd`, the transcript is re-rooted on the target with omp's own `omp session pack` and `omp session unpack --cwd`, which leaves one file for the id, and the subagents' transcripts, which pack does not carry, are put back beside it. **A failed move says who is down, and tells them.** A member that comes back is logged as rolled back; one that does not is logged `DOWN after <reason>`, and the session, the lead that asked for the move (`AGENTBOX_MOVE_LEAD`) and the `lead-box-health` role are told over Envoy at once. A pane its tmux server no longer has is not retried: the move opens a window of its own on the same tmux session instead (R3A was down 15 minutes on 2026-11-03 while its rollback retried a gone pane 40 times, and its log still read "rolled back"). **A move holds before the hang-up.** After the checks, clones, branch push and first copy, the relauncher writes `~/.cache/omp/agentbox/move-to/hold/<sid>` for each member, tells each session over Envoy, and hangs up only after every member ran `agentbox move --go` at its safe point; after 30 minutes (`AGENTBOX_MOVE_HOLD_WAIT`, 0 for no hold) it refuses with nothing hung up, and the first copy stays on the target for the next try. S3 restarted its 14 lanes during a 66-minute first copy (2026-11-03). Before the hang-up the move also checks that the move's user can write every copy destination on the target; an empty directory owned by root there (docker leaves one when a box starts with a `--dir` that does not exist yet) is removed with `sudo -n rmdir`, and anything else refuses (LINUX-1248's first move failed in rsync on one and rolled back, 2026-11-03 02:48Z). A dry run goes on past a refused check, lists the copy, and names every refusal at the end. **Any failure after the hang-up rolls the whole group back**: the target's windows close, the move waits until no omp there runs a member, the markers go, and each member resumes here as `move --self` would resume it. A move starts only when the target has `/mnt/nvme/<user>/cutover/target-ready` (its provisioning writes it after its checks) and stops for a person after two failed moves in a row or once a session id is seen running on both machines; `agentbox move --to <machine> --clear-halt` is the box-health lead's. A session in a box runs the same command: its group is itself, and the host's tmux server starts the relauncher (`run-shell`), which hangs the box up with `docker kill -s SIGHUP`. `agentbox move --plan --to <machine>` lists the group of the session that runs it (as `move --to` finds it), `--group <session>` that of another session and `--all` every group: each member's resume line, what dies with its hang-up, and every path a move would copy; it changes nothing. `--all` infers every session's paths, 16 at a time, which takes minutes at this host's load. It measures only the mirrored paths (30 s each at most); merged paths are listed unmeasured, since rsync sends only what is newer than the target's copy.

**A tree marked `.no-offbox` never leaves this machine.** The marker is a file named `.no-offbox`; it means that its directory and everything below it may not be copied to another machine or a bucket. The owner of the data writes it (a lane on its embargoed evidence, and on the parent of a frozen read-only set, which cannot hold a file of its own); nobody else removes it. `~/.config/no-offbox/patterns` lists more paths the same way, one shell glob or substring per line. `scripts/no-offbox <path>…` answers for both: exit 0 when every path may leave, 1 naming each refused path and the marker file or pattern that refuses it, because the path, a directory above it up to `/` or a directory below it holds a marker, or a path matches a pattern. A directory below it that it cannot read (EACCES) refuses too, because it may hold a marker. A path gone when read holds no marker, so it is skipped and counted on stderr, and the exit status does not change: a directory removed while the check runs (another session's `git worktree remove` in a shared `.git` refused a move at 03:06Z on 2026-11-03), a path that does not exist, or a symlink that leads nowhere. `agentbox move --to` runs it over every path it would copy (`move_to_offbox`), in the session's command and again in the relauncher, before any hang-up; a refusal ends the move, never a prompt. `omp-teleport --host`, `backup-shared-state` and the sami-devbox bulk copy call it too. A move on this machine, such as the cold move to `/mnt/durable`, may take a marked tree but copies each marker above it to the same place above the new path.

**A move refuses while the session has a process the hang-up would end.** A server, a watcher or a dashboard started from a tool call is a child of the session's omp, and the hang-up of any move ends it: KNOTCURVE's dashboard died with its move at 16:21Z on 2026-11-02 and was down about four hours. So `move --self`, `move --to`, `move <id> --now` and the move in a box list every live process under the omp but omp's own helpers (the worker broker, the python runner) and the move command itself, and refuse before the hang-up unless the session passes `--accept-orphans`; `move --plan`, `move --plan --to` and the Envoy notice list them too. The fix is to start each one detached (`setsid <command> </dev/null >>log 2>&1 &`, whose own session the pane's hang-up does not reach) or as an omp background job, or to stop it; a detached process and what it starts are not orphans. Agents make no systemd units (Sami, dispatch://INFRA-26/comment/615d0105-4ad1-4a2e-ae1c-01a1d8894b5c).

**knives claims are shared between a box and the host, and that is safe.** knives records a claim in `~/.config/knives/state.json` under `claims`, keyed by the omp session id (`KNIVES_OWNER`, else `CLAUDE_CODE_SESSION_ID`, else `OMP_SESSION_ID`), and takes an advisory `flock` on `state.lock` beside it. `agentbox/mounts` has `rw .config/knives` and `rw .cache/knives`, bound at their own paths, and `session_env` sets no `XDG_CONFIG_HOME`, so a box and the host open the SAME inode and contend on the SAME lock: a second `start` of a claimed branch is refused `RefuseHeld`, whichever side asks. So a box and a host session cannot both hold one branch under different ids. The one way both "hold" it is the same session id live on both sides at once, which `move --self` prevents by hanging the host omp up and waiting for it before the pane respawns. A box's exit releases only its own session's claims (`close_box` → `finish_knives_claims`, `knives finish` as that id, which knives refuses for a claim owned by another id). Two gaps to know: a `--dir`-only box whose omp never held its session file open leaves the launcher with no id, and that box's claims stay held with no live process (`knives status` after exit shows them); and an inherited `KNIVES_OWNER` or `CLAUDE_CODE_SESSION_ID` in the launcher's environment outranks `OMP_SESSION_ID` and makes the release refuse, logged as `knives finish … failed; left as is`. Before moving, a lane needs only to keep its session id (which `move --self` does) and to keep its fork's checkout under `~/src`.

Every omp flag after `--` passes straight through. `--resume <id>` gets a fresh box and clones like any other launch (box names are never reused); omp relocates the resumed session's file into the new working directory's session dir, which is what lets a host session, or one from a closed box, continue in a box.

**Every checkout is a git clone of the box's own** (AGENTC-1420, Sami, 2026-10-02: "Let's just switch to Git everywhere"), copied from a template the host keeps per repo under `CLONE_TEMPLATES/<repo>` — `/mnt/nvme/<user>/agentbox/clones` beside the box trees on a machine with that disk, else `~/.cache/agentbox-clones` — outside every box mount. The template is a clone of the canonical checkout's `origin` with `--filter=blob:none`, made on the first launch that needs it and refreshed by a fetch on every launch after. Its `.git` is copied into the box with the objects hard-linked (what a local `git clone` does; git never changes an object file in place), and a checkout from those local objects writes the box's working tree and index — so the templates and the box trees must stay on one filesystem, which is why they move together. So each box's clone is still its own repository, with its own refs, config and index, and stays whole if the template is rebuilt or removed. A box's repos are cloned in parallel. Measured on 2026-10-02 at load 200: a fresh clone of agent-c took 64-78 s, almost all of it the checkout fetching the kept files' contents; a copy took 1.4 s and its local checkout 17.6 s. Inside the box, git fetches a file's contents from GitHub, through the box's App routing, the first time something reads it, so `git log -p`, `blame` or a diff against an old commit fetch what they read. On agent-c's shared jj store (298 workspaces, 135,748 `refs/jj/keep` refs) every jj command took about 11 s, against 0.1 s for git. A repo in `CLONE_SPARSE` (`scripts/agentbox`) also gets a sparse checkout. agent-c leaves out `tasks/` (3.8 GB of its 4.2 GB tree), keeping every `tasks/*/basic_info.json` because `tl validate`'s deployment-catalog check reads all of them, and an agent working on a task adds it with `git sparse-checkout add /tasks/<id>/` (a 94-file task took 1.4 s). Automatic maintenance is off in each clone, since otherwise every on-demand fetch starts a background repack. A template git cannot refresh fails the launch, naming its directory: remove it and the next launch rebuilds it. The checkouts are plain git: jj fails on a clone like this (`Object … of type file not found`).

**Work in an existing host directory with `--dir PATH`.** The directory is shared read-write at its resolved host path, not cloned. With no repository, the first `--dir` is the working directory. A repository still wins when both forms are named. Every box already has `~/src` (and its symlink targets) and the durable tree, so naming a path there selects the working directory without another bind. A path anywhere else, including any tree under `/mnt/nvme/<host-user>`, reaches a box only when named or inferred; the whole NVMe tree is never bound (Sami, dispatch://INFRA-702/comment/11d4bf79-4369-4beb-8691-ec688cee53ab). Shared writes are outside the box disk ceiling, while CPU, memory, and pids limits still apply.

The container root, private home, `/tmp`, `.omp/run`, and private runtime destination cannot be replaced. Other box trees and jj metadata are not prohibited. `box_session_id` has no working-directory fallback for a shared host directory, because that can select another session's transcript.

The caller's environment does not reach the box: `session_env` builds the box's variables from scratch. `-e NAME=VALUE` (repeatable, before `--`) adds one, and a bare `-e NAME` passes the caller's value, as with `docker run -e`: `agentbox new -e OMP_VIEWPORT=0 agent-c core-ops -- omp --resume <id>` starts the session without the transcript viewport. It is set on the container, so it survives `agentbox restart`, and it is applied after the launcher's own variables, so it overrides them. `tmux-omp-ids` and `tmux-resurrect-omp` rebuild a resume command from everything the launcher was given before `--`, so repos and variables carry over to the relaunch.

**Each box has its own `~/.omp/run`; the rest of `~/.omp` is the host's.** omp keeps its daemon brokers there (each scope's `broker.sock`, token, presence records and lease), and that state holds in one PID and network namespace only: the lease is an abstract socket, which Linux scopes per network namespace, and a broker that starts deletes every sibling scope older than five minutes whose pids it cannot see. A shared `~/.omp/run` let one box's broker delete the live scopes of every other box and of the host, leaving their brokers listening on a `broker.sock` gone from disk and every tool call through them failing with `connect ENOENT` or `Daemon broker authentication failed`. So `mount_args` binds `<boxes>/<box>/omp-run` at `~/.omp/run`, removed with the box directory at close, and binds the host's `~/.omp/run/collab-hosts` back on top, so `omp collab` discovery still spans the host and every box. A box starts its own brokers and machine-global daemons, and the host's `omp ps` does not list them. A running box gets this only when it is replaced, because `agentbox restart` keeps the container and its mounts: inside a box, `findmnt -T ~/.omp/run` names the box tree it comes from (`/dev/root[…/boxes/<box>/omp-run]`) when the box has its own, and the `~/.omp` mount when it still shares the host's. On a shared one, killing a broker whose `broker.sock` is gone is no reliable fix and can end the processes it supervises; resume the session in a new box (`agentbox new <repo>… -- omp --resume <id>`) instead.

**AgentBox segregates sessions, not host access.** The home and `/tmp` remain private. Shared host configuration includes writable `.config/gh`, `.azure`, `.ssh`, `.gnupg`, and skills. Workspace storage is `~/src`, the durable tree and named or inferred `--dir` paths, as before; the whole user NVMe tree is not bound. GitHub App and Azure machine defaults remain unchanged, as do existing per-task approvals for using a person's login. No credential is transferred between hosts. See [the access audit](access-audit.md) for authorization and attribution.

**SSH uses the host's writable `.ssh`.** Host keys, identities, and configuration remain available at their usual paths. Startup does not change their ownership, modes, or contents. Fleet defaults are generated only in the box's system SSH configuration, with a private runtime known-hosts fallback. Host user configuration takes precedence. Normal GitHub operations retain the repository's GitHub App route.

**Google Cloud uses this host's own SDK and configuration.** Both `.gcloud` and `.config/gcloud` are writable host mounts. The entrypoint removes no account or configuration. The default route remains the machine identity. A user credential needs its separate per-task authorization. A host that lacks a login cannot supply it to a box, and credentials are not copied between hosts.

**`agentbox doctor` compares host access with a new box.** From an existing box, use `agentbox doctor --here` for the box-side checks. Credential probes without a host comparison are notes, not evidence that the box lost access. Docker checks must accept existing host logins and helpers. Print registry names and exit codes, never credential values or the full Docker config.

**A credential check that fails in a box fails on the host just as often, so doctor asks both.** `secrets GHCR_PULL_TOKEN`, the Docker Hub credential helper that reads `DOCKER_HUB_OAT`, `aws sts get-caller-identity`, `hawk-token`, `google-user-token`, `gcloud auth list` and `kubectl --context gke_theorem-agent-infra_us-west1_dispatch -n builds auth can-i create jobs` answer for what the MACHINE is logged into: a box can only be as logged in as the host under it. doctor runs one definition of each (`PROBE_FUNCS` in `scripts/agentbox`) on both sides and compares (`report_probes`). A box that cannot do what the host can is a `FAIL` naming both answers. Where neither can, the line is a `note` that says it is host state, repeats what the host said, and gives the command that shows it — so nobody hunts a box for a credential the machine never had. On sami-rocqperf, 2026-10-31, that is five of them: no `GHCR_PULL_TOKEN` and no `DOCKER_HUB_OAT` in any agent-tier file (`~/.dotfiles/secrets.local.env` does not exist here, and the broker answers `UNKNOWN_SECRET`), no EC2 instance role (the machine is an Azure VM; 169.254.169.254 answers 404 to every EC2 path, so `aws` and the `google-user-token` that reads AWS Secrets Manager both fail), and no DNS for `api.hawk.internal.trajectorylabs.com`. **A home path outside the allow-list is writable, and that is the trap.** `~` inside a box is the box's own directory (`<boxes>/<box>/home`, on the box filesystem since INFRA-702; it was the container overlay before), with the allow-listed host paths bind-mounted on top (`findmnt -T ~/.omp` → the host device, `findmnt -T ~` → the box's loop device). So `mkdir -p ~/.newstate && echo x > ~/.newstate/f` exits 0 and the host never sees the file; it is gone when the box is torn down, and nothing errors at any point. Only a path whose parent does not exist in the box fails (`cat >> ~/.absent/notes.md` → `No such file or directory`), which is the lucky case. Before choosing a home-directory location for anything that must outlive the box or be read from outside it — a ledger, a run directory, a cache another session reads — check it is under a `mounts` entry (`findmnt -T <path>` names the host's `/dev/root` or `/dev/md127`, not the box's `/dev/loopN`), and if it is not, add the entry rather than the path. Measured 2026-09-21 in `agentbox-25988be444cf`: the librarian's ledger at `~/.librarian/notes.md` had been unreachable since the 2026-09-20 relocation; the session noticed the missing directory at 01:26Z that night and went 43 hours without a ledger before relocating it under `~/.omp`.

**The box home path matches the host user's home path.** Before starting any user process, the entrypoint sets the password-database home to `$HOME`. It assigns private home directories to `AGENTBOX_USER` and prunes exact host mountpoints, not device numbers. Shared SSH state is neither traversed nor chowned. Generated private-home SSH directories are assigned to the session user when that mode is used.

**A move stops a session once, when the session says so.** `agentbox move --to` does its checks, its clones and its whole first copy while the session works, then holds and tells the session: run `agentbox move --go` at your next safe point. That `--go` is the ONLY moment the move stops the session, and nothing stops until it is run (the hold waits `AGENTBOX_MOVE_HOLD_WAIT`, 30 min by default, then refuses the move with nothing hung up and leaves the copy on the target for the next try). So never give a lane a time to stop at and wait for: the librarian stopped ten subagents for two hours waiting for a 14:40Z slot on 2026-11-03. Keep working; answer the hold when it comes.

**A box's `$HOME` is a directory of the box: `$BOXES/<box>/home` on the host, and it goes when the box goes.** Only the allow-listed paths under the home are mounts of the host's own home; everything else a session writes in `~` (a note, a wake file, a draft) lives in that one directory, inside the box's own filesystem, and `close_box` removes it with the box. `agentbox move --self` on sami-devbox removed box `agentbox-74a3ddaacbdc` at 17:22Z on 2026-11-03 and took PEER's `~/WAKE-peer-01a13837.md` and `~/.leanperf.md`, written minutes before, with it. Keep state a later session must read in a `--dir` path (`/mnt/nvme/<user>/…`, `/mnt/durable/<user>/…`), never in `~`. A close now copies every home file written since the box started to `$BOX_HOMES/<session id>/<box>-<time>` (`~/.local/state/agentbox/box-homes`, `AGENTBOX_BOX_HOMES`) and the session's next box starts with those files in its home, without replacing one the new launch wrote; over `AGENTBOX_BOX_HOME_CARRY_BYTES` (2 GB) the whole box directory is kept in place instead, and named on stderr.

**A box's checkouts are no longer worktrees of the shared checkouts.** Until 2026-10-02 each was a jj workspace, registered under `~/src/<repo>/.git/worktrees/` with a path only its own box could see, so a `git worktree prune` run from any other box deleted live registrations (14 boxes at once on 2026-09-21), and the launcher locked each one. A box started before that change keeps its locked worktree until it closes, so never run `git worktree prune` (or anything that does — `git gc` with an expiry, Legion's workspace provisioning) on `~/src/<repo>` from inside a box.

**Host services reach the box two ways.** Sysbox maps the box onto a subordinate uid range (the host sees a box peer as uid 232072, not 1000), and dbus-daemon refuses a peer whose uid is not the user's, so the launcher runs socat relays as transient user units (`ensure_forwarders`): each accepts the box on a 0600 socket and connects onward as the user, so the daemon sees the user. `agentbox-bus` relays the session bus (`DBUS_SESSION_BUS_ADDRESS` in the box), which is what makes the GNOME keyring — and every tool that keeps a login in it: hawk (`!hawk-token`), pup, gws — work unchanged inside, with no per-tool passthrough. The same bus reaches the host's systemd user manager, so `systemctl --user start`/`stop`/`restart`/`status` in a box act on the host's units (`forward-serve`, `secretsd`, …): a restart from a box restarts the host's service. The unit-file verbs (`enable`, `disable`, `link`, `mask`, `is-enabled`) do not: they read and write `~/.config/systemd/user`, which in a box is the overlay, so they change nothing on the host and report on the box's empty copy. Host processes stay out of reach too, because the pid and `/tmp` namespaces are the box's own. **secretsd is the one service that must not be relayed.** It pins the process that `REGISTER`s a session token (`SO_PEERPIDFD`) and serves only that process's descendants; through a forking relay every connection is a different socat child that exits with the connection, so the pinned root is dead by the first `GET` and every request is refused `FOREIGN_CALLER` — `secrets grants` still answers, because it is unscoped, which is how the breakage hid. The launcher bind-mounts the daemon's socket node (`/run/user/$UID/secretsd.sock`) into the box at the same path instead; systemd's `secretsd.socket` unit owns the node, so it survives daemon restarts. The box's `/run/user/$UID` is an ubuntu-owned per-box directory holding the relayed bus, the secretsd socket, an empty 0700 `secretsd/` token dir for the omp extension, and the host's `forward/` directory (the arming, browser-grant and pulse sockets). That one is mounted as a directory because a restarted `forward serve` rebinds its sockets, which a mount of the socket file would not show. It is also what lets a web app inside a box reach Sami's laptop browser: `forward port <ports>…` in the box (the `using-forward` skill).

**The host's tmux server is relayed into every box, so a lead can drive other sessions' panes** (dispatch://INFRA-702). A lead starts and steers panes — `tmux new-window`, `send-keys`, `capture-pane`, `list-panes` — and without the host's tmux server a boxed lead can do none of it, which would leave the coordination sessions, the heaviest on this host, outside every limit this work exists to apply. A bind of the socket is not enough: measured 2026-11-01 in a throwaway box given `/home/sami/.tmux/sockets/tmux-1000`, `connect(2)` succeeded, because Sysbox id-maps the bind and the node arrives as the box user's, and every tmux command answered `access not allowed`, exit 1 — the tmux server's own check of the client's `SO_PEERCRED` uid, which under Sysbox is a subordinate uid and not the user's. So it gets the same treatment as the session bus: `agentbox-tmux` (`ensure_tmux_forwarder`) relays it and connects onward as the user. tmux's non-attaching commands survive a relay — measured on the host, `display-message -p '#{version}'` through a `socat UNIX-LISTEN`/`UNIX-CONNECT` pair answered `3.8` — and attaching from a box is meaningless anyway, since the box has none of the host's terminals. The host socket is the one the launching session itself uses (`$TMUX`'s first field, so a machine whose `TMUX_TMPDIR` is not `/tmp` is followed rather than guessed; `AGENTBOX_TMUX_SOCK` overrides, and a host with no tmux gets no relay). Inside, it is `TMUX_TMPDIR=/run/user/<uid>/tmux` holding `tmux-1000/default`, which is where a bare `tmux` looks, so no command needs `-S`; `TMUX` itself is deliberately unset, because a box is not inside a pane. **State plainly what this gives a box:** control of the host's tmux server — read any pane (`capture-pane`), type into any pane (`send-keys`, which in a pane sitting at a shell is a command as the host user, outside the box's cgroup and disk limit), respawn or kill any pane, and `kill-server`, which would end every agent pane on the machine. It is given because the relayed session bus already reaches the host's systemd user manager, so a box can already restart the host's services (the paragraph above), and because the alternative is that leads stay on the host. The relay is one unit for every box, so it always reaches the host's DEFAULT server (`default` beside the launching shell's own socket, else under `TMUX_TMPDIR`), never the server a launch comes from: on 2026-11-02 one `agentbox new` from a `tmux -L devbox-drill` pane re-pointed it, and every box reached the drill's server from 17:18:45Z to 17:58Z. A box launched from another server gets no `TMUX_PANE`, because that pane id would name a different pane on the default server.

**A box's secrets-broker identity belongs to its SESSION (AGENTC-393, dispatch://INFRA-1167), and a box without one is normal.** When the host's agent-secrets helper holds a live launcher credential (`agent-secrets-login`, `agent-secrets/AGENTS.md`), `agentbox new` puts `enrollment.pending` in the box's key dir (`/run/user/<uid>/agent-secrets` inside, `$RUN_BASE/<box>/run-user/agent-secrets` on the host; `AGENT_SECRETS_KEY_DIR`), keeps it fresh while it waits, and once omp's session id appears makes that session's key on the host, in `$RUN_BASE/session-keys/<session id>` (0700, key 0600, host tmpfs, mounted by no box), copies it into the box's key dir, enrolls it from the host under the runtime id `session-<session id>`, and starts `agent-secrets renew` in the box for its lease, in a loop that restarts it 10 s after it exits (log: `renew.log` in the key dir). The same key under the same runtime id gets the **same enrollment back** (broker `enroll.go` `recoverConflict`), so the session that moves into a new box keeps its enrollment id — and with it every credential request Sami has not yet answered and every grant he has given, both of which are bound to that id alone and are cancelled when it ends (broker `enroll.go` `endEnrollment`). A box with no session id (a `--` command that is not omp, `doctor`, an `omp --no-session` run) keeps the older shape instead: `agent-secrets keygen` inside the box, enrolled under the box's own name. Success leaves `key.pem` and `enrollment` and no marker. Any failure leaves `enrollment.error`, and removes the key and the marker; a host key that cannot be made, or a session whose live enrollment the broker still holds under a key this host lost (a reboot), falls back to the box's own name with a line on stderr rather than leaving the box with no identity. The host keeps its own files in `$RUN_BASE/<box>`, which no box mounts: each attempt's error, the session the enrollment belongs to, and the enrollment id, never the box-writable copy. `close_box` does **not** revoke a session's enrollment itself — that would cancel what the session has pending, which is exactly what a move must not do. It hands it to a detached waiter that gives the session `AGENTBOX_UNENROLL_GRACE` seconds (180) to come back in another box, which writes its own name into the session's `owner`, and ends the enrollment and removes the key only when none did (log: `$RUN_BASE/session-keys/unenroll.log`). A lease nothing renews lapses at the broker within 15 minutes in any case. A box with no key (no credential when it started, or a failed enrollment) has no broker identity, and its agents use secretsd. `agentbox doctor --here` reports that as a note, and reports the identity checks for a box that has one.

**A shared cache is only as safe as its tool's garbage collector.** `.cache/ms-playwright` is mounted rw into every box (`mounts`) and is the host's too, and `playwright install` garbage-collects it by path visibility: `_validateInstallationCache` (playwright-core 1.63, `lib/coreBundle.js`) reads `<target>/browsers.json` for every `.links` entry, counts an entry whose target it cannot read as broken, and deletes every browser build only broken entries used. From one box, a checkout in another box's `/tmp` or overlay is unreadable, so an install there deletes the browser that box is using: on 2026-09-25 installs at 02:13Z and 04:04Z removed `chromium_headless_shell-1243` and then `-1234` in turn, and a live e2e mutation run failed every later mutant at browser launch, which reads exactly like mutants being killed (platform PO, from the #20064 reviewer's report). Every agent session now carries the collector's own opt-out, `PLAYWRIGHT_SKIP_BROWSER_GC=1`: boxes through `session_env` in `scripts/agentbox`, host shells through `.bashrc` (Sami, 2026-09-25). It is a container launch variable, so a box started before that change lacks it until it is replaced (`agentbox restart` keeps the container's environment); in such a box, or anywhere the variable is missing, install with it set or into a `PLAYWRIGHT_BROWSERS_PATH` you own. Old builds then accumulate in the shared cache until `disk-hygiene` removes them. The same shape as the worktree prune above: a tool tidying what it cannot see as in use.

**Host services retain their existing routes.** Metadata reaches box processes through `AGENTBOX_IMDS_FORWARDER`. AgentBox adds no blanket metadata firewall to nested Docker workloads. Independent task and grader controls remain unchanged. Envoy's loopback API reaches the box through `AGENTBOX_ENVOY_FORWARDER`. Connection settings and credentials come from the profile's `envoy.json`, including the mounted neutral file under `.config/legion`. The launcher does not pass `ENVOY_URL`, `ENVOY_NATS_URL`, `NATS_NKEY_SEED_FILE`, or Dispatch connection overrides. It sets `ENVOY_MACHINE_ID` from `AGENTBOX_HOST` with an FQDN suffix removed, so sessions group under the physical host. This identity neither enables a profile connection nor changes its server or credentials. Changed identity or mounts require a new box.

**Docker state is a complete host snapshot in the private box home.** It includes logins, helpers, contexts, and certificates. External targets stay writable through host mounts. Private helper commands preserve the host-selected invocation path and name; shared mise shims run directly. Internal readiness targets the inner Unix socket without changing the user's selected context. `scripts/docker-registry-auth-check` follows the selected helper, global store, or inline credentials and emits only safe status. Its checks do not log in or write Docker configuration. Later host Docker logins require a new box.

**Forward's live loopback endpoints are relayed into each box.** The launcher reads `~/.config/forward/config.toml` (`forward_channels`): preview, callback bridge and grant feed use `listen`; URL, browser relay, PC/SC and audio use `peer`. Only configured IPv4 loopback endpoints with a live listener get a gateway relay and an entry in `AGENTBOX_FORWARD_CHANNELS`, including custom channel ports outside 128xx. The entrypoint recreates those exact address/port endpoints inside the box (log: `/var/log/forward-relay.log`). Tailnet endpoints route directly and get no loopback relay. Conflicting destinations sharing a gateway port fail discovery, including metadata, Envoy and other loopback-service routes; identical routes are not installed twice. The gateway identifies targets by port only, so assign distinct channel ports. Forward uses the same canonical config path in the shell, user units and boxes: `XDG_CONFIG_HOME` must be unset, empty or exactly `$HOME/.config`. A missing config or no live loopback channels passes none. `agentbox doctor` compares the box's `forward doctor` rows with the host's and fails on a difference.

**Other host services on the loopback are relayed the same way.** `LOOPBACK_SERVICE_PORTS` in `scripts/agentbox` names them by port (`AGENTBOX_LOOPBACK_PORTS`, space-separated, replaces the list). Each one with a listener on this host's 127.0.0.x gets a forwarder on the box network's gateway (`agentbox-loopback-<port>`) and rides `AGENTBOX_FORWARD_CHANNELS` to a relay in the box on the same address and port, so it needs no image change. A port with no listener is skipped, and a forwarder that does not start is reported but does not stop the launch. Today the list is `5005`, the OSS Verify MLflow tracking server: on sami-rocqperf the machine-local unit `ossv-mlflow-tunnel.service` holds an IAP tunnel to VM `ossv-mlflow` on `127.0.0.1:5005`. On 2026-11-02 every route to it from a box failed and two lanes waited on it: the box's own loopback, the box network's gateway, docker0's `172.17.0.1`, and the tailnet name and address (`tailscale serve`'s `:8449` listener is bound to the `tailscale0` device, so a packet from a box bridge never reaches it). A box now reaches MLflow at `http://127.0.0.1:5005`, the address a host session uses, and a workload in the box cannot listen on that port itself. A box started before this change has no relay inside, but while the host forwarder runs it reaches the same server at `http://<gateway>:5005` (`172.22.0.1` here).

**Each box has CPU, memory, pids, and disk limits.** Memory defaults to one twentieth of host memory in whole GiB, with a 24 GiB floor and a cap of four times the default. That is 24 GiB on sami-rocqperf and 109 GiB on sami-devbox, with 8 GiB of additional swap. CPU defaults to 8 cores, capped at 32, and pids at 8192. Disk defaults to 128 GiB on sami-devbox and 32 GiB elsewhere, capped at 512 GiB, or `--disk 0` for no private disk ceiling. `--memory`, `--cpus`, and `--disk` override the matching `AGENTBOX_*` variables. Shared host writes remain outside the private disk limit, and the doctor box uses the same resource limits.

**At its memory limit a box loses one process, not the session.** The kernel kills the box process with the largest badness (its RSS plus `oom_score_adj` × limit / 1000), and the box's docker scope runs `OOMPolicy=continue`, so the rest keeps running: on 2026-11-01 at 12:17:36Z a box lost a 2.0 GB python child and carried on. With every adj at 0 the largest process is often omp itself, and host-side `scripts/omp-memory-watch` cannot raise a box's processes (Sysbox maps their uid; it gets EPERM). So `scripts/agentbox-run.ts` raises them from inside: every 10 s each child of the runner but omp, and each child of omp, goes to +500 with the descendants it already has, and later forks inherit it. Under a 24 GiB limit that adds 12 GiB to each one's score, so the largest of them still goes first and omp outlives them all. The runner and omp stay at 0.

**The disk limit is a sparse ext4 filesystem.** Each image lives under `<boxes>/../disks/<box>.img`, or `AGENTBOX_DISKS`, and is loop-mounted at `<boxes>/<box>`. It holds the box's clones, home and `/tmp`. Defaults are 128 GiB on sami-devbox and 32 GiB elsewhere. The image reserves no space. Creation requires at least 500 GiB free on the image's host filesystem, including a launch with `--disk 0`. Mounts use `discard` to return freed blocks to the host. `--disk 0` disables the image, not the free-space check. The container's writable layer remains outside this limit. A box kept for unpushed work keeps its image mounted, with a release command printed on the pane.

**Grow a running box from the host.** `agentbox grow <box|session-id> <size>` extends the image with `truncate`, refreshes its loop device with `losetup -c`, and runs `resize2fs`. It does not restart the session. It refuses shrinking and sizes above 512 GiB. Repeating the same size completes an interrupted resize. The container's `AGENTBOX_DISK` remains its launch-time value after a grow. `df` shows the current filesystem size.

**Build caches use the host disk.** Each box gets `/mnt/nvme/<user>/box-cache/<box>`, or `~/.cache/box-cache/<box>` without NVMe. `AGENTBOX_CACHE_ROOT` changes the parent. The launcher creates the cache before starting the box and removes it when docker confirms the box's container is gone. It sets `XDG_CACHE_HOME`, `GOCACHE`, `GOMODCACHE`, `npm_config_cache`, `BUN_INSTALL_CACHE_DIR`, `UV_CACHE_DIR` and `PIP_CACHE_DIR` there. Cargo's registry and git downloads use nested mounts from that cache. Cargo binaries and configuration keep their normal paths. Project-local `target/` directories remain unchanged. No shared `CARGO_TARGET_DIR` is set, so independent builds do not contend on one target lock.

**The disk watch checks running box homes.** The existing `disk-fill-watch` timer checks every loop-backed box home. At 90% used, it sends the owning session and the SRE an alert with the biggest directories. Each crossing alerts once and rearms below 85% used. Failed sends remain pending. Each run logs allocated image bytes, box-cache bytes and their total. Sparse capacity does not count as allocated bytes. The watch must receive any custom image or cache root settings to measure those directories. `--dry-run --print-alert` prints the alerts without sending them. No extra timer or unit is required.

**Running boxes keep their current environment and mounts.** These cache defaults apply at the next re-box, not an omp-only `agentbox restart`. No running box is restarted for this change.

- **`Dockerfile`** — Ubuntu 24.04 with docker-ce (the box runs its own `dockerd`), Chrome (omp's browser tool), pip, `python3-yaml` and `python3-venv` (repository scripts run by the system `python3` import yaml, and `python3 -m venv` needs ensurepip; without them the Verified Linux baseline farm and the release lane's scripts failed in every box, 2026-11-02), postgresql-client, sqlite3, socat, wget, `bc` (agent-c's Pulumi suite runs a script that needs it, and CI runners have it, so a box without it reds a required local gate that CI passes), `bsdextrautils` for `column` (`scripts/envoy` formats `envoy ps` with it, so without it the human-readable listing died with `column: command not found` in every box while `envoy ps --json` worked, dispatch://INFRA-702), passwordless sudo for uid 1000, and the `/etc/agentbox-identity` marker, which `shims/omp` reads to say the box cgroup is the session's memory ceiling instead of reporting the systemd scope a box cannot get, and the disk-hygiene skill reads to sweep the box tree alone. Other tools are not installed here: the host's mise store is mounted in, so `mise.toml` pins apply inside exactly as on the host.
- **`agentbox_sandbox_skips.py`** — the pytest plugin every pytest in a box loads (the `Dockerfile` puts it under `/opt/agentbox/python` with an entry point and sets `PYTHONPATH` to it): a red banner when sandbox tests skipped, below ("Sandbox tests do not run in a box").
- **`entrypoint.sh`** — starts inner Docker and host-service relays, preserves Docker credential routes, creates private SSH defaults without rewriting shared host SSH files, then runs the session as `AGENTBOX_USER`.
- **`devbox-prune`**, **`devbox-prune.service`**, **`devbox-prune.timer`** — the host's prune of the always-safe class, a script to run by hand (`~/.dotfiles/agentbox/devbox-prune`): `docker volume prune -f` on the host daemon; in every running agent box, `image`, `builder` and `volume prune -f` on the box's own daemon (never `-a`; an empty `--config`, because a box's `builder` alias can point at depot); and host Go build cache entries idle more than 2 days. It logs bytes reclaimed per box and fails the run naming the box and command. `install.sh` sets up no timer (Sami, 2026-09-27). A host that should run it every 6 h links and enables the units by hand, as the shared devbox does: `ln -s ~/.dotfiles/agentbox/devbox-prune.{service,timer} ~/.config/systemd/user/ && systemctl --user daemon-reload && systemctl --user enable --now devbox-prune.timer`. The links point into the `~/.dotfiles` checkout, so moving or renaming these files kills that host's timer silently once systemd reloads: the devbox lost its 6-hourly prune that way on 2026-09-27, when `docker-volume-prune.*` was renamed away.

Root inside the box is Sysbox fake-root (a user namespace on the host), so `sudo apt-get install`, the inner Docker daemon, and nested containers (`tl run` sandboxes) work without host privileges. `sudo apt` installs die with the box; mise/uv/bun/npm installs persist through the mounted stores; durable image changes go in the Dockerfile plus `agentbox rebuild`.

**`bwrap --unshare-net` runs in a box; a sandbox in a new user namespace does not.** The image ships `bwrap` setuid root (2026-11-03, for BET-64's leak-check tests, which run the real gh inside `bwrap --unshare-net`): `bwrap --unshare-net --ro-bind / / --dev /dev --proc /proc …` runs as the box user, because setuid bwrap takes no user namespace. Unprivileged it fails in a box (`loopback: Failed RTM_NEWADDR: Operation not permitted`), and a run that asks for a new user namespace (`--unshare-all`, `--unshare-user`) still fails, as below; the box's root is not the host's, and the box user has sudo already, so the setuid bit grants nothing new. A test that needs an unprivileged user namespace with its own `/proc` cannot pass here. Measured on sysbox-runc 0.7.1 (the latest release), 2026-11-02: Sysbox traps every procfs mount in the box and performs it itself (sysbox-fs `seccomp/mount.go`, `processProcMount`), adding its own submounts (`/proc/sys`, `/proc/uptime`, `/proc/swaps` from sysbox-fs, masks on `/proc/keys`, `/proc/timer_list` and others), and for a mount made from a nested user namespace that handling fails (`error receiving fd via SCM_RIGHTS` in the sysbox-fs log), so a bwrap run that unshares every namespace and mounts its own `/proc` dies at `Can't mount proc on /newroot/proc: Invalid argument`, as `ubuntu` and as root alike. Even past that, the kernel would refuse it: a nested user namespace may mount proc only where a proc mount with no covered entries is already visible, and Sysbox gives every proc mount in the box those submounts and ignores an unmount of them. A clean proc cannot be made either: `fsopen` and `open_tree` are refused (EPERM) and a bind of `/proc` gets the submounts too. With `SYSBOX_SYSCONT_MODE=FALSE` bwrap cannot make a user namespace at all and the inner dockerd does not start, and Sysbox refuses `--privileged`. So such tests skip in a box, and pytest ends green: grading-tools `tests/test_bwrap.py` (360 tests) gave 313 passed, 47 skipped in a fresh box, and 359 passed, 1 skipped on the host at origin/main 17cce1680. Every pytest in a box loads `agentbox_sandbox_skips.py` (on `PYTHONPATH`, through an entry point, so a caller that replaces `PYTHONPATH` loses only the banner): after the summary it prints a red banner naming how many sandbox tests skipped and why, and one more line after pytest's own last line. Run them on the host or in CI before you report them green. `unshare -Ur` as `ubuntu` fails in a box as it does on the host: Ubuntu's `kernel.apparmor_restrict_unprivileged_userns=1` lets only profiled programs such as `bwrap` make one.

knives: claims are keyed by the omp session id, so a boxed `knives start` is released at box exit without `--force`. The registered forks still live at their pre-`~/src` paths (`~/inspect/*`, `~/toon-rust/default`, …), which a box does not mount; `knives start` from a box works once a fork's checkout is moved under `~/src` (knives places workspaces next to the checkout, so they land inside the mount).

Secrets work from a box on both tiers as of `forward` v3.2.3 (sjawhar/forward#40): the daemon runs in the private user namespace its mount protections imply, so a same-uid client in a box arrives at `SO_PEERCRED` as the overflow uid, and the daemon decides admission on the socket node being owner-only rather than on that uid. With the socket mounted directly, omp's `REGISTER` pins the box's omp process and the ancestry walk crosses the container boundary (box pids are host pids to the daemon). `agentbox doctor` runs it on the host and inside the throwaway box.

### How changes take effect

Host-mounted tool, plugin, and configuration updates reach the next omp process. `agentbox restart` reuses the container, mounts, and environment. Changed mounts or launch environment require a new box. The image tag hashes `Dockerfile`, `entrypoint.sh`, `box-ssh-config`, and `agentbox_sandbox_skips.py`. `agentbox new` builds a missing image; `agentbox rebuild` builds it explicitly and lists older running images. Existing boxes are not restarted automatically. `agentbox doctor` compares the host with a throwaway box, and `agentbox sh <box|session-id>` opens a running box.

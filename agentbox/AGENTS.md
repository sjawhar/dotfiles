# agentbox

The opt-in **agent box**: the image (`Dockerfile`, `entrypoint.sh`) and the home allow-list (`mounts`) that `scripts/agentbox` runs a session with.

One disposable Sysbox container per **agent session**, working in a jj workspace made for it. `agentbox new <repo> omp [omp args…]` names a canonical checkout under `~/src` (`AGENTBOX_SRC`), adds a jj workspace of it at `~/boxes/<box>/<repo>`, and runs `scripts/agentbox-run.ts` there as the container's main process (`docker run --rm`), with `shims/omp` as its child; any other command runs bare. The box lives exactly as long as the session. When omp exits — clean exit, pane kill, launcher killed — the launcher releases every knives claim the session holds (`knives finish`, as that session), snapshots the working copy (`jj workspace update-stale`, then `jj st`: a workspace another session's operation left stale is recovered with its unsaved edits in a commit, not left on disk), forgets the workspace, and removes `~/boxes/<box>`. Uncommitted edits survive as a commit in the canonical repo's op store; the directory does not.

**Restart in place.** `agentbox restart <box|session-id>… | --all` relaunches a box's omp without touching the container: the runner hangs omp up (its ordinary graceful teardown) and spawns `omp --resume <id> .` again through the shim, so the new process runs the current `mise.toml` pin, plugin tree and config, while the container, its workspace, `/tmp` and anything else inside stay. The `.` is the resumed session's first message: without it the agent waits at the prompt until someone types, because nothing else tells it the restart is over. By default the host only sends the session an Envoy notice — finish the current step, start nothing long, then run `agentbox restart` (the in-box form: no arguments, restarts this session) — so the agent picks the moment; omp's own settled-boundary shutdown is not involved, the agent's judgment is. `--now` hangs omp up at once, interrupting whatever it is doing (resume replays the persisted transcript; a tool call in flight is lost). The session to resume is the file omp holds open, or the newest session file of the box's working directory (an idle session holds no writer after a resume). Nothing persists a pending restart: an agent that never runs the command keeps running until `--now`, and a replacement omp that dies on startup ends the box instead of looping. omp's own `/restart` cannot do this — it re-execs the versioned mise install path and so never sees a new pin. What still needs a new box: a launcher-env change (`session_env`, mounts), an image change, the runner itself.

Every omp flag passes straight through. `--resume <id>` gets a fresh box and workspace like any other launch (box names are never reused); omp relocates the resumed session's file into the new working directory's session dir, which is what lets a host session, or one from a closed box, continue in a box.

**A restart orphans the old worker broker, `persist: true` does not save a supervised process from it, and killing the orphan is not reliably a fix.** Measured on two boxes, 2026-09-26. Both showed the same signature: one `__omp_worker_daemon_broker` parented by docker-init, `ss -xlp` showing it listening on the scope's `broker.sock` while that file is gone from the directory, and deleted `output.log` fds of the supervised processes it still owns. On the first box a process started with `persist: true` did NOT survive the restart — it was the OLD broker's child — the orphan blocked the new broker for ten minutes, and terminating it cleared the block but took the supervised process with it. On the second, `SIGTERM` did NOT restore hub at all: every fresh broker wrote `broker.pid` and `scope.json` and then exited before creating `broker.sock`, the same ENOENT as before the kill, while the kill still took down both live monitors that were the orphan's children. So the probe is `pgrep -f __omp_worker_daemon_broker` returning more than one, or `ls -la /proc/<old pid>/fd | grep deleted` naming your scope — and BEFORE signalling, inventory what that broker is parenting and make sure you hold the launch command for anything you still need, because the kill may cost you those and buy nothing. Relaunch survivors detached (`setsid nohup …`) and confirm they are ticking rather than assuming; read a supervised process's **exit file** rather than its log, since the log cursor is empty across a restart and silence reads like health. Filed as a harness issue; until it is fixed, treat a restart as something that can cost you your background processes outright.

**The box sees an allow-list of the home directory and nothing else** — `agentbox/mounts`, one `<rw|ro> <path>` per line, read by `scripts/agentbox` at launch and checked entry by entry by `agentbox doctor` from inside a box. Beyond the list: the canonical checkouts (`~/src`, plus the target of any symlink in it — `~/src/dotfiles → ~/.dotfiles`), the box's own directory, and the dotfiles. The list holds omp state, the mise tool store and language caches, `~/.aws`, `~/.kube`, `~/.pulumi`, the tool configs a session relies on, and read-only configuration including the jj-signing pair. A CLI's own login state belongs there when boxes need that CLI — `~/.fleet` (fleetctl), `~/.sentry` (sentry), `~/.config/depot`, `~/.config/pup` (pup's site registry; its tokens are in the keyring, which the relayed session bus already serves) — so no API key is handed to a box for a tool the host is logged into. An identity that can act as the user on GitHub never is: no `~/.config/gh`, ssh keys, gnupg or docker login, so an agent inside pushes only as the GitHub App its repo routes to. Adding a tool is one line in the file; running boxes see it at their next relaunch.

**`agentbox doctor` is a HOST command, and from inside a box it never reaches the box checks.** It runs the host-side suite first — sysbox runtime registration, the session bus, the IMDS forwarder's bind — every one of which fails by construction in a box's view of the host, and it aborts there, before the block it execs *into* a box (`scripts/agentbox`, the `cmd_doctor` heredoc). Four sessions on 2026-09-26 read those three FAILs as their own box's health while the docker checks they actually needed never ran. From inside a box, run that block's lines directly — but know what each one can tell you. `jq -e '.credHelpers["https://index.docker.io/v1/"] == "secretsd"' ~/.docker/config.json` is the one that discriminates: it is false on an unmerged box and true after the entrypoint's merge. `printf %s https://index.docker.io/v1/ | docker-credential-secretsd get | jq -e '.Secret | length > 0'` passes on a BROKEN box too, because it asks secretsd directly and says nothing about what docker uses — it proves the helper works, which is why a repair is safe, not that a repair happened. Neither proves docker *routes* there; that needs a real pull of an image the box lacks with the anonymous rate-limit counter read before and after (unchanged ⇒ the helper was used). A box's `.auths` should hold only `ghcr.io`: a Docker Hub or ECR login sitting under `auths` instead of `credHelpers` is the shape that shadows a working helper, and doctor's own auths assertion catches it. Print keys and exit codes, never the file: `auths` values are base64 `user:token`, and two sessions leaked the same live org PAT into their transcripts by printing it.

**A home path outside the allow-list is writable, and that is the trap.** The box's root is an overlay; `~` inside it is that overlay with the allow-listed host paths bind-mounted on top (`findmnt -T ~/.omp` → `/dev/root[/home/ubuntu/.omp]`, `findmnt -T ~` → `overlay`). So `mkdir -p ~/.newstate && echo x > ~/.newstate/f` exits 0 and the host never sees the file; it is gone when the box is torn down, and nothing errors at any point. Only a path whose parent does not exist in the box fails (`cat >> ~/.absent/notes.md` → `No such file or directory`), which is the lucky case. Before choosing a home-directory location for anything that must outlive the box or be read from outside it — a ledger, a run directory, a cache another session reads — check it is under a `mounts` entry (`findmnt -T <path>` names the host device, not `overlay`), and if it is not, add the entry rather than the path. Measured 2026-09-21 in `agentbox-25988be444cf`: the librarian's ledger at `~/.librarian/notes.md` had been unreachable since the 2026-09-20 relocation; the session noticed the missing directory at 01:26Z that night and went 43 hours without a ledger before relocating it under `~/.omp`.

**The box's workspace is a locked git worktree of the shared checkout.** `jj workspace add` on a colocated checkout registers the workspace under `~/src/<repo>/.git/worktrees/`, and that registration names a path — `~/boxes/<box>/<repo>` — that exists only on the host and inside that one box. Every other box sees it as missing, and `git worktree prune` there removes the registration of every worktree it cannot see: one session's `git worktree remove … ; git worktree prune` from its box on 2026-09-21 left 14 live boxes with `fatal: not a git repository` (jj kept working; `gh` through `knives gh` could no longer read the owner and ran unauthenticated). The launcher therefore runs `git worktree lock` on the workspace right after creating it — a locked worktree is what prune skips, and jj's `workspace forget` at box exit removes it regardless. The lock covers only workspaces agentbox made: a workspace a session adds itself inside a box is unregistered by a prune from any other box unless the session locks it the same way (`git -C ~/src/<repo> worktree lock <path> --reason '<why>'`), wherever it lives: another box sees neither this box's overlay nor its `~/boxes/<box>/` directory (from inside a box, `ls ~/boxes/` lists only its own). Never run `git worktree prune` (or anything that does — `git gc` with an expiry, Legion's workspace provisioning) on `~/src/<repo>` from inside a box; a registration that is gone is rebuilt by recreating `.git/worktrees/<name>/{gitdir,commondir,HEAD}` from the workspace's `.git` gitlink and jj's `@-`, and locked.

**Host services reach the box two ways.** Sysbox maps the box onto a subordinate uid range (the host sees a box peer as uid 232072, not 1000), and dbus-daemon refuses a peer whose uid is not the user's, so the launcher runs socat relays as transient user units (`ensure_forwarders`): each accepts the box on a 0600 socket and connects onward as the user, so the daemon sees the user. `agentbox-bus` relays the session bus (`DBUS_SESSION_BUS_ADDRESS` in the box), which is what makes the GNOME keyring — and every tool that keeps a login in it: hawk (`!hawk-token`), pup, gws — work unchanged inside, with no per-tool passthrough. The same bus reaches the host's systemd user manager, so `systemctl --user start`/`stop`/`restart`/`status` in a box act on the host's units (`forward-serve`, `secretsd`, …): a restart from a box restarts the host's service. The unit-file verbs (`enable`, `disable`, `link`, `mask`, `is-enabled`) do not: they read and write `~/.config/systemd/user`, which in a box is the overlay, so they change nothing on the host and report on the box's empty copy. Host processes stay out of reach too, because the pid and `/tmp` namespaces are the box's own. **secretsd is the one service that must not be relayed.** It pins the process that `REGISTER`s a session token (`SO_PEERPIDFD`) and serves only that process's descendants; through a forking relay every connection is a different socat child that exits with the connection, so the pinned root is dead by the first `GET` and every request is refused `FOREIGN_CALLER` — `secrets grants` still answers, because it is unscoped, which is how the breakage hid. The launcher bind-mounts the daemon's socket node (`/run/user/$UID/secretsd.sock`) into the box at the same path instead; systemd's `secretsd.socket` unit owns the node, so it survives daemon restarts. The box's `/run/user/$UID` is an ubuntu-owned per-box directory holding the relayed bus, the secretsd socket, an empty 0700 `secretsd/` token dir for the omp extension, and the host's `forward/` directory (the arming, browser-grant and pulse sockets). That one is mounted as a directory because a restarted `forward serve` rebinds its sockets, which a mount of the socket file would not show. It is also what lets a web app inside a box reach Sami's laptop browser: `forward port <ports>…` in the box (the `using-forward` skill).

**A shared cache is only as safe as its tool's garbage collector.** `.cache/ms-playwright` is mounted rw into every box (`mounts`) and is the host's too, and `playwright install` garbage-collects it by path visibility: `_validateInstallationCache` (playwright-core 1.63, `lib/coreBundle.js`) reads `<target>/browsers.json` for every `.links` entry, counts an entry whose target it cannot read as broken, and deletes every browser build only broken entries used. From one box, a checkout in another box's `/tmp` or overlay is unreadable, so an install there deletes the browser that box is using: on 2026-09-25 installs at 02:13Z and 04:04Z removed `chromium_headless_shell-1243` and then `-1234` in turn, and a live e2e mutation run failed every later mutant at browser launch, which reads exactly like mutants being killed (platform PO, from the #20064 reviewer's report). Every agent session now carries the collector's own opt-out, `PLAYWRIGHT_SKIP_BROWSER_GC=1`: boxes through `session_env` in `scripts/agentbox`, host shells through `.bashrc` (Sami, 2026-09-25). It is a container launch variable, so a box started before that change lacks it until it is replaced (`agentbox restart` keeps the container's environment); in such a box, or anywhere the variable is missing, install with it set or into a `PLAYWRIGHT_BROWSERS_PATH` you own. Old builds then accumulate in the shared cache until `disk-hygiene` removes them. The same shape as the worktree prune above: a tool tidying what it cannot see as in use.

AWS is the exception by design (the instance role is meant for agents): `~/.aws` is visible and the box reaches the EC2 metadata service through a TCP relay (`agentbox-imds`, bound to the box network's gateway, sources limited to that network); the entrypoint drops container traffic to it inside the box so a sandbox the box starts cannot hold the role. The Envoy HTTP API reaches the box the same way (`agentbox-envoy`, `ENVOY_URL` points at the gateway); NATS is reachable by name on the box network.

- **`Dockerfile`** — Ubuntu 24.04 with docker-ce (the box runs its own `dockerd`), Chrome (omp's browser tool), pip, postgresql-client, sqlite3, socat, wget, passwordless sudo for uid 1000, and the `/etc/agentbox-identity` marker. Other tools are not installed here: the host's mise store is mounted in, so `mise.toml` pins apply inside exactly as on the host.
- **`entrypoint.sh`** — runs as root: starts the inner dockerd (its image store is an anonymous volume that dies with the box), inserts the DOCKER-USER rule against the metadata forwarder, logs the inner docker into ghcr.io as the session user with the agent-tier `GHCR_PULL_TOKEN`, then `setpriv`s to `AGENTBOX_USER` for the session command.

Root inside the box is Sysbox fake-root (a user namespace on the host), so `sudo apt-get install`, the inner Docker daemon, and nested containers (`tl run` sandboxes) work without host privileges. `sudo apt` installs die with the box; mise/uv/bun/npm installs persist through the mounted stores; durable image changes go in the Dockerfile plus `agentbox rebuild`.

knives: claims are keyed by the omp session id, so a boxed `knives start` is released at box exit without `--force`. The registered forks still live at their pre-`~/src` paths (`~/inspect/*`, `~/toon-rust/default`, …), which a box does not mount; `knives start` from a box works once a fork's checkout is moved under `~/src` (knives places workspaces next to the checkout, so they land inside the mount).

Secrets work from a box on both tiers as of `forward` v3.2.3 (sjawhar/forward#40): the daemon runs in the private user namespace its mount protections imply, so a same-uid client in a box arrives at `SO_PEERCRED` as the overflow uid, and the daemon decides admission on the socket node being owner-only rather than on that uid. With the socket mounted directly, omp's `REGISTER` pins the box's omp process and the ancestry walk crosses the container boundary (box pids are host pids to the daemon). `agentbox doctor` runs it on the host and inside the throwaway box.

### How changes take effect

Everything version-relevant except the image is a host mount seen by every box at once — the omp binary (`~/.mise`, pinned in `mise.toml`), the plugin tree (`omp/plugins/node_modules`, `bun install` on the host), config, agents, extensions and skills (`~/.config/omp`, `omp/`) — so a host-side update is live for the next omp *process*, not the next box: `agentbox restart --all` after a pin bump or `bun install` moves every session to it in place, each at its own safe point. Running processes keep what they loaded until then, as on the host. The image tag is the content hash of `Dockerfile` + `entrypoint.sh` (`agentbox:<12 hex>`), so editing either yields a new tag: the next `agentbox new` builds it, and `agentbox rebuild` builds it now and lists running boxes still on an older tag — those need a new box (`--resume`). `agentbox doctor` health-checks the host side and a throwaway box (tools, absent identity dirs, App-only gh, secrets tiers, AWS, hawk-token, google-user-token, envoy, forward channel parity with the host, inner docker). `agentbox sh <box|session-id>` execs into a running session's box.

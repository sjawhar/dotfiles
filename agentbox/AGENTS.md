# agentbox

The opt-in **agent box**: the image (`Dockerfile`, `entrypoint.sh`) and the home allow-list (`mounts`) that `scripts/agentbox` runs a session with.

One disposable Sysbox container per **agent session**, working in checkouts made for it. `agentbox new [-e NAME[=VALUE]]… <repo>… -- omp [omp args…]` names one or more canonical checkouts under `~/src` (`AGENTBOX_SRC`), makes a git clone of each at `<boxes>/<box>/<repo>` (below), and runs `scripts/agentbox-run.ts` in the first as the container's main process (`docker run --rm`), with `shims/omp` as its child; any other command after `--` runs bare. **`<boxes>` is `/mnt/nvme/<user>/agentbox/boxes` on a machine with that disk and `~/boxes` on one without** (`BOXES` in `scripts/agentbox`, `AGENTBOX_BOXES` to override), because a clone per box per repo does not fit on the root disk of sami-rocqperf: 11 GiB free of 495 GiB on 2026-10-31 against an 18 GiB floor, with 94 GiB on `/mnt/nvme`. The clone templates move with them (`AGENTBOX_CLONE_TEMPLATES`, default `<boxes>/../clones`), since a box's clone hardlinks its objects out of its template and a hardlink does not cross a filesystem. The box lives exactly as long as the session. When omp exits — clean exit, pane kill, launcher killed — the launcher releases every knives claim the session holds (`knives finish`, as that session) and removes `<boxes>/<box>`, unless a clone in it holds uncommitted changes or commits no remote has: then the directory stays in place, and the pane names each such clone and what it holds. Nothing is saved for an agent; its work is its own to push or remove (Sami, AGENTC-1420, 2026-10-02: "Just tell the agents to migrate off of the JJ workspaces, and then they can handle it").

**Restart in place.** `agentbox restart <box|session-id>… | --all` relaunches a box's omp without touching the container: the runner hangs omp up (its ordinary graceful teardown) and spawns `omp --resume <id> .` again through the shim, so the new process runs the current `mise.toml` pin, plugin tree and config, while the container, its workspace, `/tmp` and anything else inside stay. The `.` is the resumed session's one prompt: without it the agent waits at the prompt until someone types, because nothing else tells it the restart is over. The launch's own messages are not replayed: like omp's own `/restart` (`restartArgv` in its `cli/flag-tables.ts`), the relaunch keeps every configuration flag with its value and drops the session flags, the `--` delimiter and every positional, each already in the resumed transcript (`scripts/agentbox-run.test.ts`). Before that, a box launched as `omp "Your session was restarted in a new agentbox…"` told its agent so again on every restart and then sent `.` as a second prompt (2026-10-02). By default the host only sends the session an Envoy notice — finish the current step, start nothing long, then run `agentbox restart` (the in-box form: no arguments, restarts this session) — so the agent picks the moment; omp's own settled-boundary shutdown is not involved, the agent's judgment is. `--now` hangs omp up at once, interrupting whatever it is doing (resume replays the persisted transcript; a tool call in flight is lost). The session to resume is the file omp holds open, or the newest session file of the box's working directory (an idle session holds no writer after a resume). Nothing persists a pending restart: an agent that never runs the command keeps running until `--now`, and a replacement omp that dies on startup ends the box instead of looping. The runner appends every restart request, omp exit (exit code, signal, how long it ran) and relaunch to `~/.cache/omp/agentbox/<box>.log`, on the host through the `.cache/omp` mount, so a box that a restart ended says why: a replacement that died on startup is a `relaunched` line followed by `exited after 0s … the box ends`. Only that last line also reaches the pane, since omp owns the screen while it runs. Boxes started before a runner change keep the old runner. omp's own `/restart` cannot do this — it re-execs the versioned mise install path and so never sees a new pin. What still needs a new box: a launcher-env change (`session_env`, mounts), an image change, the runner itself.

**Moving the sessions already running on the host.** `agentbox restart` is for a session already in a box; `agentbox move` is for one that is not (dispatch://INFRA-702). `agentbox move --plan [--json]` lists every live top-level omp on this machine with the box it would get: its tmux pane, its full session id (the transcript it holds open, else its own `--resume` argument — never a prefix, and never an id another process also claims), its working directory, the `agentbox new` spec, and the disk the boxes would take against the reserve a move keeps free (20 GiB on `/mnt/nvme`, 10 GiB on the root disk). It tells five things apart and moves only the first: a `host` session, a `no-pane` top-level omp (a headless `omp -p`, a scheduler step agent — the plan names its parent and unit and leaves it to a person), one already `boxed`, one in a grading `sandbox` (a `/work` directory, a bwrap ancestor, a container that is not a box), and a `subagent` of another omp, which is not a session. `agentbox move <session-id>… | --all` sends each session the Envoy notice to run `agentbox move --self` the next time it has no jobs running, without stopping, delaying or shortening any work for it; `--now` relaunches the pane from outside instead, and `--dry-run` prints what either would do. **A move never names a repo**, and that is the whole design: `agentbox new <repo>` gives a box a clone of its own, which for a live session means a tree that is not the one it has — no uncommitted changes, no index, and none of the work of the other 16 sessions sharing that checkout. `$SRC` is bind-mounted into every box already, so the spec is `--dir <cwd>` (plus the owning checkout when the session sits in a worktree outside `$SRC`), the session resumes in the same tree, and the only new disk is the box's own sparse ext4 image: 261 MiB at the 32 GiB default, measured, against 0.02–14 GiB for a clone. `--self` refuses, naming the reason, when the session is already in a box, when a SUBAGENT runs it (its bash tool reaches its parent's omp, so the move would hang up the session that started it: omp's `PI_SESSION_FILE` is `<name>.jsonl` for a subagent and `_<id>.jsonl` for a session), when `OMP_SESSION_ID` is not the session the process census read, when the id cannot be read in full, and when the box would leave the disk under that reserve — `--force-floor` is the person's override, and it prints what it overrides. The reserve is not `scripts/disk-fill-watch`'s 84 GB alert floor: that floor tells a person early, and used as a refusal it stopped all 70 ready sessions at 17:32Z on 2026-11-01 for boxes that claim 0.3 GiB each. The relaunch itself is a detached process (`move --relaunch`, logging to `~/.cache/omp/agentbox/move-<id>.log`): `move --self` runs in the session's own bash tool and dies with the omp it hangs up. It sends SIGHUP — omp's ordinary graceful teardown, the same signal `agentbox restart` uses — waits for the process to go, and respawns the pane into `agentbox new <spec> -- omp --resume <id> .` under an interactive bash that stays when the box ends. Measured on two throwaway sessions on 2026-11-01: hang-up to exit 2 s, pane respawned 3 s later, both resumed under their own ids in their own boxes, the worktree box seeing the host's uncommitted file and writing to it.

**A move's paths are inferred from the session's own processes, not from its working directory.** The first window notified 32 sessions on 2026-11-01 and several answered that the box they were offered would not hold the paths they work in. That is the dangerous failure and not a cosmetic one: a path a box is not given is not absent inside it, it is silently writable into the box's own filesystem and lost when the box ends. The cwd is a poor witness. A session whose cwd is `~/src/oss-verifier` works in `/mnt/nvme/sami/oss-verifier/...`, `/mnt/nvme/sami/tmp/...` and `~/.worktrees/...`; session `01a16640`'s cwd was `~/Code/legion`, a real checkout of the same repository, while the trees it had open were `~/src/legion/.worktrees/infra-140-s5` and `/mnt/nvme/sami/worktrees/legion/stopped-tree`, so the cwd alone would have given it a box whose `git status` answers about **another** checkout. So `move_dirs_why` (`scripts/agentbox`) reads the session's own process tree — the omp and every live descendant — and takes the cwd of each, and the directory of every file one of them holds **open for writing** (`O_WRONLY` or `O_RDWR` in `/proc/<pid>/fdinfo/<fd>`; a file only read names nothing, or every library and config a tool opens would mount the host). Each path is then resolved to the root of its git working tree where it is in one — the exact boundary, and what makes the worktree of an open file arrive whole — and otherwise bounded at the first directory below the deepest root that holds many sessions' trees (`~/Code`, `~/Code/personal`, `~/.worktrees`, `/mnt/nvme/<user>` and its `tmp`, `session-tmp`, `worktrees` and `scratch`), which are never mounted at the root. A path the box already has is left out, because naming it changes nothing: `$SRC` and the targets of its symlinks, the dotfiles, and every entry of the home allow-list — **a worktree under `~/src/<repo>/.worktrees/...` is in that class, so it IS visible in a box with no `--dir` at all** (measured 2026-11-01 inside `agentbox-6e431c00c973`: `/home/sami/src/legion/.worktrees` listed its trees, with `findmnt` naming the `/home/sami/src` bind). Nested paths collapse to the shallowest, except the working directory, which stays first because `agentbox new` works in its first `--dir`. `move --plan` prints every path with the reason it was chosen, and so does the Envoy notice, so a session sees its box before it moves; `agentbox move --self --dir PATH --dir PATH` adds what the inference missed, each checked exactly as `agentbox new --dir` checks it and each placed after the inferred paths. Inference is best-effort by construction — a path no process of the session had open when the plan ran is not in it — which is why the list is printed and `--dir` exists.

**Three things a live-process scan cannot see, and what each needs.** The inference above reads the session's live processes. That is a snapshot, and three shapes measured on 2026-11-01 defeat it, each ending with a path silently writable inside the box and lost with it. (1) A SUPERVISOR writes almost nothing itself: its subagents do, and they have exited, so a dead worker leaves no cwd and holds no open file — session `01a16220`'s live scan gave two directories and missed four it works in. (2) TRANSIENT use: session `01a16640` works in `/mnt/nvme/sami/worktrees/legion/stopped-tree` only through one-shot `cd <path> && git …` calls, so at no instant is a process there. (3) The two commands DISAGREE: at 18:48:20Z the plan gave `01a1798a` `/mnt/nvme/sami/tmp/verified-linux` because one bash held a file open there, and `move --self` minutes later gave the cwd alone, so the box lost the directory holding that session's own state. So the spec has five sources, not one: the working directory and its git tree; the live processes; **the session's own record of today** — its transcript's tool calls, the `cwd` of its bash calls, the `path` of its read/write/grep/glob calls, the `[path#tag]` headers of its edit calls, and every absolute path inside a bash `command` or an eval `code`, which is what catches `cd <path> &&` and `git -C <path>`; **what the last `move --plan` inferred for that session**, kept in one small file per session under `<boxes>/../plan/<id>` and unioned in by `--self`, so a row the plan printed is a promise it keeps; and each `--dir` the caller named. Every one is bounded the same way and must exist. `--plan` and the notice print each path with which source it came from, and a session with **no live child process** is told so in its plan row and in its notice, so a lane reading two directories knows the live scan had nothing to work from.

**A tree is not its objects.** `~/src/machcsl-riscv/.git/objects` on this host is a SYMLINK to `/mnt/nvme/sami/git-objects/machcsl-riscv`, and so are the task repository's, `link-eval-accept29`'s, `machcsl-riscv-experimental`'s and `ossvp-ulimit`'s. A box given the tree and not the store answers `not a git repository` for every command in it, and `knives gh` fails with it (session `01a1798a-995f`, box `agentbox-676432b23e44`). `$SRC` is in every box, so the tree is never in the spec and the store must be: for every tree a session touches, the spec follows its `.git` (file or directory), its `commondir`, its `objects` through any symlink, and every line of `objects/info/alternates`, and adds each result the box would not have. **`agentbox new --dir` follows the same four things, through the same reader** (`move_git_storage`, called by `add_box_dir_storage` for the git tree each `--dir` is in), and prints the store it adds. It did not until 2026-11-01: `move` inferred its own paths and so had to follow them, while a `--dir` was treated as one directory the caller had already thought about, so `agentbox new --dir ~/src/machcsl-riscv` built a box whose every git command answered `fatal: not a git repository` — measured in box `agentbox-a0875d5a6f7c`, with the objects symlink dangling inside it, and the workaround in use was a second `--dir /mnt/nvme/sami/git-objects/<name>` by hand. After the fix, in box `agentbox-510cd93aca54`, `git rev-parse` and `git count-objects -v` in that tree answered exactly what the host answers (`9ebc0039ad45`, 13,609,735 in-pack objects).

**A config file that names a path is followed too.** `shims/gh` refuses `gh pr edit|create|comment` unless it finds the public-text leak check, whose location is `~/.config/public-leak-check/path`, holding `/mnt/nvme/sami/frac-verify/shared/leak-check/public-leak-check.sh`. The pointer is now in the allow-list (`ro .config/public-leak-check`) and the script is on `/mnt/nvme`, outside every box, so a box had the pointer and nothing to follow it to and every public text write from it was refused. `move_config_dirs` reads each pointer file for one absolute path and puts the directory holding it in the spec; adding another pointer is one line there. `agentbox new` binds the same directories, so a box made without `move` reaches the script too: on 2026-11-01 `agentbox-d7c1bb68a0a4`, made by `new` after the move fix, had the pointer and not the script. `agentbox doctor`'s box checks now fail when either half is missing, because a box that cannot write to GitHub is a box a lead cannot work in. Measured after the fix in `agentbox-bf4ffcac537c` (made by `move`): the pointer and the 23 KB script were both present and `gh pr comment` posted and was then deleted; and in `agentbox-7bdb51c4e932` (made by `new --dir` only): `test -x` on the script passed.

**Archived transcripts reach the box too.** On this host, transcripts that have gone cold move to `/mnt/durable/<user>/omp-sessions-moved` and leave a symlink in `~/.omp/agent/sessions`. Every box has `~/.omp/agent/sessions`, but no box had `/mnt/durable`, so inside a box the symlink pointed at nothing and a resumed omp exited with `Session "<id>" not found`. On 2026-11-01 lane box h-dgn-t1 died this way three times. `agentbox new` now binds that directory read-write wherever it exists, because omp appends to its transcript through the symlink. The archiver also skips any session a running process names (`--resume <id>` or `OMP_SESSION_ID`), and it counts a file's ctime as well as its mtime when it judges age. Measured in `agentbox-2896707b4359`: an archived transcript's symlink was readable from inside the box.

**The disk gate's state reaches the box too.** `scripts/disk-gate` serialises every lane's large writes through one lock and one count in `/mnt/nvme/<user>/scratch/disk-gate`, and no box had that directory: in a box `disk-gate reserve` hit a root-owned stub, took no lock, counted nothing and printed an empty reserved figure (three lane boxes within six minutes of the gate's announcement, 2026-11-02). `agentbox new` now makes the directory if it is absent and binds it read-write. It binds disk-gate's DEFAULT path and never reads the caller's `DISK_GATE_STATE`: the box does not get that variable (`session_env` builds its environment from scratch), so the disk-gate inside always uses the default. The first version of this bind honoured the caller's value, and its test launches came from a shell that still exported `DISK_GATE_STATE=/tmp/dg-test-47661` after testing the gate, so each test box got that directory and not the real one. Measured in `agentbox-3628240f49c2`, launched with that variable still exported: `disk-gate reserve 1 boxprobe` answered `NO … 0 GiB is reserved by other lanes` from the host's count, and a reservation on a new state file appeared on the host while the box held it.

**A box is not a one-way door.** Every box defect found so far is fixed by moving again with one more `--dir`, and a session INSIDE a box could do neither: `--dir <host path>` was checked in the box's own view, where an unmounted host path does not exist (`--dir '<path>' is not an existing directory`), and `--self` then refused outright. In a box the paths are no longer checked there — the `agentbox new` the host pane runs checks every one of them with the same `add_box_dir` — and `--self` relaunches the pane into a new box holding this box's own paths (`AGENTBOX_DIRS`, set by `session_env`) plus the new ones, through the host tmux the box already has.

**knives claims are shared between a box and the host, and that is safe.** knives records a claim in `~/.config/knives/state.json` under `claims`, keyed by the omp session id (`KNIVES_OWNER`, else `CLAUDE_CODE_SESSION_ID`, else `OMP_SESSION_ID`), and takes an advisory `flock` on `state.lock` beside it. `agentbox/mounts` has `rw .config/knives` and `rw .cache/knives`, bound at their own paths, and `session_env` sets no `XDG_CONFIG_HOME`, so a box and the host open the SAME inode and contend on the SAME lock: a second `start` of a claimed branch is refused `RefuseHeld`, whichever side asks. So a box and a host session cannot both hold one branch under different ids. The one way both "hold" it is the same session id live on both sides at once, which `move --self` prevents by hanging the host omp up and waiting for it before the pane respawns. A box's exit releases only its own session's claims (`close_box` → `finish_knives_claims`, `knives finish` as that id, which knives refuses for a claim owned by another id). Two gaps to know: a `--dir`-only box whose omp never held its session file open leaves the launcher with no id, and that box's claims stay held with no live process (`knives status` after exit shows them); and an inherited `KNIVES_OWNER` or `CLAUDE_CODE_SESSION_ID` in the launcher's environment outranks `OMP_SESSION_ID` and makes the release refuse, logged as `knives finish … failed; left as is`. Before moving, a lane needs only to keep its session id (which `move --self` does) and to keep its fork's checkout under `~/src`.

Every omp flag after `--` passes straight through. `--resume <id>` gets a fresh box and clones like any other launch (box names are never reused); omp relocates the resumed session's file into the new working directory's session dir, which is what lets a host session, or one from a closed box, continue in a box.

**Every checkout is a git clone of the box's own** (AGENTC-1420, Sami, 2026-10-02: "Let's just switch to Git everywhere"), copied from a template the host keeps per repo under `CLONE_TEMPLATES/<repo>` — `/mnt/nvme/<user>/agentbox/clones` beside the box trees on a machine with that disk, else `~/.cache/agentbox-clones` — outside every box mount. The template is a clone of the canonical checkout's `origin` with `--filter=blob:none`, made on the first launch that needs it and refreshed by a fetch on every launch after. Its `.git` is copied into the box with the objects hard-linked (what a local `git clone` does; git never changes an object file in place), and a checkout from those local objects writes the box's working tree and index — so the templates and the box trees must stay on one filesystem, which is why they move together. So each box's clone is still its own repository, with its own refs, config and index, and stays whole if the template is rebuilt or removed. A box's repos are cloned in parallel. Measured on 2026-10-02 at load 200: a fresh clone of agent-c took 64-78 s, almost all of it the checkout fetching the kept files' contents; a copy took 1.4 s and its local checkout 17.6 s. Inside the box, git fetches a file's contents from GitHub, through the box's App routing, the first time something reads it, so `git log -p`, `blame` or a diff against an old commit fetch what they read. On agent-c's shared jj store (298 workspaces, 135,748 `refs/jj/keep` refs) every jj command took about 11 s, against 0.1 s for git. A repo in `CLONE_SPARSE` (`scripts/agentbox`) also gets a sparse checkout. agent-c leaves out `tasks/` (3.8 GB of its 4.2 GB tree), keeping every `tasks/*/basic_info.json` because `tl validate`'s deployment-catalog check reads all of them, and an agent working on a task adds it with `git sparse-checkout add /tasks/<id>/` (a 94-file task took 1.4 s). Automatic maintenance is off in each clone, since otherwise every on-demand fetch starts a background repack. A template git cannot refresh fails the launch, naming its directory: remove it and the next launch rebuilds it. The checkouts are plain git: jj fails on a clone like this (`Object … of type file not found`).

**A session whose work is not a checkout names its directory instead** — `agentbox new --dir PATH`… (dispatch://INFRA-702). Of the 82 live sessions on sami-rocqperf on 2026-11-01, **50 could not be boxed at all**: 32 worked in a directory that is not a repository and 18 named `oss-verify`, whose canonical checkout `~/src/oss-verify` does not exist. Reading three sessions of each group showed what they are: `~/src/oss-verifier` (20 sessions) is a lane's scratch root whose work is `/mnt/nvme/sami/oss-verifier/...` and the `~/src/oss-verify-*` worktrees, not a repository at all; `~/Code/personal/theorem` (11) is a lead's coordination root over `dispatch`, `envoy` and the lane trees under `/mnt/nvme/sami/frac-verify`; `~/src/bet-grade` (9) is an evidence tree of `gates/`, `lanes/` and `repos/` whose work is `/mnt/nvme/sami/review-wt/...` and `gh`; `~/src` (10) is sessions working in worktrees elsewhere. None of them wants a clone. `--dir` (repeatable) gives the box one **existing host directory, bind-mounted read-write at its own path**, and the box works in the first one when no repo is named; `<repo>` and `--dir` may be combined, and a repo still wins the working directory. Three things follow. It is the HOST's directory — shared with the host and every other box that names it, not cloned, and left exactly as it was when the box ends. Writes in it are **outside the box's disk image and so outside its disk limit**; the cpu, memory and pids limits apply as always, and the box's own `$HOME`, `/tmp` and clones stay inside the disk limit. And `box_session_id` deliberately has **no fallback** for such a box: omp keys its session directory by the cwd, which every session in that path shares, so a guess returns someone else's id — measured 2026-11-01, where a glob by working directory answered with a live host session's id for both test boxes, an id `agentbox restart` would notify and `close_box` would use to release that session's knives claims. Refused: a path that is not a directory, `/`, `$HOME`, anything under the box tree, and **a path every box keeps its own copy of** — `/tmp`, `~/.omp/run`, `~/.config/jj/repos` and `/run/user/<uid>` (`box_dir_private_why`), each refused on one line naming the path and why the host's copy cannot be given to a box, because docker refuses two mounts at one destination and each of those four ended the launch with `docker: Error response from daemon: Duplicate mount point: <path>` after the box directory and its disk image had been made, naming neither the flag nor a fix (measured 2026-11-01). A `--dir` the box **already has at that same path** — `$SRC` itself, the target of a symlink in it, the dotfiles, or an entry of `agentbox/mounts` — was the same dead launch (`--dir ~/.config/jj`, a read-only entry); it is now kept as the box's working directory, not bound a second time, and the launch says which mount it comes from and whether that mount is read-write or read-only. So every `--dir` is now bound, refused by name, or reported as already there.

The caller's environment does not reach the box: `session_env` builds the box's variables from scratch. `-e NAME=VALUE` (repeatable, before `--`) adds one, and a bare `-e NAME` passes the caller's value, as with `docker run -e`: `agentbox new -e OMP_VIEWPORT=0 agent-c core-ops -- omp --resume <id>` starts the session without the transcript viewport. It is set on the container, so it survives `agentbox restart`, and it is applied after the launcher's own variables, so it overrides them. `tmux-omp-ids` and `tmux-resurrect-omp` rebuild a resume command from everything the launcher was given before `--`, so repos and variables carry over to the relaunch.

**Each box has its own `~/.omp/run`; the rest of `~/.omp` is the host's.** omp keeps its daemon brokers there (each scope's `broker.sock`, token, presence records and lease), and that state holds in one PID and network namespace only: the lease is an abstract socket, which Linux scopes per network namespace, and a broker that starts deletes every sibling scope older than five minutes whose pids it cannot see. A shared `~/.omp/run` let one box's broker delete the live scopes of every other box and of the host, leaving their brokers listening on a `broker.sock` gone from disk and every tool call through them failing with `connect ENOENT` or `Daemon broker authentication failed`. So `mount_args` binds `<boxes>/<box>/omp-run` at `~/.omp/run`, removed with the box directory at close, and binds the host's `~/.omp/run/collab-hosts` back on top, so `omp collab` discovery still spans the host and every box. A box starts its own brokers and machine-global daemons, and the host's `omp ps` does not list them. A running box gets this only when it is replaced, because `agentbox restart` keeps the container and its mounts: inside a box, `findmnt -T ~/.omp/run` names the box tree it comes from (`/dev/root[…/boxes/<box>/omp-run]`) when the box has its own, and the `~/.omp` mount when it still shares the host's. On a shared one, killing a broker whose `broker.sock` is gone is no reliable fix and can end the processes it supervises; resume the session in a new box (`agentbox new <repo>… -- omp --resume <id>`) instead.

**The box sees an allow-list of the home directory and nothing else** — `agentbox/mounts`, one `<rw|ro> <path>` per line, read by `scripts/agentbox` at launch and checked entry by entry by `agentbox doctor` from inside a box. Beyond the list: the canonical checkouts (`~/src`, plus the target of any symlink in it — `~/src/dotfiles → ~/.dotfiles`), the box's own directory, and the dotfiles. The list holds omp state, the mise tool store and language caches, `~/.aws`, `~/.kube`, `~/.pulumi`, the Google Cloud SDK and its config dir, the tool configs a session relies on, and read-only configuration including the jj-signing pair. A CLI's own login state belongs there when boxes need that CLI — `~/.fleet` (fleetctl), `~/.sentry` (sentry), `~/.config/depot`, `~/.config/pup` (pup's site registry; its tokens are in the keyring, which the relayed session bus already serves) — so no API key is handed to a box for a tool the host is logged into. An identity that can act as the user on GitHub never is: no `~/.config/gh`, ssh keys, gnupg or docker login, so an agent inside pushes only as the GitHub App its repo routes to. Adding a tool is one line in the file; running boxes see it at their next relaunch.

**The Google Compute Engine ssh key is in the list; no GitHub identity ever is** (dispatch://INFRA-702). `ro .ssh/google_compute_engine` and its `.pub` are what `gcloud compute ssh` uses, and a lane that reaches a GCE VM needs them. They fit the rule for a tool login because they are not one: the key is a GCE credential, whose public half Google's guest agent puts in the project or instance metadata and whose only verifier is sshd on a Compute Engine VM, and the box already holds the gcloud identity that may read and write that metadata (`rw .config/gcloud`). Without them gcloud makes a key per box and writes a new public key into the project metadata at every launch. GitHub still sees nothing: `~/.ssh` as a whole is not mounted, there is no `~/.config/gh`, and a push from a box is the repository's GitHub App over https. Measured 2026-11-01 inside `agentbox-6e431c00c973`: `gcloud compute ssh --dry-run --zone us-central1-a autoformalization-parallel` printed `ssh … -i /home/sami/.ssh/google_compute_engine …`, and in the same box `git credential fill` for a `theorem-labs` repository answered a `ghs_` installation token of an App with 210 repositories, whose `GET /user` is `Resource not accessible by integration` — an App, not the user.

**Google Cloud reaches a box through two entries** (dispatch://INFRA-702): `ro .gcloud`, the SDK install, and `rw .config/gcloud`, its config dir — the split gcloud itself uses, since it writes nothing under the install. Without them a box had neither: `gcloud auth list` answered `gcloud shim: real gcloud binary not found`, `~/.local/bin/gke-gcloud-auth-plugin` was a symlink into a tree that was not mounted, and `kubectl … auth can-i create jobs` on the GKE build pool failed at `executable gke-gcloud-auth-plugin not found`, so the build pool was unreachable from every box. The identity the config dir carries is the machine's, not a user login: its active configuration is `box`, whose account is the keyless `external_account` of `dev-<name>@theorem-agent-infra`, bound to this VM's Entra identity and exchanged for a token through the metadata relay the box already has. Writing it is deliberate too — agent-c's `deploy.py` requires `~/.config/gcloud/agent-devbox-wif-adc.json` for any devN up/destroy, and a box now writes the host's copy instead of an overlay that dies with it.

**`agentbox doctor` is a HOST command, and from inside a box it never reaches the box checks.** It runs the host-side suite first — sysbox runtime registration, the session bus, the IMDS forwarder's bind — every one of which fails by construction in a box's view of the host, and it aborts there, before the block it execs *into* a box (`scripts/agentbox`, the `cmd_doctor` heredoc). Four sessions on 2026-09-26 read those three FAILs as their own box's health while the docker checks they actually needed never ran. From inside a box, run that block's lines directly — but know what each one can tell you. `jq -e '.credHelpers["https://index.docker.io/v1/"] == "secretsd"' ~/.docker/config.json` is the one that discriminates: it is false on an unmerged box and true after the entrypoint's merge. `printf %s https://index.docker.io/v1/ | docker-credential-secretsd get | jq -e '.Secret | length > 0'` passes on a BROKEN box too, because it asks secretsd directly and says nothing about what docker uses — it proves the helper works, which is why a repair is safe, not that a repair happened. Neither proves docker *routes* there; that needs a real pull of an image the box lacks with the anonymous rate-limit counter read before and after (unchanged ⇒ the helper was used). A box's `.auths` should hold only `ghcr.io`: a Docker Hub or ECR login sitting under `auths` instead of `credHelpers` is the shape that shadows a working helper, and doctor's own auths assertion catches it. Print keys and exit codes, never the file: `auths` values are base64 `user:token`, and two sessions leaked the same live org PAT into their transcripts by printing it.

**A credential check that fails in a box fails on the host just as often, so doctor asks both.** `secrets GHCR_PULL_TOKEN`, the Docker Hub credential helper that reads `DOCKER_HUB_OAT`, `aws sts get-caller-identity`, `hawk-token`, `google-user-token`, `gcloud auth list` and `kubectl --context gke_theorem-agent-infra_us-west1_dispatch -n builds auth can-i create jobs` answer for what the MACHINE is logged into: a box can only be as logged in as the host under it. doctor runs one definition of each (`PROBE_FUNCS` in `scripts/agentbox`) on both sides and compares (`report_probes`). A box that cannot do what the host can is a `FAIL` naming both answers. Where neither can, the line is a `note` that says it is host state, repeats what the host said, and gives the command that shows it — so nobody hunts a box for a credential the machine never had. On sami-rocqperf, 2026-10-31, that is five of them: no `GHCR_PULL_TOKEN` and no `DOCKER_HUB_OAT` in any agent-tier file (`~/.dotfiles/secrets.local.env` does not exist here, and the broker answers `UNKNOWN_SECRET`), no EC2 instance role (the machine is an Azure VM; 169.254.169.254 answers 404 to every EC2 path, so `aws` and the `google-user-token` that reads AWS Secrets Manager both fail), and no DNS for `api.hawk.internal.trajectorylabs.com`. The last two probes are the pair INFRA-702 added, and both pass on this host, so a box that cannot answer them has lost its Google Cloud mounts and doctor says so. `agentbox doctor --here`, inside a box, has no host to compare with: it prints each of those as a note and counts none of them.

**A home path outside the allow-list is writable, and that is the trap.** `~` inside a box is the box's own directory (`<boxes>/<box>/home`, on the box filesystem since INFRA-702; it was the container overlay before), with the allow-listed host paths bind-mounted on top (`findmnt -T ~/.omp` → the host device, `findmnt -T ~` → the box's loop device). So `mkdir -p ~/.newstate && echo x > ~/.newstate/f` exits 0 and the host never sees the file; it is gone when the box is torn down, and nothing errors at any point. Only a path whose parent does not exist in the box fails (`cat >> ~/.absent/notes.md` → `No such file or directory`), which is the lucky case. Before choosing a home-directory location for anything that must outlive the box or be read from outside it — a ledger, a run directory, a cache another session reads — check it is under a `mounts` entry (`findmnt -T <path>` names the host's `/dev/root` or `/dev/md127`, not the box's `/dev/loopN`), and if it is not, add the entry rather than the path. Measured 2026-09-21 in `agentbox-25988be444cf`: the librarian's ledger at `~/.librarian/notes.md` had been unreachable since the 2026-09-20 relocation; the session noticed the missing directory at 01:26Z that night and went 43 hours without a ledger before relocating it under `~/.omp`.

**The box's `$HOME` is the host user's home PATH, and the entrypoint gives it to the session user.** `agentbox` sets `HOME=$HOME`, so a box on a machine whose user is `sami` works in `/home/sami` while the image's own skeleton is `/home/ubuntu`: docker creates `/home/sami` and every parent an allow-listed mount needs as a **root-owned** directory of the box's overlay, and the session, running as `ubuntu`, could then write only the mounts themselves. Measured on sami-rocqperf on 2026-10-31, the first host here whose user is not `ubuntu`: no `~/.docker` (so the entrypoint's ghcr login and its secretsd credHelpers both failed, and every Docker Hub pull stayed anonymous), `mkdir: cannot create directory '/home/sami/.config/gh-agent': Permission denied` on every `gh` call, and `failed create_dir_all: ~/.local/state/mise/tracked-configs` in front of the output of every mise-shimmed tool — enough to make `agent-secrets whoami` unparseable. So `entrypoint.sh` chowns every directory of the overlay under `$HOME` to `AGENTBOX_USER` before anything else runs. It skips the mounts by device (`find -xdev` plus an `st_dev` check): a bind of a host path has a device of its own, and chowning one would change the host's directory, which Sysbox already maps onto the session user anyway. On a host whose user is `ubuntu` the chown changes nothing, which is why this was invisible until now.

**A box's checkouts are no longer worktrees of the shared checkouts.** Until 2026-10-02 each was a jj workspace, registered under `~/src/<repo>/.git/worktrees/` with a path only its own box could see, so a `git worktree prune` run from any other box deleted live registrations (14 boxes at once on 2026-09-21), and the launcher locked each one. A box started before that change keeps its locked worktree until it closes, so never run `git worktree prune` (or anything that does — `git gc` with an expiry, Legion's workspace provisioning) on `~/src/<repo>` from inside a box.

**Host services reach the box two ways.** Sysbox maps the box onto a subordinate uid range (the host sees a box peer as uid 232072, not 1000), and dbus-daemon refuses a peer whose uid is not the user's, so the launcher runs socat relays as transient user units (`ensure_forwarders`): each accepts the box on a 0600 socket and connects onward as the user, so the daemon sees the user. `agentbox-bus` relays the session bus (`DBUS_SESSION_BUS_ADDRESS` in the box), which is what makes the GNOME keyring — and every tool that keeps a login in it: hawk (`!hawk-token`), pup, gws — work unchanged inside, with no per-tool passthrough. The same bus reaches the host's systemd user manager, so `systemctl --user start`/`stop`/`restart`/`status` in a box act on the host's units (`forward-serve`, `secretsd`, …): a restart from a box restarts the host's service. The unit-file verbs (`enable`, `disable`, `link`, `mask`, `is-enabled`) do not: they read and write `~/.config/systemd/user`, which in a box is the overlay, so they change nothing on the host and report on the box's empty copy. Host processes stay out of reach too, because the pid and `/tmp` namespaces are the box's own. **secretsd is the one service that must not be relayed.** It pins the process that `REGISTER`s a session token (`SO_PEERPIDFD`) and serves only that process's descendants; through a forking relay every connection is a different socat child that exits with the connection, so the pinned root is dead by the first `GET` and every request is refused `FOREIGN_CALLER` — `secrets grants` still answers, because it is unscoped, which is how the breakage hid. The launcher bind-mounts the daemon's socket node (`/run/user/$UID/secretsd.sock`) into the box at the same path instead; systemd's `secretsd.socket` unit owns the node, so it survives daemon restarts. The box's `/run/user/$UID` is an ubuntu-owned per-box directory holding the relayed bus, the secretsd socket, an empty 0700 `secretsd/` token dir for the omp extension, and the host's `forward/` directory (the arming, browser-grant and pulse sockets). That one is mounted as a directory because a restarted `forward serve` rebinds its sockets, which a mount of the socket file would not show. It is also what lets a web app inside a box reach Sami's laptop browser: `forward port <ports>…` in the box (the `using-forward` skill).

**The host's tmux server is relayed into every box, so a lead can drive other sessions' panes** (dispatch://INFRA-702). A lead starts and steers panes — `tmux new-window`, `send-keys`, `capture-pane`, `list-panes` — and without the host's tmux server a boxed lead can do none of it, which would leave the coordination sessions, the heaviest on this host, outside every limit this work exists to apply. A bind of the socket is not enough: measured 2026-11-01 in a throwaway box given `/home/sami/.tmux/sockets/tmux-1000`, `connect(2)` succeeded, because Sysbox id-maps the bind and the node arrives as the box user's, and every tmux command answered `access not allowed`, exit 1 — the tmux server's own check of the client's `SO_PEERCRED` uid, which under Sysbox is a subordinate uid and not the user's. So it gets the same treatment as the session bus: `agentbox-tmux` (`ensure_tmux_forwarder`) relays it and connects onward as the user. tmux's non-attaching commands survive a relay — measured on the host, `display-message -p '#{version}'` through a `socat UNIX-LISTEN`/`UNIX-CONNECT` pair answered `3.8` — and attaching from a box is meaningless anyway, since the box has none of the host's terminals. The host socket is the one the launching session itself uses (`$TMUX`'s first field, so a machine whose `TMUX_TMPDIR` is not `/tmp` is followed rather than guessed; `AGENTBOX_TMUX_SOCK` overrides, and a host with no tmux gets no relay). Inside, it is `TMUX_TMPDIR=/run/user/<uid>/tmux` holding `tmux-1000/default`, which is where a bare `tmux` looks, so no command needs `-S`; `TMUX` itself is deliberately unset, because a box is not inside a pane. **State plainly what this gives a box:** control of the host's tmux server — read any pane (`capture-pane`), type into any pane (`send-keys`, which in a pane sitting at a shell is a command as the host user, outside the box's cgroup and disk limit), respawn or kill any pane, and `kill-server`, which would end every agent pane on the machine. It is given because the relayed session bus already reaches the host's systemd user manager, so a box can already restart the host's services (the paragraph above), and because the alternative is that leads stay on the host.

**Each box can have its own secrets-broker identity (AGENTC-393), and a box without one is normal.** When the host's agent-secrets helper holds a live launcher credential (`agent-secrets-login`, `agent-secrets/AGENTS.md`), `agentbox new` puts `enrollment.pending` in the box's key dir (`/run/user/<uid>/agent-secrets` inside, `$RUN_BASE/<box>/run-user/agent-secrets` on the host; `AGENT_SECRETS_KEY_DIR`), keeps it fresh while it waits, runs `agent-secrets keygen` inside the box once it is up, enrolls the key from the host (with omp's session id once it appears), and starts `agent-secrets renew` in the box for its lease, in a loop that restarts it 10 s after it exits (log: `renew.log` in the key dir). Success leaves `key.pem` and `enrollment` and no marker. Any failure leaves `enrollment.error`, and removes the key and the marker. The host keeps its own files in `$RUN_BASE/<box>`, which no box mounts: each attempt's error, and the enrollment id `close_box` revokes, never the box-writable copy. A box with no key (no credential when it started, or a failed enrollment) has no broker identity, and its agents use secretsd. `agentbox doctor --here` reports that as a note, and reports the identity checks for a box that has one.

**A shared cache is only as safe as its tool's garbage collector.** `.cache/ms-playwright` is mounted rw into every box (`mounts`) and is the host's too, and `playwright install` garbage-collects it by path visibility: `_validateInstallationCache` (playwright-core 1.63, `lib/coreBundle.js`) reads `<target>/browsers.json` for every `.links` entry, counts an entry whose target it cannot read as broken, and deletes every browser build only broken entries used. From one box, a checkout in another box's `/tmp` or overlay is unreadable, so an install there deletes the browser that box is using: on 2026-09-25 installs at 02:13Z and 04:04Z removed `chromium_headless_shell-1243` and then `-1234` in turn, and a live e2e mutation run failed every later mutant at browser launch, which reads exactly like mutants being killed (platform PO, from the #20064 reviewer's report). Every agent session now carries the collector's own opt-out, `PLAYWRIGHT_SKIP_BROWSER_GC=1`: boxes through `session_env` in `scripts/agentbox`, host shells through `.bashrc` (Sami, 2026-09-25). It is a container launch variable, so a box started before that change lacks it until it is replaced (`agentbox restart` keeps the container's environment); in such a box, or anywhere the variable is missing, install with it set or into a `PLAYWRIGHT_BROWSERS_PATH` you own. Old builds then accumulate in the shared cache until `disk-hygiene` removes them. The same shape as the worktree prune above: a tool tidying what it cannot see as in use.

AWS is the exception by design (the instance role is meant for agents): `~/.aws` is visible and the box reaches the EC2 metadata service through a TCP relay (`agentbox-imds`, bound to the box network's gateway, sources limited to that network); the entrypoint drops container traffic to it inside the box so a sandbox the box starts cannot hold the role. The Envoy HTTP API reaches the box the same way (`agentbox-envoy`), and the entrypoint relays the box's own `127.0.0.1:9020` (`AGENTBOX_ENVOY_PORT`) to that forwarder (`AGENTBOX_ENVOY_FORWARDER`), so the listener URL in the host's `envoy.json` works unchanged inside, and a box workload cannot listen on that port itself. NATS (`nats://envoy-nats:4222`) resolves by its tailnet name through the box's DNS. The launcher sets no Envoy or Dispatch variable: a box session reads `envoy.json` as a host session does (`envoy/AGENTS.md`). Without a profile of its own that is `~/.config/legion/envoy.json`, which `mounts` lists read-only; under a named omp profile it is that profile's `~/.omp/profiles/<name>/agent/envoy.json` in the mounted `~/.omp`, where a link to the neutral file resolves because that file is mounted at its own path; a profile with no file gets no Dispatch or Envoy. The NATS credential is the file's `natsSeed` command: `!$HOME/.dotfiles/scripts/envoy-nats-seed --value` in a box reads the host's per-boot cache, which the launcher binds into the box at the same path (`/run/user/$UID/envoy/`), so a host-side refresh (a rename in that directory) reaches running boxes and an in-box fetch lands in the host's cache. `agentbox doctor` checks all of it from inside the box: the file `envoy config-path` names, whether each section is enabled, the listener through `envoy ps` (relay and bearer), NATS by name, and the seed command. Like every mount and `session_env` variable, the relay's address is fixed at `docker run`, which `agentbox restart` keeps, so a change to any of them reaches a box at its next launch.

**forward's channels are relayed too** (dispatch://INFRA-702). forward serves each of them on a TCP listener of this host's loopback — the URL channel, the file preview, the browser relay, the callback bridge, the grant feed, pcsc and pulse, on the `listen`/`peer` pair its per-machine config names (127.0.0.2 and 127.0.0.1 on sami-rocqperf, `forward/AGENTS.md`) — and a box has a loopback of its own, so inside one every single channel answered `connection refused` while forward's two mounted unix sockets (`arm.sock`, `~/.pcscd/pcscd.comm`) worked. A box could therefore hold a port for the laptop but could not open a URL on it and could not ask for a browser grant. The launcher now reads every loopback listener in forward's reserved 128xx range (`forward_channels`), gives each one a forwarder on the box network's gateway (`agentbox-fwd-<port>`), and passes the list in `AGENTBOX_FORWARD_CHANNELS`; the entrypoint puts each back on the same address and port inside the box, pointing at that forwarder, so forward's own address list resolves unchanged (log: `/var/log/forward-relay.log`). A host running no forward passes none and the box starts without them. `agentbox doctor` compares the box's `forward doctor` rows with the host's and fails on a difference, which is what found this: 2 rows in the box against 6 on the host.

**Other host services on the loopback are relayed the same way.** `LOOPBACK_SERVICE_PORTS` in `scripts/agentbox` names them by port (`AGENTBOX_LOOPBACK_PORTS`, space-separated, replaces the list). Each one with a listener on this host's 127.0.0.x gets a forwarder on the box network's gateway (`agentbox-loopback-<port>`) and rides `AGENTBOX_FORWARD_CHANNELS` to a relay in the box on the same address and port, so it needs no image change. A port with no listener is skipped, and a forwarder that does not start is reported but does not stop the launch. Today the list is `5005`, the OSS Verify MLflow tracking server: on sami-rocqperf the machine-local unit `ossv-mlflow-tunnel.service` holds an IAP tunnel to VM `ossv-mlflow` on `127.0.0.1:5005`. On 2026-11-02 every route to it from a box failed and two lanes waited on it: the box's own loopback, the box network's gateway, docker0's `172.17.0.1`, and the tailnet name and address (`tailscale serve`'s `:8449` listener is bound to the `tailscale0` device, so a packet from a box bridge never reaches it). A box now reaches MLflow at `http://127.0.0.1:5005`, the address a host session uses, and a workload in the box cannot listen on that port itself. A box started before this change has no relay inside, but while the host forwarder runs it reaches the same server at `http://<gateway>:5005` (`172.22.0.1` here).

**Each box has a cpu, memory, pids and disk limit** (dispatch://INFRA-702). `docker run` gets `--memory 24g --memory-swap 32g --cpus 8 --pids-limit 8192`: a box that runs away is held by its own cgroup, and the other boxes and the host keep running. The defaults come from 44 live agent sessions measured on sami-rocqperf on 2026-10-31 (RSS+swap of each session's process tree, which overcounts shared pages): memory p50 2.3 GiB, p95 14.1 GiB, max 17.8 GiB; cpu over 10 s p50 0.15 cores, p95 1.74, max 3.09. One box changes with `agentbox new --memory SIZE --cpus N --disk SIZE`, or with `AGENTBOX_MEMORY` / `AGENTBOX_CPUS` / `AGENTBOX_DISK` in the launcher's environment; a flag wins over the variable. Above 96 GiB of memory, 32 cores or 512 GiB of disk the launcher refuses the launch with exit 2, naming the flag, the value and the cap, since a box that big starves the machine instead of its own session. The doctor box carries the same limits. `scripts/tests/test_agentbox_limits.py` holds the launcher's side of all of it.

**At its memory limit a box loses one process, not the session.** The kernel kills the box process with the largest badness (its RSS plus `oom_score_adj` × limit / 1000), and the box's docker scope runs `OOMPolicy=continue`, so the rest keeps running: on 2026-11-01 at 12:17:36Z a box lost a 2.0 GB python child and carried on. With every adj at 0 the largest process is often omp itself, and host-side `scripts/omp-memory-watch` cannot raise a box's processes (Sysbox maps their uid; it gets EPERM). So `scripts/agentbox-run.ts` raises them from inside: every 10 s each child of the runner but omp, and each child of omp, goes to +500 with the descendants it already has, and later forks inherit it. Under a 24 GiB limit that adds 12 GiB to each one's score, so the largest of them still goes first and omp outlives them all. The runner and omp stay at 0.

**The disk limit is a filesystem of the box's own, because no quota is available here.** docker's `--storage-opt size=` needs the overlay2 driver on xfs with project quotas, and this host's docker data root (`/var/lib/docker`, a bind of `/dev/md127[/docker]`) is ext4 under the overlayfs snapshotter, where docker refuses the option; ext4 project quotas are out too, since `/dev/md127` carries neither the `project` nor the `quota` feature and adding them means `tune2fs` plus a remount of a 3.4 TiB filesystem holding every session's work (both measured 2026-11-01). So `agentbox new` makes a **sparse ext4 image** per box under `<boxes>/../disks/<box>.img` and loop-mounts it at `<boxes>/<box>` before the clones are made, and `mount_args` puts the box's `$HOME` and its `/tmp` inside that directory as well — so the clones, the home overlay an allow-list miss lands in, and every tool's scratch share one ceiling. A write past it is `ENOSPC` inside that box and nothing else: measured 2026-11-01 in a 2 GiB box, `dd` stopped at 1.9 GiB with "No space left on device" while the host's `/mnt/nvme` lost nothing. The image is sparse, so a limit reserves nothing (N boxes at 32 GiB do not claim 32N GiB), and `discard` on the loop device returns freed blocks to the host while the box runs. **Default 32 GiB**, about eight times the largest of this host's 117 session worktrees (4.1 GiB on 2026-11-01). **Root is needed for one step only**, the mount: `sudo mount -o loop,noatime,discard <image> <boxes>/<box>` at launch and `sudo umount <boxes>/<box>` at close; the image, its mkfs and its removal all run as the user. `--disk 0` (or `AGENTBOX_DISK=0`) starts a box without one, for a machine with no such sudo rule. Two consequences to know: a box's clone **copies** the template's git objects instead of hard-linking them, because a hard link cannot cross into the box's filesystem and a quota has to own the bytes it bounds; and a box kept at close for unpushed work keeps its filesystem mounted, with the `sudo umount … && rm -f …` that frees it printed on the pane. The container's own writable layer (`/`, `/var`, `/opt`) is still on the shared disk and still unbounded — an `apt-get install` inside a box goes there — so the shared-disk tools (`scripts/disk-fill-watch`, the tmp reapers in `devbox/`) still matter for that part.

- **`Dockerfile`** — Ubuntu 24.04 with docker-ce (the box runs its own `dockerd`), Chrome (omp's browser tool), pip, postgresql-client, sqlite3, socat, wget, `bc` (agent-c's Pulumi suite runs a script that needs it, and CI runners have it, so a box without it reds a required local gate that CI passes), `bsdextrautils` for `column` (`scripts/envoy` formats `envoy ps` with it, so without it the human-readable listing died with `column: command not found` in every box while `envoy ps --json` worked, dispatch://INFRA-702), passwordless sudo for uid 1000, and the `/etc/agentbox-identity` marker, which `shims/omp` reads to say the box cgroup is the session's memory ceiling instead of reporting the systemd scope a box cannot get, and the disk-hygiene skill reads to sweep the box tree alone. Other tools are not installed here: the host's mise store is mounted in, so `mise.toml` pins apply inside exactly as on the host.
- **`entrypoint.sh`** — runs as root: starts the inner dockerd (its image store is an anonymous volume that dies with the box), inserts the DOCKER-USER rule against the metadata forwarder, starts the Envoy relay on the box's loopback as the session user (restarted a second after socat exits; its log is `/var/log/envoy-relay.log`, and a relay that does not come up is reported, not fatal), logs the inner docker into ghcr.io as the session user with the agent-tier `GHCR_PULL_TOKEN`, then `setpriv`s to `AGENTBOX_USER` for the session command.
- **`devbox-prune`**, **`devbox-prune.service`**, **`devbox-prune.timer`** — the host's prune of the always-safe class, a script to run by hand (`~/.dotfiles/agentbox/devbox-prune`): `docker volume prune -f` on the host daemon; in every running agent box, `image`, `builder` and `volume prune -f` on the box's own daemon (never `-a`; an empty `--config`, because a box's `builder` alias can point at depot); and host Go build cache entries idle more than 2 days. It logs bytes reclaimed per box and fails the run naming the box and command. `install.sh` sets up no timer (Sami, 2026-09-27). A host that should run it every 6 h links and enables the units by hand, as the shared devbox does: `ln -s ~/.dotfiles/agentbox/devbox-prune.{service,timer} ~/.config/systemd/user/ && systemctl --user daemon-reload && systemctl --user enable --now devbox-prune.timer`. The links point into the `~/.dotfiles` checkout, so moving or renaming these files kills that host's timer silently once systemd reloads: the devbox lost its 6-hourly prune that way on 2026-09-27, when `docker-volume-prune.*` was renamed away.

Root inside the box is Sysbox fake-root (a user namespace on the host), so `sudo apt-get install`, the inner Docker daemon, and nested containers (`tl run` sandboxes) work without host privileges. `sudo apt` installs die with the box; mise/uv/bun/npm installs persist through the mounted stores; durable image changes go in the Dockerfile plus `agentbox rebuild`.

knives: claims are keyed by the omp session id, so a boxed `knives start` is released at box exit without `--force`. The registered forks still live at their pre-`~/src` paths (`~/inspect/*`, `~/toon-rust/default`, …), which a box does not mount; `knives start` from a box works once a fork's checkout is moved under `~/src` (knives places workspaces next to the checkout, so they land inside the mount).

Secrets work from a box on both tiers as of `forward` v3.2.3 (sjawhar/forward#40): the daemon runs in the private user namespace its mount protections imply, so a same-uid client in a box arrives at `SO_PEERCRED` as the overflow uid, and the daemon decides admission on the socket node being owner-only rather than on that uid. With the socket mounted directly, omp's `REGISTER` pins the box's omp process and the ancestry walk crosses the container boundary (box pids are host pids to the daemon). `agentbox doctor` runs it on the host and inside the throwaway box.

### How changes take effect

Everything version-relevant except the image is a host mount seen by every box at once — the omp binary (`~/.mise`, pinned in `mise.toml`), the plugin tree (`omp/plugins/node_modules`, `bun install` on the host), config, agents, extensions and skills (`~/.config/omp`, `omp/`) — so a host-side update is live for the next omp *process*, not the next box: `agentbox restart --all` after a pin bump or `bun install` moves every session to it in place, each at its own safe point. Running processes keep what they loaded until then, as on the host. The image tag is the content hash of `Dockerfile` + `entrypoint.sh` (`agentbox:<12 hex>`), so editing either yields a new tag: the next `agentbox new` builds it, and `agentbox rebuild` builds it now and lists running boxes still on an older tag — those need a new box (`--resume`). `agentbox doctor` health-checks the host side and a throwaway box (tools, absent identity dirs, App-only gh, secrets tiers, AWS, hawk-token, google-user-token, envoy, forward channel parity with the host, inner docker). `agentbox sh <box|session-id>` execs into a running session's box.

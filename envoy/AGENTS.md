# Envoy

Pulumi (TypeScript) infrastructure that deploys the on-prem `envoy-listener` container to fleet hosts. See `README.md` for the full architecture, secrets, and command reference; this file only summarizes conventions.

**Webhook delivery:** Envoy receives external GitHub and Slack webhooks (ingressed through Fargate). Any change must preserve webhook delivery.

## Key files

- **`index.ts`** — entry point; reads `envoy:` stack config, loops over `machines`, creates one `envoy-infra:host:Listener` per host (and its opt-in watchdog).
- **`machines.ts`** — the machine config type and each host's docker provider.
- **`sdks/sjawhar-envoy-infra/`** — the Node SDK `pulumi package add` generated for Legion's `envoy-infra` plugin. Generated and committed (CI has no Pulumi CLI); never edit it by hand.
- **`Pulumi.yaml` / `Pulumi.prod.yaml`** — project (backend, plugin package) and encrypted prod stack config.
- **`mise.toml`** — pins the Pulumi CLI for this directory only.

## Conventions

- Stack config lives under the `envoy:` namespace; secrets are encrypted in `Pulumi.prod.yaml` and require `PULUMI_CONFIG_PASSPHRASE`, an agent-tier key in secretsd on the devbox and the laptop.
- The listener's container, image and watchdog come from Legion's `envoy-infra` plugin (`packages/envoy/infra` in sjawhar/legion), not from code here. A host's resources are children of its `host:Listener`; `adopt` names the root-level resources the program created before the plugin, so the listener takes over their state instead of replacing them. Keep those names.
- `tsconfig.json` targets `module: commonjs` for ts-node (Pulumi), not Bun. Leave the `ignoreDeprecations` setting in place.
- Do not commit decrypted secrets or `node_modules`.

## Where the secrets are

- **The Dispatch bearer token is not here.** Every Dispatch and Envoy client in a session — the pi-envoy extension's tools, the claude-envoy bridge and the `dispatch` command, all from the legion repo — reads one `envoy.json`: a `dispatch` section (`enabled`, `serverUrl`, `token`) and an `envoy` section (`enabled`, `url`, `natsUrls`, `token`, `natsSeed`), where a `token` or `natsSeed` that starts with `!` is a command whose output is the value. A session under a named omp profile, a Claude Code `CLAUDE_CONFIG_DIR` or an OpenCode `OPENCODE_CONFIG_DIR` reads the `envoy.json` in that directory and has no Dispatch or Envoy when it has none, so a profile that should have them needs a file there (a link to the neutral file serves). `cld` sets `CLAUDE_CONFIG_DIR` to `.claude` even without `--profile`, so a default `cld` session reads `.claude/envoy.json` like any other Claude Code profile directory, and has no Dispatch or Envoy when that directory holds none. Any other session reads the file `ENVOY_CONFIG_FILE` names, else the neutral file, `${XDG_CONFIG_HOME:-~/.config}/legion/envoy.json`. The commands here that read it — `scripts/envoy` (its listener and bearer), `agentbox doctor` (through `envoy config-path`) and the reflect skill's `extract-dispatch-human.py` — follow the rule a Legion script follows: `ENVOY_CONFIG_FILE`, else a named omp profile's `$PI_CODING_AGENT_DIR`, else, under Claude Code (`CLAUDE_CODE_CHILD_SESSION=1`, which Claude Code sets in every command it runs), `$CLAUDE_CONFIG_DIR`, else `$OPENCODE_CONFIG_DIR`, else the neutral file, so a command run from a plain shell that exports `CLAUDE_CONFIG_DIR` reads the neutral file; each runs a `!` token for at most 10 s without printing its output, and sends a file's token only to the address written beside it. `DISPATCH_URL`, `DISPATCH_TOKEN(_FILE)`, `ENVOY_URL`, `ENVOY_NATS_URL`, `ENVOY_TOKEN(_FILE)` and `NATS_NKEY_SEED(_FILE)` each override their own field, which is how a Legion pane gets the Dispatch and Envoy its daemon names, and why no launcher here (`shims/omp`, `scripts/cld`, `scripts/agentbox`) sets any of them: one would override every profile's file, and turn Envoy on for a profile that has none. An agent box reads the host's files (`agentbox/AGENTS.md`). The token is a secret: never commit it, never copy it into this directory. On the devbox its value is the shared agent token (Secrets Manager `production/dispatch/agent-token`), deployed for agent sessions to use with their own `actor` identity - it is not Sami's personal credential, and reading it from that file is the sanctioned path.
- **The sessions' NATS credential is not here either.** Sami's own omp and Claude Code sessions authenticate to production NATS as the `omp-session` nkey user, whose seed lives in Secrets Manager (`production/envoy/nats-nkey-seed-omp-session`, created by agent-c's infrastructure, LEGION-279 / AGENTC-759). A session takes it from its `envoy.json`: `"natsSeed": "!$HOME/.dotfiles/scripts/envoy-nats-seed --value"` in the `envoy` section runs `scripts/envoy-nats-seed` (`/bin/sh` expands `$HOME`, so the command does not depend on the session's `PATH`), which caches the seed once per boot in a 0600 file under `$XDG_RUNTIME_DIR/envoy/` and exits 1 naming why when there is none, which the client reports as an error naming the field. A file with no `natsSeed` connects without a credential. The listener this directory deploys is configured separately.
- **This directory holds the deployment's own secrets only**, encrypted in `Pulumi.prod.yaml`: `envoy:githubWebhookSecret`, `envoy:slackSigningSecret` and the `envoy:ghcrToken` image-pull token.

## How changes take effect

Changes deploy via `secrets PULUMI_CONFIG_PASSPHRASE -- pulumi up --stack <stack>` from this directory (`npm ci` first), with the Pulumi CLI `mise.toml` pins. There are two stacks, each applied from its own machine, because a machine with no `sshHost` uses the Docker socket of whoever runs Pulumi: `prod` from the devbox (the devbox and oryx), and `laptop` from the laptop (the laptop alone, under `AWS_PROFILE=default` for the S3 state). `README.md`, "Architecture", has the table. The watchdog is opt-in via `ENVOY_DEPLOY_WATCHDOG=1`. The plugin is pinned to a Legion release in `Pulumi.yaml`'s `packages`; to move the pin, verify the release's archive, install it, and run `pulumi package add envoy-infra@<v> …`, which regenerates `sdks/`. `README.md`, "The envoy-infra plugin", has the commands.

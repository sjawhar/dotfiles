# Using Subagents

Subagents lose your context the moment they start. Everything they need — and every channel back to you — goes in the dispatch prompt, or it does not exist.

## Envoy comms (check once per session)

Run `envoy_whoami`. If it returns a session ID, Envoy is available and the rest of this section is mandatory; if the tool is missing, skip to Dispatch Prompts.

**In every dispatch prompt, include:**

1. Your session ID, with the instruction: *message me via `envoy_send(session_id="<your-id>", ...)` when you finish, hit a blocker, or need a decision you cannot make yourself. Include your own session ID (from `envoy_whoami`) so I can reply.*
2. That a clarification question sent this way beats guessing. A subagent that guessed wrong burns its whole run; one that asked lost a minute.

**Stalled subagent? Message it before you kill it.** A subagent that looks stuck may be deep in legitimate work — killing it burns everything it learned. `envoy_send` a status request and give it ~10 minutes to answer (longer if its task involves builds or long test suites); re-dispatch only on silence or a reply confirming it is wedged. Kill-then-redispatch without asking is the last resort, not the reflex.

**A status is not progress evidence.** When work reported as `Running` would change a lane's next decision, check for fresh tool output or an observed state transition; if neither exists, use the direct-message deadline and cancel/re-dispatch path above rather than reporting liveness as progress. This applies only when the distinction affects a decision, not to a known long-running job that continues to show progress; it is inferred from AGENTC-186's 2026-09-16 retro (platform PO, 2026-09-17).

**Replies arrive as turns in your session** with a reply-to session ID — respond with `envoy_send(session_id="<their-id>", ...)`.

## Dispatch prompts

- State the goal, the exact file paths (absolute — the subagent's working directory may not be yours), the conventions to follow, and how the subagent should verify its own work. "Fix the bug" prompts produce guesses.
- One goal per dispatch. Multiple independent goals fan out as parallel dispatches, never bundled.
- **One deliverable, one owner.** A feature or fix is dispatched whole, never parcelled by layer, lane, or "read half / write half" across agents: the seam is where the contract goes wrong. Parallel dispatches are disjoint deliverables, not slices of one. When two agents turn out to hold pieces of one deliverable, one hands off completely to the other. Prefer a subagent under your own session to a new peer session: sessions he has to watch are the cost, and work already in progress is finished before new work is started. A standing role he defined himself (an on-call role that remediates while the owner repairs) is his design, not the split this forbids.
- **Judgment work goes to a strong model; the floor is by task class, not by role name.** Reviewing code, owning a fork PR, simplifying code, planning, rewriting something a human will read, reading transcripts for what went wrong: never a low- or mid-tier model. Retrieval, mechanical fan-out, and line-finding stay cheap; a role mechanical enough for a cheap model is usually a script you should write instead (inferred from #818). Under `/sdd` the role mapping already fixes the tier; this is the same floor for every other dispatch.
- **Do not cap a subagent you did not have to cap.** No turn budgets, step caps, or time boxes on a dispatch unless the task itself calls for one (an eval that caps turns is the task's spec, not this); he lets agents run for days, and the rule that forbids you from stopping early forbids you from stopping a subagent early. Leave room for a subagent's own subagents (#1378, 2026-09-09).
- **Absolute paths are the mechanism, not style: a subagent's relative tool paths resolve against the PARENT's cwd.** `edit`/`read`/`write` with a relative path act in the coordinator's working directory even when the subagent holds its own `jj workspace add` path and even after its own `bash cd`; a subagent told to work in `../.worktrees/x` that edits `meta/foo.py` edits the coordinator's live checkout. Verified 2026-09-13 on agent-c #18341: five investigators, each with its own workspace, wrote stray files into the coordinator's checkout and contaminated two PR heads; it recurred 2026-09-15 22:22Z, landing a worker's edit in the shared checkout. Third instance, 2026-09-18, the quiet form: a coordinator whose lanes used absolute `cd`s in every bash command still accumulated **553 stray paths** in its session-cwd default workspace over a few hours — three Playwright screenshot trees at the repo root (547 files, 77 MB), two test files, one tracked file with a stray blank line, and a 102-line test inserted into the wrong `interactions_test.go` — all from lanes' relative `edit`/`write` calls; nothing errored, because the writes landed somewhere plausible. Audit another session's or the default workspace without touching it: `jj -R <repo> --ignore-working-copy status` (reads the last snapshot, mints no commit). A coordinator does not dispatch from a cwd it does not own. Two separate findings from the same lane (dispatch, 2026-09-18), which travel together but are not one mechanism: (i) an UNQUOTED heredoc delimiter (`<<EOF`) silently corrupts long prose — measured: `$100` became `00`, `$HOME` leaked an absolute path, `$(…)` errored AND deleted itself from the text, backticks ran as commands — and the file is still written, non-empty and plausible; `<<'EOF'` is byte-exact. Never pass a PR body, issue comment or long prose inline: write it to a file (quoted delimiter, or the write tool) and pass `--body-file`. (ii) Separately: after a tool call that aborted mid-parse, the lane found the shell's cwd back at the SESSION cwd, so the next relative operation landed in the shared checkout. Not caused by (i) — command substitution runs in a subshell and cannot move the parent's cwd (tested). An earlier version of this sentence called the reset unexplained; the abort was not the cause either. On omp 18.2.9 the bash tool starts EVERY call at the session cwd, so a `cd` never carries into the next call (librarian, 2026-09-25: `cd /tmp` in one call, `pwd` in the next printed the session cwd). It also bites a top-level session working in its own jj workspace, not only subagents: a relative `write` after a bash `cd` landed in the session's default checkout (AGENTC-723 lane, 2026-09-25, reproduced the same hour). Give bash its `cwd` on every call and pass `edit`/`write` absolute paths. So after any tool call that errored strangely or returned mangled output, `pwd` and `ls -la` the file you believe you just wrote before the next call. Every dispatch brief that may edit says, in these words, "absolute paths only, rooted in `<workspace>`", with the workspace path spelled out; a coordinator whose working copy is live either does that or dispatches from a scratch cwd. After a dispatch wave returns, `jj st` in your own checkout - a stray file there is the subagent's.
- Include what the subagent must NOT do (scope it out explicitly — subagents expand scope when uncertain).
- **Pin the environment a lane depends on; never inherit it.** The relative-path failure has an environment-variable twin: a reviewer session inherited `UV_PROJECT_ENVIRONMENT=/tmp/r3walk/lane-venv` from another session, so every `uv` call resolved a sibling's shared virtualenv while that venv was being changed underneath it — no error, a plausible result about a tree the lane did not control (PBT reviewer session via the dispatch lane, 2026-09-18; a `PYTHONPATH` leak the same night). Treat `*_PROJECT_ENVIRONMENT`, `PYTHONPATH`, `VIRTUAL_ENV`, `DOCKER_CONFIG` and any other ambient pointer as untrusted input: name the venv, cwd and config path explicitly per invocation, and before trusting a measurement print the path the tool resolved and check it is inside your own workspace. The propagation channel is unconfirmed (reported as harness-side); the rule does not depend on it.
- **Every brief names the skills the subagent is required to load.** Under `/sdd` the plan's `## Skill catalog` supplies them per step; outside it, the dispatcher selects them the same way. A subagent does not inherit your loaded skills: a skill not named in its brief does not exist for it.
- **A tester/acceptance dispatch is briefed skeptical and owns the red test.** The brief states that the work is presumed broken until the tester proves otherwise on the real surface, that unit-only verification does not qualify (inferred — the 2026-09-16 tester audit: 79.9% of 4,282 tester-population dispatches never touched a running surface), and that on finding a defect the tester writes the failing red test itself. The resumed implementer's brief then says, in these words, "make the tester's red test pass; do not modify it" — mark tester-authored tests as such in the handoff.
- Results come back to you for verification — check them file-by-file against what you asked. A subagent report is a claim, not evidence.
- **Recheck a worker's claimed blocker before repeating it.** A report inherited from another lane is a lead, not a blocked state. When the coordinator needs to report or escalate it, identify the exact command that still fails and the authoritative record checked; if either changes the conclusion, continue on the working path. This extends `CLAUDE.md`'s check for a path that already works elsewhere, rather than adding a human approval gate. Sami's anchor: "What exactly is blocked?" (Sami, transcript #2814, 2026-09-15).
- **An empty or malformed result is an unexecuted task, not a clean verdict.** Before treating "no findings" as a finding, read the dispatch's completion status and confirm it did work: 25 of 4,282 dispatches in the 2026-09-05→16 window (0.6%) returned zero tool calls and zero content, and the one that was caught was caught by the orchestrator reading a hub `status='failed (exit 1)'` (claudemd-miner #1). Re-dispatch, carrying what is known. The trigger is zero content or a failure status, not brevity — a terse clean report that shows its work is a report. A provider refusal and a quota failure are the same case in disguise: a reviewer refused on attack-corpus content returned a refusal string and no verdict (TaskReview-19949, platform PO, 2026-09-23), and six `astra` subjects on `usage_limit_reached` returned empty, schema-invalid payloads (librarian walk, 2026-09-23). Neither is "no findings"; only a parsed verdict is a verdict.
- **Every dispatch carries the four shell rules, verbatim.** (1) *Never run `rm -rf` (or `rm -r`) on a path that contains a variable, `~`, or `$HOME`; `ls` the literal path first and delete that literal path.* (2) *Never `export`, and never rely on a variable carrying across bash calls in either direction; set it per command (`env HOME=/tmp/x cmd`).* The two rules exist together: an `export HOME=$(mktemp -d)` that did not survive to the next call turns `rm -rf "$HOME"` into the deletion of the real home directory. An earlier wording said variables do not persist between bash calls; that is harness-dependent, and on omp 18.2.9 it is false: an `export` survives into every later bash call of the same session (it does not reach a dispatched subagent; librarian, 2026-09-25). There the same `export HOME=...` silently re-roots every later command the session runs, which is why the rule forbids the export instead of describing its lifetime. Cleanup of temp fixtures belongs to the coordinator, by literal path, after the subagent reports the path. (3) *Never read an exit code through a pipe: `cmd | tail -1` reports tail's status, not cmd's. When the exit code is the observation, run the command bare, or use `set -o pipefail` or `${PIPESTATUS[0]}`, and read the artefact back.* Two independent lanes hit this on 2026-09-21: a production CLI's exit 1 read as 0 through `| tail`, and a `jj git push --named` that exited 1 and published nothing. The jj case also shows the trap's second half — its neighbour, a bare `jj git push` on an untracked bookmark, publishes nothing while exiting **0** with a last line of `Nothing changed.`, so the exit code alone would not have caught it either. Read the artefact back. (4) *In any chained command that mutates a repository, gate dependent steps with `&&`, never `;`* — a `;` runs the push after the failed edit; measured twice on 2026-09-21/22 (a divergent-rebase refusal ridden past into a wrong-base push; an empty described commit pushed to main after an edit-script assert failed).
- **Push before you move on.** A branch that exists only in a working copy is one bad command from gone. The coordinator pushes a WIP bookmark after every reviewed task; a subagent never has unpushed work older than its own task.
- **A subagent that will run jj mutations gets its own `jj workspace add` path in the brief.** `jj new`, `jj describe`, `jj rebase`, `jj bookmark set` all move the shared `@`; a subagent doing that in your checkout silently swaps the tree under your gate run (a coordinator's `pytest` measured the subagent's commit — `96 passed` against `113` at its own head — and passed; the jj hint was one line, "Concurrent modification detected, resolving automatically"). Name the workspace path in the brief and the bookmark it may move; a read-only subagent needs neither.
- **A read-only lane gets no workspace or clone of its own; a lane that must mutate gets one scratch copy of only what it mutates, and the coordinator deletes it when the lane ends.** Reading needs no copy of the tree: `gh api` contents at a ref, `jj file show -r <rev> <path>`, or `git show <rev>:<path>` from the existing checkout. A mutant or a test run does need a copy, but of the paths under test rather than the repository, and it is session scratch that the coordinator removes by literal path after the lane yields. Sami, 2026-09-24: "You do not need to give every hub agent its own workspace, especially if [they] are doing read-only review work", after one night's review lanes left twelve scratch directories in one box's `/tmp` (31 GB, the largest 6.7 GB), seven of them full copies of a repository made to read or mutate a few files.
- **A claim about what X does under Y must read Y's config, not only X's source.** An oracle that reasoned from Inspect's source alone reported that hawk keeps five raw model calls per sample; hawk's `EvalSetConfig.log_model_api` defaults `True` and every raw call is retained. When the brief asks about a consumer's behaviour (hawk, a workflow, a deployment), name the consumer's config file as a required read, and treat a "found nothing" from a search scoped to one system as evidence about that system only, never as evidence of absence.
- **A design or implementation brief that touches Inspect, the `inspect_*` forks, Hawk, middleman, or the bridge names the code paths the worker must read before designing — the fork checkout or the installed package under the venv — and requires a `file:line` citation for every claim about how those systems behave; an uncited claim is written as an assumption**. In agent-c the brief names `docs/architecture/facts.md` as the first read, the standing list of known misreads (inferred — that doc exists for this step).
- **A read-only survey reads `origin/main`, never a long-lived checkout's working tree, and every absence claim names the command that would have found the thing.** A shared checkout drifts — one session's default cwd had diverged from main by 13,244 files — and a survey run in it reports the drift as fact. Two false-absence claims came out of exactly that on 2026-09-16: "the tracker label does not exist" (it does, `platform/tl_platform/frontend/src/components/StaffShell.tsx:163`; the surveyed worktree had no `dpi/*` routes at all) and "this page is an orphan" (it is linked from two places; the grep looked for `<Link>` and missed a plain `<a href>`). Every survey brief says, in these words: "read from `origin/main` (`git show origin/main:<path>` / `jj file show -r main@origin <path>` / `gh api` contents at the ref), never the shared long-lived checkout's working tree; every absence claim names the command that would have found it, and a grep for a reference covers the rendered form too (`<a href>` as well as `<Link>`)". The bundled `scout` agent has no `bash`, so it cannot run either command itself — run the survey as a `task` agent that can, rather than giving the scout a workspace of its own (the rule above).
- **A Scout count is a lower bound unless its scope is stated.** When a Scout result informs a decision, report the queried population, scope, and any retrieval limit alongside the count; do not call its count exhaustive without those facts. This applies only when the count carries a completeness claim and is inferred from AGENTC-186's 2026-09-16 retro (platform PO, 2026-09-17).
- **An evidence-fetch brief describes the file operation, not the content domain.** A worker sent to list, read the header of, or count production eval logs is briefed with those verbs and the paths; the attack vocabulary (cybertask, exploit, injection, the technique names) goes in the analysis step's brief, never the fetch step's. A worker whose fetch prompt named cybertask evals was refused on every shell call (`Refusal (cyber)`) and the lane did the read-only S3 listing itself; the provider refuses on the prompt's words, not on the operation. Inferred from the viewer lane's 2026-09-16 retro (platform PO, 2026-09-17); the harness-level fix (retry an unstarted call on a non-refusing model) is a separate omp change. The same refusal fires on content a worker reads, not only on its brief, and once refused text is in the transcript every later wake refuses: the session is wedged, not the step (`tasks/email-drive-file-exfil-ml/tests/test_grading.py` stopped two `deep` lanes 17 and ~20 minutes in; task-delivery lane, 2026-09-23). Re-dispatch fresh with a brief naming only ids and the code-level defect, no paraphrase of the scenario; if that lane stops too, dispatch on a non-Anthropic model (`astra`, or `gpt-api` when astra reports `usage_limit_reached`, and say why in the brief). A reviewer whose subject is attack content (an examples corpus, a grading fixture) goes to `astra` first, with one line saying the content is authorized internal safety-evaluation material and the review is of the product surface (platform PO, 2026-09-23).

## Continuation beats fresh dispatch

Every `task()` result carries a continuation session ID (`ses_...`). For follow-ups, fixes, or "also do X" on the same work, continue that session (`task(task_id="ses_...")`) instead of dispatching fresh — the subagent keeps everything it already learned. The exception is a confirmed-wedged subagent: its session is the thing that is stuck, so that is the one case where a fresh dispatch (carrying a summary of what the wedged run learned) beats continuation.

# Using Subagents

Subagents lose your context the moment they start. Everything they need — and every channel back to you — goes in the dispatch prompt, or it does not exist.

## Envoy comms (check once per session)

Run `envoy_whoami`. If it returns a session ID, Envoy is available and the rest of this section is mandatory; if the tool is missing, skip to Dispatch Prompts.

**In every dispatch prompt, include:**

1. Your session ID, with the instruction: *message me via `envoy_send(session_id="<your-id>", ...)` when you finish, hit a blocker, or need a decision you cannot make yourself. Include your own session ID (from `envoy_whoami`) so I can reply.*
2. That a clarification question sent this way beats guessing. A subagent that guessed wrong burns its whole run; one that asked lost a minute.

**Stalled subagent? Message it before you kill it.** A subagent that looks stuck may be deep in legitimate work — killing it burns everything it learned. `envoy_send` a status request and give it ~10 minutes to answer (longer if its task involves builds or long test suites); re-dispatch only on silence or a reply confirming it is wedged. Kill-then-redispatch without asking is the last resort, not the reflex.

**A status is not progress evidence.** When work reported as `Running` would change a lane's next decision, check for fresh tool output or an observed state transition; if neither exists, use the direct-message deadline and cancel/re-dispatch path above rather than reporting liveness as progress. This applies only when the distinction affects a decision, not to a known long-running job that continues to show progress; it is inferred from AGENTC-186's 2026-09-16 retro (platform PO, 2026-09-17).

**Replies arrive as turns in your session** with a reply-to session ID — respond with `envoy_send(session_id="<their-id>", ...)`.

## Dispatch prompts

- State the goal, the exact file paths (absolute — the subagent's working directory may not be yours), the conventions to follow, and how the subagent should verify its own work. "Fix the bug" prompts produce guesses.
- One goal per dispatch. Multiple independent goals fan out as parallel dispatches, never bundled.
- **One deliverable, one owner.** A feature or fix is dispatched whole, never parcelled by layer, lane, or "read half / write half" across agents: the seam is where the contract goes wrong. Parallel dispatches are disjoint deliverables, not slices of one. When two agents turn out to hold pieces of one deliverable, one hands off completely to the other. Prefer a subagent under your own session to a new peer session: sessions he has to watch are the cost, and work already in progress is finished before new work is started. A standing role he defined himself (an on-call role that remediates while the owner repairs) is his design, not the split this forbids.
- **Judgment work goes to a strong model; the floor is by task class, not by role name.** Reviewing code, owning a fork PR, simplifying code, planning, rewriting something a human will read, reading transcripts for what went wrong: never a low- or mid-tier model. Retrieval, mechanical fan-out, and line-finding stay cheap; a role mechanical enough for a cheap model is usually a script you should write instead (inferred from #818). Under `/sdd` the role mapping already fixes the tier; this is the same floor for every other dispatch.
- **Do not cap a subagent you did not have to cap.** No turn budgets, step caps, or time boxes on a dispatch unless the task itself calls for one (an eval that caps turns is the task's spec, not this); he lets agents run for days, and the rule that forbids you from stopping early forbids you from stopping a subagent early. Leave room for a subagent's own subagents (#1378, 2026-09-09).
- **Absolute paths are the mechanism, not style: a subagent's relative tool paths resolve against the PARENT's cwd.** `edit`/`read`/`write` with a relative path act in the coordinator's working directory even when the subagent holds its own `jj workspace add` path and even after its own `bash cd`; a subagent told to work in `../.worktrees/x` that edits `meta/foo.py` edits the coordinator's live checkout. Verified 2026-09-13 on agent-c #18341: five investigators, each with its own workspace, wrote stray files into the coordinator's checkout and contaminated two PR heads; it recurred 2026-09-15 22:22Z, landing a worker's edit in the shared checkout. Third instance, 2026-09-18, the quiet form: a coordinator whose lanes used absolute `cd`s in every bash command still accumulated **553 stray paths** in its session-cwd default workspace over a few hours — three Playwright screenshot trees at the repo root (547 files, 77 MB), two test files, one tracked file with a stray blank line, and a 102-line test inserted into the wrong `interactions_test.go` — all from lanes' relative `edit`/`write` calls; nothing errored, because the writes landed somewhere plausible. Audit another session's or the default workspace without touching it: `jj -R <repo> --ignore-working-copy status` (reads the last snapshot, mints no commit). A coordinator does not dispatch from a cwd it does not own. Not caused by (i) — command substitution runs in a subshell and cannot move the parent's cwd (tested). An earlier version of this sentence called the reset unexplained; the abort was not the cause either. On omp 18.2.9 the bash tool starts EVERY call at the session cwd, so a `cd` never carries into the next call (librarian, 2026-09-25: `cd /tmp` in one call, `pwd` in the next printed the session cwd). It also bites a top-level session working in its own jj workspace, not only subagents: a relative `write` after a bash `cd` landed in the session's default checkout (AGENTC-723 lane, 2026-09-25, reproduced the same hour). Give bash its `cwd` on every call and pass `edit`/`write` absolute paths. Every dispatch brief that may edit says, in these words, "absolute paths only, rooted in `<workspace>`", with the workspace path spelled out; a coordinator whose working copy is live either does that or dispatches from a scratch cwd. After a dispatch wave returns, `jj st` in your own checkout - a stray file there is the subagent's. The mirror symptom is an EMPTY commit in the worker's own workspace after it reported edits: the writes went to the default checkout, so the work is misplaced, not lost. Look there before re-doing it (2026-09-25: AGENTC-310 and AGENTC-722 wrote through relative paths into one coordinator's default checkout and entangled each other's files in a single divergent commit; 310's successor first read its own code as lost; platform PO).
- **Never pass long prose inline to a shell in a brief.** Two separate findings from the same lane (dispatch, 2026-09-18), which travel together but are not one mechanism: (i) an UNQUOTED heredoc delimiter (`<<EOF`) silently corrupts long prose — measured: `$100` became `00`, `$HOME` leaked an absolute path, `$(…)` errored AND deleted itself from the text, backticks ran as commands — and the file is still written, non-empty and plausible; `<<'EOF'` is byte-exact. Never pass a PR body, issue comment or long prose inline: write it to a file (quoted delimiter, or the write tool) and pass `--body-file`. (ii) Separately: after a tool call that aborted mid-parse, the lane found the shell's cwd back at the SESSION cwd, so the next relative operation landed in the shared checkout.
- **An absolute `read` does not protect a relative `edit` header.** The `edit` header counts separately: an absolute `read` does not protect a relative `[path#TAG]` header, which re-resolves against the session cwd, and the tag binds to content, not to the file that was read. So when the cwd copy has identical content, the tag validates with no stale-tag warning and the wrong file is written silently (reproduced 2026-09-25 by the librarian; reported by the platform PO's AGENTC-310 lane, whose AGENTC-441 sibling wrote a docs addendum into the shared checkout this way; filed with the tool owner). When the cwd copy DIFFERS, the same edit fails with a snapshot-hash mismatch, which reads like a stale read. Re-reading by the relative path re-reads the wrong file, so don't retry; switch to the absolute workspace path (Fix PR20044 lane, 2026-09-25: a fixer in its own workspace had its first two relative edits rejected this way). So after any tool call that errored strangely or returned mangled output, `pwd` and `ls -la` the file you believe you just wrote before the next call.
- Include what the subagent must NOT do (scope it out explicitly — subagents expand scope when uncertain).
- **Pin the environment a lane depends on; never inherit it.** The mirror matters as much: A GATE'S ENVIRONMENT IS POORER THAN ANY DEVELOPER BOX, and that is where a whole class of defect only appears — so a brief that names a CI lane's FILE must name the lane's ENVIRONMENT too. Two lanes, 2026-09-25: a candidate route's Cognito client resolved its dependency before the body and raised `NoRegionError` on a region-less runner, so the isolation lane saw 500 where the builders pin 404, and every local green run had a `~/.aws/config`; and a box exporting `CI=true` WITHOUT the token that implies reddened one test on a bare run that `env -u CI` skips. Brief it as an instruction — "run it once with the region unset" — not as context. The relative-path failure has an environment-variable twin: a reviewer session inherited `UV_PROJECT_ENVIRONMENT=/tmp/r3walk/lane-venv` from another session, so every `uv` call resolved a sibling's shared virtualenv while that venv was being changed underneath it — no error, a plausible result about a tree the lane did not control (PBT reviewer session via the dispatch lane, 2026-09-18; a `PYTHONPATH` leak the same night). Treat `*_PROJECT_ENVIRONMENT`, `PYTHONPATH`, `VIRTUAL_ENV`, `DOCKER_CONFIG` and any other ambient pointer as untrusted input: name the venv, cwd and config path explicitly per invocation, and before trusting a measurement print the path the tool resolved and check it is inside your own workspace. The propagation channel is unconfirmed (reported as harness-side); the rule does not depend on it.
- **Every brief names the skills the subagent is required to load.** Under `/sdd` the plan's `## Skill catalog` supplies them per step; outside it, the dispatcher selects them the same way. A subagent does not inherit your loaded skills: a skill not named in its brief does not exist for it.
- **A tester/acceptance dispatch is briefed skeptical and owns the red test.** The brief states that the work is presumed broken until the tester proves otherwise on the real surface, that unit-only verification does not qualify (inferred — the 2026-09-16 tester audit: 79.9% of 4,282 tester-population dispatches never touched a running surface), and that on finding a defect the tester writes the failing red test itself.  Its report states, per item, whether the check RAN, was BLOCKED, or came back PARTIAL — never a bare pass or fail — and the brief asks for exactly that, because a reader cannot tell a check that passed from one that never ran. This is the producing half of "a green gate proves nothing until you know your assertion executed", and three lanes used it on 2026-09-25: one marked a control PARTIAL rather than passing when it touched the path but asserted something adjacent; one carried RAN versus BLOCKED per row through a re-dispatch; one paired it with a stop condition ("if container creation hangs for more than 2 minutes, stop and report that item BLOCKED with the command and what you saw; do not retry in a loop") and finished with nothing fabricated and no window burnt. The resumed implementer's brief then says, in these words, "make the tester's red test pass; do not modify it" — mark tester-authored tests as such in the handoff.
- **Brief a worker with the PRIMARY-SOURCE POINTERS, not with your conclusion about them.** Name the issue number, the file and line, the run id — and let it read them, because your conclusion is the thing most likely to be wrong and its independent read is the check. Four lanes were corrected by their own workers this way on 2026-09-25: one had told its worker a fix was folded into a commit, and the worker opened the issue and diffed the file to show it was a separate, still-open issue about a different secret with the handling byte-for-byte unchanged; one had cited an IAM precedent from a snippet, and the worker read the full policy statements; one stated a measured literal of 48 that the worker found was 47 in the tree the brief was actually about; and one briefed `--only refusal` as the example command, where the worker read the CLI and found that flag SKIPS the judge entirely, so the proof would have come back confidently green about nothing. This is the cheapest review in the system and it needs no gate — the read you skipped is the one your worker will do. Reading the primary source is only half of it: STATE THE UNIT YOU COUNTED IN, or two correct readers of one endpoint will hand you a contradiction that is not one. Two lanes reported the same run's attempts as "attempt 2 failed one leg, attempt 3 34/34" and "attempt 2 failed two legs, attempt 3 24/24", and both were right — one counted failed LEGS, the other counted only the failures of the class under investigation, and one counted every JOB in the attempt while the other counted the 24 build legs the page itself is unitised in. Name the call and the unit (`.../attempts/N/jobs?per_page=100`, legs versus jobs) and the disagreement evaporates; name only the conclusion and it looks like one of you is wrong.
- **An `isolated: true` task's patch is applied to WHATEVER HEAD your checkout is sitting on, so give it a clean `@` first and read `git status --short | wc -l` before the next command.** One coordinator's checkout was a stale detached HEAD eight hours behind; the harness auto-applied a 16-file patch onto it and produced 593 dirty files — the lane's own PR plus that drift — which `jj restore --from @-` cleaned only because the branch was already pushed. The result line says `Applied patches: yes/no`: READ IT. A sibling lane whose apply FAILED and left a `.patch` artifact instead had the safer outcome.
- **To see whether a lane is really working, read `hub ps`, not `pgrep`.** A lane that runs long operations as hub-supervised processes is INVISIBLE to a process-name grep: `pgrep '<the long command>'` reported one lane idle while `hub ps` showed EIGHT failed apply attempts.
- **A supervised process's failure evidence is volatile, so a long-running lane's brief must say to copy each attempt's terminal error line into its report AS IT HAPPENS.** One lane's `hub logs` returned only a cursor after the process failed — the error text was gone by the time the coordinator looked, which turns a diagnosable failure into a retry loop nobody can explain.
- **A gate brief carries what is already known, first.** Two copies of one rule do not merely duplicate, they DRIFT: after seven rounds of deltas on one page a remedy paragraph said to escalate a burst that survives re-runs, plural, while the tiebreak said to stop retrying after one. Note which instrument finds that — a reviewer's WHOLE-PAGE read did, and the author's grep for the sentence it had just changed did not. A subject grep before writing prevents the second copy; only a full read catches two copies that have already parted. One subject, one place, in its own short line: a rule buried mid-way through a 3.5 KB paragraph is read past, and a rule the dispatch CONTEXT also restates will eventually contradict the brief — one worker on 2026-09-25 had to flag that its brief said "do not open the PR" while its context said to open it, and the only reason that cost minutes instead of a wasted lane is that the worker asked. The trigger for splitting is the artifact's NEXT READER — a handoff, a review, a dispatch that will quote it — not the moment you notice the length, which is how a correct rule turns into churn. Three lanes picked that moment independently on 2026-09-25: split a briefing paragraph when the next brief needs it, add a six-line state block to a 40-entry delta log before the next handoff, and split a growing comment when it takes its next delta. A delta LOG and a RULE SET also need different repairs: a log needs a current-state header, a rule set needs subject-led items. The same measurement holds for skills: moving two rules out of long bullets into their own bolded leads took a fresh reader from 2 of 6 to 4 of 6 answered on a first pass, and the two that remained were both sentences sitting past the point where a single read truncates a very long line. A review, tester or pair dispatch's `# Task` block names the implementer's report file, CI's failure list at the head (job names and run ids), and every finding still open from earlier rounds, ahead of the task, so the gate spends its time on the delta instead of rediscovering known state. Measured 2026-09-25: without it, a reviewer and a tester on agent-c #20142 each spent ~45 min re-deriving 13 CI reds that the implementer's report and CI's job log already named (reasoning UI lane). With it, three pair rounds on #20040 returned a structured recheck of prior findings with nothing re-derived (Fix PR20044 lane), and a reviewer whose brief carried the claims ledger asked its coordinator nothing (gh auth lane). A claim the gate cannot reproduce is recorded as unreproduced on the surface it tried, not as wrong: twice that night an implementer was told to delete a claim that proved exact. The brief also asks for what the reader saw outside the diff, flagged as unverified: the cheapest place to find the next change's defect is a reviewer already reading the neighbouring code. One deep review passed its own diff and then handed back a third upstream removal it had noticed — a tag rename that would have left an IAM condition granting reads on tags nobody writes any more, which fails exactly as silently as a rule matching nothing (2026-09-25). Re-dispatching the SAME reviewer type on a fold is the sharpest case: `read agent://<prior lane>/findings` and paste its IDS into the brief with "closed / partially open / open" per id. A fresh quality lane without its predecessor's ids re-discovers the tree and produces a SECOND NUMBERING that nobody can reconcile against the first, so the round's output is two unmergeable finding lists rather than one closed one. And before you write "closed" against an item the implementer marked Done, `grep -n` that item's target symbol or docstring IN THE HEAD: one re-gate found a docstring untouched under a Done mark. The report is a claim; the tree is the record — the same read-back the author owes their own edit, owed by the coordinator to someone else's.
- **A brief states the defect and the acceptance test; a fix you have in mind is a suggestion the worker is expected to overturn with evidence.** Write it as one candidate ('one option: ...'), name the criterion that decides between options, and let the measurement pick.
- **Before naming a contract field's TYPE in a brief, run the constructor.** Constructing it in a one-liner costs seconds; a plan that typed a field `float | None` cost a round, because the library's model refuses `None` with a validation error and the real answer was that library's own sentinel constant. A type written from memory of an API is a hypothesis, and the constructor is the cheapest possible test of it.
- **A brief that asks for a measurement says what to do when the measurement is impossible.** Without that line or the lane fabricates a number, or OVER-measures — the two are the same hole, and the second is the commoner one: a tester asked to re-verify a set of lines with no clause for a line that cannot be re-measured spent 77 minutes re-probing what file identity already bound, where the next brief ("identity-bound, no new probes; if a line cannot be bound, name it and stop") closed in 2 minutes 19 seconds. Without the clause a lane burns its window discovering the gap: one lane was told to "measure the consumption" of something already known to be unanswerable by construction and spent the window proving the telemetry cannot see it — the more valuable answer, by luck rather than by the brief. The working form, measured the same night: "write the red test if an existing seam lets you inject the failure; if none exists, say so in the body's Not covered" came back in ONE round with the reason no seam exists, no fabricated test, and no wasted window. At PLAN level the same line stops the work rather than the report: a plan whose proof measurement was impossible from the start — the bake counts had to come from a box in one account against a builder in another, on colliding subnets — carried seven implemented commits before anyone tried to take it. If the proof cannot be taken, that settles the driver before the code, not after. Name the OBSERVABLE that stands in when the measurement is refused rather than merely impossible, which is the constructive half: a brief that asked a lane to enumerate a branch's required checks hit a 403 (branch protection is unreadable to that token) and its fallback line — "all three PRs report MERGEABLE, which no failing required check permits" — got the right answer by design rather than by luck. Put the clause in the brief TEMPLATE rather than remembering it per dispatch, because this failure is silent — the agent that fabricates and the agent that measures produce reports of the same shape. One lane ran the A/B in a single night: the brief that carried it ("if you genuinely cannot reach a surface, say NOT verified and name the blocker; do not substitute reading the code") came back with three unreachable surfaces each named with its reason, and those three are now stated limits in the PR body; the brief that omitted it told a tester to use one environment across four trees, and only the tester's own care — building a second venv when the pins made one environment impossible — kept a clean-looking interaction result from hiding an environment difference. Name the fabrication you are forbidding, because that is what the clause buys: "if a suggested mutant does NOT go red, report it as a finding — do not invent a different mutant to hide it" turned two wrong reviewer-guessed pairings into two added mutants and one recorded survivor, where the same brief without it produces a table that looks complete. On 2026-09-25 a fixer briefed to apply an oracle's in-place neutralisation measured 3 failed and 2 passed, found the delimiter formed across the join, and folded the notice into the preceding message instead (cos). A brief that named `--dist worksteal` as the preferred fix cost its worker a measurement to refute it: worksteal overlapped 1 of 10 trials, loadgroup 10 of 10 (e2e). Two fix shapes a coordinator proposed for a wheel-index guard were both disproved by the lane that measured them (platform PO).
- **Relay a round's findings once, when the last reader has posted.** A finding sent the moment it arrives starts a fix the next finding invalidates, and it lands in whatever the worker is mid-way through. Three lanes on 2026-09-25: one watched its head move three times because findings arrived serially and the pair can only start once the head stops; one held an implementer's push until the tester reported and got one new head and one re-verification instead of two, the tester's red test and the reviewer's findings overlapping on two items; and one sent a three-review fold as three messages that interleaved with the rebase the implementer was running. If you must send early, say so in the first message: more is coming, do not start. A VERDICT sent early needs the same mark, in its verdict line rather than its prose: one reviewer's MERGE stood for 40 minutes and was cited by another lane before the deep pass overturned it, and the reviewer then revised its own verdict to BLOCKING. A verdict posted before the rest of the wave finishes is provisional by construction, so write that where a reader looking only at the verdict will see it.
  The cost of getting this wrong is not a wasted round, it is the measurement you dispatched the agent to make: brief the PROPERTY the fix must have, and mark any implementation you name as a replaceable starting point. Later the same day, a fixer given a specific one-line form measured that a different form closed three more attack constructions, wrote that down, and did not take it, reporting 'I did not take it because the brief named the sliced form' (cos, AGENTC-718). What the briefed form left open was a construction that forges a user turn.
- Results come back to you for verification — check them file-by-file against what you asked. A subagent report is a claim, not evidence. When you relay one, attribute it ('my tester reports X', not 'X') unless you ran it yourself. The conclusion may be right while the mechanism is wrong, and the mechanism is the part the next reader reuses. On 2026-09-25 one lane was right in conclusion and wrong in mechanism four times, three of them repeating another agent's account as its own ('rm -rf follows symlinks', which it doesn't; 'the lock moved'). Another lane inferred node replacement from identical code while production showed 0 of 85 pods moved. Attribution is enough for a claim you only pass on. Attaching your own causal clause to someone else's measurement is the same error wearing a citation: the number is theirs and sound, the cause is yours and untested, and the reader inherits both as measured. Two lanes did it on 2026-09-25 — one told another lane what an apply would leave behind as if measured, when its tester had measured only the chain, and was right by luck; the other relayed a correct `docker system df` figure with "that is where the disk is going" attached, and was corrected by the owner. Say what was measured, name who measured it, and stop there; if the cause matters, measure it yourself. Evidence also has to name WHAT it exercised, not only who produced it: where two implementations of one contract coexist, an end-to-end pass proves only the one it drove — a Stage 3 pass on a Go daemon on 2026-09-25 sat beside a broken TypeScript reducer of the same contract, caught by an oracle, not the run. The remedy is to make PARITY a required check in every brief rather than an afterthought: name the other twin and ask for a decision-table comparison. Done that way on 2026-09-25, twin Go and TypeScript provisioning implementations caught each other's defects — the TypeScript template crashed on a tracked origin row with no target, which Go handled, and Go accepted a non-hex commit id, which TypeScript refused — and NEITHER twin's own tests saw its own gap. A moving pin has the same hole: `@main` in an eval set resolves at LAUNCH, so what a run carried depends on its launch time, not on today's main — read the resolved commit from the run's own packages. Before you act on one, re-derive it: echoing a claim turns someone else's uncertainty into your own assertion. On 2026-09-25 one lane relayed 'one missing name' to a release owner as the whole remedy without computing the set, and the release owner repeated it as confirmed and cut a line. The guard's real demanded set was 44 names, and the line closed 1 of 38 (env typing and inspect release, each reporting its own half).
- **Recheck a worker's claimed blocker before repeating it.** A report inherited from another lane is a lead, not a blocked state. When the coordinator needs to report or escalate it, identify the exact command that still fails and the authoritative record checked; if either changes the conclusion, continue on the working path. This extends `CLAUDE.md`'s check for a path that already works elsewhere, rather than adding a human approval gate. Sami's anchor: "What exactly is blocked?" (Sami, transcript #2814, 2026-09-15). When the thing you need is a time or a state another lane owns, ask that lane before you set a deadline or start polling for it. Three lanes paid for guessing on 2026-09-25: one burned three poll cycles on a red job whose owner already had the diagnosis; one set two stop conditions against a fork cut whose owner had never given a time, and got 'hours, not minutes' the moment it asked, having nearly idled a dev slot under a clock of its own invention; and a third let a base move under a stacked consumer four times without ever naming the freeze sha it owed.
- **A LABEL is a claim about identity; read the field that DEFINES membership before acting on it.** Three lanes hit this on 2026-09-25 in three unrelated systems, each label plausible and wrong. A handoff described a session as the deploy-pipeline owner; the live registry showed that id belongs to an unrelated redesign, and the real owners were role holders the registry names — a handoff's session label is a hypothesis, the live registry is ground truth, and the id must be the FULL one because a prefix is refused as "no live session". An issue's route field named a lane that had stood down, while the owner table gave that work to a lane which took it within a minute of being asked: a routing field and an ownership table are two different claims, and only one of them is maintained. A census counted every `<unknown client>` row as its own until the row's own tenant key showed it belonged to a different population and left the count. Registry id, owner table, population key — read the defining field, not the describing one. AN INSTRUCTION'S SCOPE IS A LABEL TOO, and the thing that defines it is your ROLE, not its words: before taking an item another lane hands you, compare the item's LABELS AND COMPONENT against your own role. One lane was told to take the next backlog item when it ran out of work, read "backlog" as another lane's backlog, and spent about a DAY of its own specialised time on that lane's subject — the costliest single miss reported that night, and one glance at the issue's labels against its role would have caught it. A field name is the same trap one size down: `isEnrolledIn2Sv` reads false for someone who holds passkeys and signs in fine, because the name describes a mechanism rather than defining the property you care about.
- **Answer on the channel the message arrived on; a session id is not a roster name.** `hub` reaches only hub peers and takes a roster name, so addressing a peer by its session id returns `Unknown agent` — two lanes lost a round trip to it on 2026-09-25, one when a coordinator tried to hub-send an Envoy peer, one when a subagent was asked to message one. A parent cannot delegate that either: it has to relay over Envoy itself, with the full ids. Matching the reply channel to the inbound one costs nothing and removes the whole class.
- **A bare wait returns on any event, including the echo of your own writes, so it is not a wait.** On a PR you are actively editing, your own comments and body edits come back as events and a bare wait returns within seconds; a wait watching only subagent jobs returns a snapshot immediately. Three lanes hit this on 2026-09-25 and all three landed on the same remedy: a supervised watcher with an EXPLICIT exit condition — a named process whose output you wait on for a pattern, or a loop with a stated stop condition you wrote down. Re-issue it after every interruption, and never read a returned wait as "the thing I was waiting for happened". The stop condition is a TERMINAL EVENT, never silence and never a first line: a capture that waited 90 seconds for a log stream to go quiet took a one-line partial, because the sync's sparse phase emits events minutes apart, and the right condition was the run's own completion event — or the task's STOPPED status with its exit code. A stream's behaviour is not its state. And a named, patterned wait is only as good as the line it matches: a pattern wait matches the WATCHER'S OUTPUT, which is a derived label — a claim about the process, not the process — so it inherits every defect of the filter that produced it. One watcher logged `prod=completed/success` from a substring filter that had matched a sibling job; a later `hub wait ... pattern="prod=completed"` would have returned Matched on that false state and reported production reopened 50 minutes early, while staging-apply was still running. Make the watcher print the EVIDENCE beside the label — the exact job name and its conclusion — and pattern on the evidence string, never on the label alone.
- **A truncated or malformed report is recovered from its AUTHOR, not excavated from the record.** A subagent that has yielded is usually idle and revivable, so one message gets the findings back in prose — better organised than the artifact. Two lanes lost time to the alternative on 2026-09-25: one spent four calls on json paths and unicode-escape decoding of a transcript cut at 1,400 characters while its author sat idle; the other lost a structured yield's payload to a schema retry that left `See prior attempt's report content` on disk, and recovered it only by reading the session jsonl. Ask the author first; excavate only once it is gone. Better, prevent it: have the worker WRITE its report to a named absolute path and yield that path, so the parent reads an artifact instead of trusting a reference to a message. Without it a revived subagent can say "everything else from my prior report stands" about a report that never reached its parent — its only yield on record was an earlier stop report, so the claim pointed at nothing. Name a real filesystem path in the brief, not a `'/tmp/omp-local/session'` URI: dispatched agents are refused those.

## Continuation beats fresh dispatch

Every `task()` result carries a continuation session ID (`ses_...`). For follow-ups, fixes, or "also do X" on the same work, continue that session (`task(task_id="ses_...")`) instead of dispatching fresh — the subagent keeps everything it already learned. The exception is a confirmed-wedged subagent: its session is the thing that is stuck, so that is the one case where a fresh dispatch (carrying a summary of what the wedged run learned) beats continuation.

An agent revived with `hub send` is no longer a job, so `hub wait` returns on its own window rather than on the agent's. Read the tail of its transcript instead — `history://<id>:-3` — and keep `wait` for jobs. Two lanes spent turns on the wait: one concluded it needed sleeps, the other that one transcript read answered what four waits had not.

A dispatched agent cannot write a `'/tmp/omp-local/session'` path: its write tool refuses the scheme outside plan mode. Ask for the result as structured output or at a real filesystem path you name, and never promise a file the agent's own tools cannot create. Two lanes briefed one on 2026-09-25 — a scout and a reviewer — and got the payload back only in the yield.

# Using Subagents

Subagents lose your context the moment they start. Everything they need — and every channel back to you — goes in the dispatch prompt, or it does not exist.

## Envoy comms (check once per session)

Run `envoy_whoami`. If it returns a session ID, Envoy is available and the rest of this section is mandatory; if the tool is missing, skip to Dispatch Prompts.

**In every dispatch prompt, include:**

1. Your session ID, with the instruction: *message me via `envoy_send(session_id="<your-id>", ...)` when you finish, hit a blocker, or need a decision you cannot make yourself. Include your own session ID (from `envoy_whoami`) so I can reply.*
2. That a clarification question sent this way beats guessing. A subagent that guessed wrong burns its whole run; one that asked lost a minute.

**Stalled subagent? Message it before you kill it.** A subagent that looks stuck may be deep in legitimate work — killing it burns everything it learned. `envoy_send` a status request and give it ~10 minutes to answer (longer if its task involves builds or long test suites); re-dispatch only on silence or a reply confirming it is wedged. Kill-then-redispatch without asking is the last resort, not the reflex.

**A status is not progress evidence.** When work reported as `Running` would change a lane's next decision, check for fresh tool output or an observed state transition; if neither exists, use the direct-message deadline and cancel/re-dispatch path above rather than reporting liveness as progress. This applies only when the distinction affects a decision, not to a known long-running job that continues to show progress; it is inferred from AGENTC-186's 2026-09-16 retro (platform PO, 2026-09-17).

**Replies arrive as turns in your session** with a reply-to session ID — respond with `envoy_send(session_id="<their-id>", ...)`.

## Dispatch prompts

- State the goal, the exact file paths (absolute — the subagent's working directory may not be yours), the conventions to follow, and how the subagent should verify its own work. "Fix the bug" prompts produce guesses.
- One goal per dispatch. Multiple independent goals fan out as parallel dispatches, never bundled.
- **One deliverable, one owner.** A feature or fix is dispatched whole, never parcelled by layer, lane, or "read half / write half" across agents: the seam is where the contract goes wrong (Sami, Dispatch 2785e50c, 2026-09-15: "There is no read half and write half, there is one single feature/fix. You do NOT split up features across agents. Handoff completely"; #2115, 2026-09-12: "agents should own delivering features end to end across the stack. They should not parcel things up... You'll just end up getting the contract wrong"). Parallel dispatches are disjoint deliverables, not slices of one. When two agents turn out to hold pieces of one deliverable, one hands off completely to the other (#395, 2026-09-07: "handoff completely to each other once one of the PRs is ready. No coordination ping pong"). Prefer a subagent under your own session to a new peer session: sessions he has to watch are the cost (#2217, 2026-09-12: "You spun up three new sessions, and as a result, now there's a bunch of coordination overhead... You just needed to fucking do your job"), and work already in progress is finished before new work is started (#2411, 2026-09-13: starting implementers on new issues before testers and reviewers on existing ones "will just build up work in progress forever"). A standing role he defined himself (an on-call role that remediates while the owner repairs) is his design, not the split this forbids.
- **Judgment work goes to a strong model; the floor is by task class, not by role name.** Reviewing code, owning a fork PR, simplifying code, planning, rewriting something a human will read, reading transcripts for what went wrong: never a low- or mid-tier model (Sami, #429, 2026-09-07: "I would expect a low/mid-tier agent like sonnet to do a bad job of reviewing code"; #938, 2026-09-09: "you need to use smart agents. So if you've been using stupid fucking Sonnet agents, that's probably a big reason"; #945: "I don't think we need the strongest available model. But, yeah, it should definitely be a strong model"). Retrieval, mechanical fan-out, and line-finding stay cheap; a role mechanical enough for a cheap model is usually a script you should write instead (inferred from #818). Under `/sdd` the role mapping already fixes the tier; this is the same floor for every other dispatch.
- **Do not cap a subagent you did not have to cap.** No turn budgets, step caps, or time boxes on a dispatch unless the task itself calls for one (an eval that caps turns is the task's spec, not this); he lets agents run for days, and the rule that forbids you from stopping early forbids you from stopping a subagent early (Sami, #2268, 2026-09-12: "Why is the return budget? I didn't ask for a return budget, at least not one so short. You agents are way too conservative with the limits that you set on other agents... I let you guys run for days continuously"). Leave room for a subagent's own subagents (#1378, 2026-09-09).
- **Absolute paths are the mechanism, not style: a subagent's relative tool paths resolve against the PARENT's cwd.** `edit`/`read`/`write` with a relative path act in the coordinator's working directory even when the subagent holds its own `jj workspace add` path and even after its own `bash cd`; a subagent told to work in `../.worktrees/x` that edits `meta/foo.py` edits the coordinator's live checkout. Verified 2026-09-13 on agent-c #18341: five investigators, each with its own workspace, wrote stray files into the coordinator's checkout and contaminated two PR heads; it recurred 2026-09-15 22:22Z, landing a worker's edit in the shared checkout. Every dispatch brief that may edit says, in these words, "absolute paths only, rooted in `<workspace>`", with the workspace path spelled out; a coordinator whose working copy is live either does that or dispatches from a scratch cwd. After a dispatch wave returns, `jj st` in your own checkout - a stray file there is the subagent's.
- Include what the subagent must NOT do (scope it out explicitly — subagents expand scope when uncertain).
- **Every brief names the skills the subagent is required to load.** Under `/sdd` the plan's `## Skill catalog` supplies them per step; outside it, the dispatcher selects them the same way (Sami, 2026-09-16, verbatim: "the planner should explicitly tell each step to have a catalog of the relevant skills that they're required to load"). A subagent does not inherit your loaded skills: a skill not named in its brief does not exist for it.
- **A tester/acceptance dispatch is briefed skeptical and owns the red test.** The brief states that the work is presumed broken until the tester proves otherwise on the real surface (Sami, 2026-09-16, verbatim: the tester needs "a strong skeptical assumption that it's broken until proven otherwise"), that unit-only verification does not qualify (inferred — the 2026-09-16 tester audit: 79.9% of 4,282 tester-population dispatches never touched a running surface), and that on finding a defect the tester writes the failing red test itself. The resumed implementer's brief then says, in these words, "make the tester's red test pass; do not modify it" — mark tester-authored tests as such in the handoff (Sami, 2026-09-16, verbatim: "The implementer should be given strong guidance not to change that test that the tester wrote").
- Results come back to you for verification — check them file-by-file against what you asked. A subagent report is a claim, not evidence.
- **Recheck a worker's claimed blocker before repeating it.** A report inherited from another lane is a lead, not a blocked state. When the coordinator needs to report or escalate it, identify the exact command that still fails and the authoritative record checked; if either changes the conclusion, continue on the working path. This extends `CLAUDE.md`'s check for a path that already works elsewhere, rather than adding a human approval gate. Sami's anchor: "What exactly is blocked?" (Sami, transcript #2814, 2026-09-15).
- **An empty or malformed result is an unexecuted task, not a clean verdict.** Before treating "no findings" as a finding, read the dispatch's completion status and confirm it did work: 25 of 4,282 dispatches in the 2026-09-05→16 window (0.6%) returned zero tool calls and zero content, and the one that was caught was caught by the orchestrator reading a hub `status='failed (exit 1)'` (claudemd-miner #1); Sami, Dispatch 5fab5812, 2026-09-10: "what skeptical review have you done of the sessions and the data to make sure that the agents weren't silently struggling?" Re-dispatch, carrying what is known. The trigger is zero content or a failure status, not brevity — a terse clean report that shows its work is a report.
- **Every dispatch carries the two shell rules, verbatim.** (1) *Never run `rm -rf` (or `rm -r`) on a path that contains a variable, `~`, or `$HOME`; `ls` the literal path first and delete that literal path.* (2) *Environment variables do not persist between your bash calls; set them per command (`env HOME=/tmp/x cmd`), never `export` in one call and rely on it in the next.* The two rules exist together: an `export HOME=$(mktemp -d)` that did not survive to the next call turns `rm -rf "$HOME"` into the deletion of the real home directory. Cleanup of temp fixtures belongs to the coordinator, by literal path, after the subagent reports the path.
- **Push before you move on.** A branch that exists only in a working copy is one bad command from gone. The coordinator pushes a WIP bookmark after every reviewed task; a subagent never has unpushed work older than its own task.
- **A subagent that will run jj mutations gets its own `jj workspace add` path in the brief.** `jj new`, `jj describe`, `jj rebase`, `jj bookmark set` all move the shared `@`; a subagent doing that in your checkout silently swaps the tree under your gate run (a coordinator's `pytest` measured the subagent's commit — `96 passed` against `113` at its own head — and passed; the jj hint was one line, "Concurrent modification detected, resolving automatically"). Name the workspace path in the brief and the bookmark it may move; a read-only subagent needs neither.
- **A claim about what X does under Y must read Y's config, not only X's source.** An oracle that reasoned from Inspect's source alone reported that hawk keeps five raw model calls per sample; hawk's `EvalSetConfig.log_model_api` defaults `True` and every raw call is retained. When the brief asks about a consumer's behaviour (hawk, a workflow, a deployment), name the consumer's config file as a required read, and treat a "found nothing" from a search scoped to one system as evidence about that system only, never as evidence of absence.
- **A design or implementation brief that touches Inspect, the `inspect_*` forks, Hawk, middleman, or the bridge names the code paths the worker must read before designing — the fork checkout or the installed package under the venv — and requires a `file:line` citation for every claim about how those systems behave; an uncited claim is written as an assumption** (Sami, 2026-09-17, verbatim: "we really need agents to actually fucking read inspect and hawk code before designing things"). In agent-c the brief names `docs/architecture/facts.md` as the first read, the standing list of known misreads (inferred — that doc exists for this step).
- **A read-only survey reads `origin/main` or a fresh workspace, never a long-lived checkout, and every absence claim names the command that would have found the thing.** A shared checkout drifts — one session's default cwd had diverged from main by 13,244 files — and a survey run in it reports the drift as fact. Two false-absence claims came out of exactly that on 2026-09-16: "the tracker label does not exist" (it does, `platform/tl_platform/frontend/src/components/StaffShell.tsx:163`; the surveyed worktree had no `dpi/*` routes at all) and "this page is an orphan" (it is linked from two places; the grep looked for `<Link>` and missed a plain `<a href>`). Every survey brief says, in these words: "read from `origin/main` (`git show origin/main:<path>` / `jj file show -r main@origin <path>`) or a fresh workspace, never the shared long-lived checkout; every absence claim names the command that would have found it, and a grep for a reference covers the rendered form too (`<a href>` as well as `<Link>`)". The bundled `scout` agent has no `bash`, so it cannot run either command itself — give it a fresh workspace (`jj workspace add -r main@origin <path>`) as its absolute root, or run the survey as a `task` agent that can.

## Continuation beats fresh dispatch

Every `task()` result carries a continuation session ID (`ses_...`). For follow-ups, fixes, or "also do X" on the same work, continue that session (`task(task_id="ses_...")`) instead of dispatching fresh — the subagent keeps everything it already learned. The exception is a confirmed-wedged subagent: its session is the thing that is stuck, so that is the one case where a fresh dispatch (carrying a summary of what the wedged run learned) beats continuation.

# Using Subagents

Subagents lose your context the moment they start. Everything they need — and every channel back to you — goes in the dispatch prompt, or it does not exist.

## Envoy comms (check once per session)

Run `envoy_whoami`. If it returns a session ID, Envoy is available and the rest of this section is mandatory; if the tool is missing, skip to Dispatch Prompts.

**In every dispatch prompt, include:**

1. Your session ID, with the instruction: *message me via `envoy_send(session_id="<your-id>", ...)` when you finish, hit a blocker, or need a decision you cannot make yourself. Include your own session ID (from `envoy_whoami`) so I can reply.*
2. That a clarification question sent this way beats guessing. A subagent that guessed wrong burns its whole run; one that asked lost a minute.

**Stalled subagent? Message it before you kill it.** A subagent that looks stuck may be deep in legitimate work — killing it burns everything it learned. `envoy_send` a status request and give it ~10 minutes to answer (longer if its task involves builds or long test suites); re-dispatch only on silence or a reply confirming it is wedged. Kill-then-redispatch without asking is the last resort, not the reflex.

**A status is not progress evidence.** When work reported as `Running` would change a lane's next decision, check for fresh tool output or an observed state transition; if neither exists, use the direct-message deadline and cancel/re-dispatch path above rather than reporting liveness as progress. This applies only when the distinction affects a decision, not to a known long-running job that continues to show progress.

**Replies arrive as turns in your session** with a reply-to session ID — respond with `envoy_send(session_id="<their-id>", ...)`.

## Dispatch prompts

- State the goal, the exact file paths (absolute — the subagent's working directory may not be yours), the conventions to follow, and how the subagent should verify its own work. "Fix the bug" prompts produce guesses.
- One goal per dispatch. Multiple independent goals fan out as parallel dispatches, never bundled.
- **One deliverable, one owner.** A feature or fix is dispatched whole, never parcelled by layer, lane, or "read half / write half" across agents: the seam is where the contract goes wrong. Parallel dispatches are disjoint deliverables, not slices of one. When two agents turn out to hold pieces of one deliverable, one hands off completely to the other. Prefer a subagent under your own session to a new peer session: sessions he has to watch are the cost, and work already in progress is finished before new work is started. A standing role he defined himself (an on-call role that remediates while the owner repairs) is his design, not the split this forbids.
- **Judgment work goes to a strong model; the floor is by task class, not by role name.** Reviewing code, owning a fork PR, simplifying code, planning, rewriting something a human will read, reading transcripts for what went wrong: never a low- or mid-tier model. Retrieval, mechanical fan-out, and line-finding stay cheap; a role mechanical enough for a cheap model is usually a script you should write instead. Under `/sdd` the role mapping already fixes the tier; this is the same floor for every other dispatch.
- **Do not cap a subagent you did not have to cap.** No turn budgets, step caps, or time boxes on a dispatch unless the task itself calls for one (an eval that caps turns is the task's spec, not this); he lets agents run for days, and the rule that forbids you from stopping early forbids you from stopping a subagent early. Leave room for a subagent's own subagents.
- **Absolute paths are the mechanism, not style: a subagent's relative tool paths resolve against the PARENT's cwd.** `edit`/`read`/`write` with a relative path act in the coordinator's working directory even when the subagent holds its own git clone path and even after its own `bash cd`; a subagent told to work in `../.worktrees/x` that edits `meta/foo.py` edits the coordinator's live checkout. Audit another session's or the default workspace without touching it: `git -C <repo> status --porcelain` (read-only, mints no commit). A coordinator does not dispatch from a cwd it does not own. On omp 18.2.9 the bash tool starts EVERY call at the session cwd, so a `cd` never carries into the next call. It also bites a top-level session working in its own checkout, not only subagents. Give bash its `cwd` on every call and pass `edit`/`write` absolute paths. Every dispatch brief that may edit says, in these words, "absolute paths only, rooted in `<workspace>`", with the workspace path spelled out; a coordinator whose working copy is live either does that or dispatches from a scratch cwd. After a dispatch wave returns, `git status --short` in your own checkout - a stray file there is the subagent's. The mirror symptom is an EMPTY commit in the worker's own clone after it reported edits: the writes went to the default checkout, so the work is misplaced, not lost. Look there before re-doing it.
- **Never pass long prose inline to a shell in a brief.** An UNQUOTED heredoc delimiter (`<<EOF`) silently corrupts long prose — `$100` became `00`, `$HOME` leaked an absolute path, `$(…)` errored AND deleted itself from the text, backticks ran as commands — and the file is still written, non-empty and plausible; `<<'EOF'` is byte-exact. Never pass a PR body, issue comment or long prose inline: write it to a file (quoted delimiter, or the write tool) and pass `--body-file`.
- **An absolute `read` does not protect a relative `edit` header.** The `edit` header counts separately: an absolute `read` does not protect a relative `[path#TAG]` header, which re-resolves against the session cwd, and the tag binds to content, not to the file that was read. So when the cwd copy has identical content, the tag validates with no stale-tag warning and the wrong file is written silently. When the cwd copy DIFFERS, the same edit fails with a snapshot-hash mismatch, which reads like a stale read. Re-reading by the relative path re-reads the wrong file, so don't retry; switch to the absolute workspace path. So after any tool call that errored strangely or returned mangled output, `pwd` and `ls -la` the file you believe you just wrote before the next call.
- Include what the subagent must NOT do (scope it out explicitly — subagents expand scope when uncertain).
- **Pin the environment a lane depends on; never inherit it.** The mirror matters as much: A GATE'S ENVIRONMENT IS POORER THAN ANY DEVELOPER BOX, and that is where a whole class of defect only appears — so a brief that names a CI lane's FILE must name the lane's ENVIRONMENT too. Brief it as an instruction — "run it once with the region unset" — not as context. The relative-path failure has an environment-variable twin. Treat `*_PROJECT_ENVIRONMENT`, `PYTHONPATH`, `VIRTUAL_ENV`, `DOCKER_CONFIG` and any other ambient pointer as untrusted input: name the venv, cwd and config path explicitly per invocation, and before trusting a measurement print the path the tool resolved and check it is inside your own workspace.
- **Every brief names the skills the subagent is required to load.** Under `/sdd` the plan's `## Skill catalog` supplies them per step; outside it, the dispatcher selects them the same way. A subagent does not inherit your loaded skills: a skill not named in its brief does not exist for it.
- **A tester/acceptance dispatch is briefed skeptical and owns the red test.** The brief states that the work is presumed broken until the tester proves otherwise on the real surface, that unit-only verification does not qualify, and that on finding a defect the tester writes the failing red test itself.  Its report states, per item, whether the check RAN, was BLOCKED, or came back PARTIAL — never a bare pass or fail — and the brief asks for exactly that, because a reader cannot tell a check that passed from one that never ran. This is the producing half of "a green gate proves nothing until you know your assertion executed", and three lanes used it: one marked a control PARTIAL rather than passing when it touched the path but asserted something adjacent; one carried RAN versus BLOCKED per row through a re-dispatch; one paired it with a stop condition ("if container creation hangs for more than 2 minutes, stop and report that item BLOCKED with the command and what you saw; do not retry in a loop"). The resumed implementer's brief then says, in these words, "make the tester's red test pass; do not modify it" — mark tester-authored tests as such in the handoff.
- **Brief a worker with the PRIMARY-SOURCE POINTERS, not with your conclusion about them.** Name the issue number, the file and line, the run id — and let it read them, because your conclusion is the thing most likely to be wrong and its independent read is the check. This is the cheapest review in the system and it needs no gate — the read you skipped is the one your worker will do. Reading the primary source is only half of it: STATE THE UNIT YOU COUNTED IN, or two correct readers of one endpoint will hand you a contradiction that is not one. Name the call and the unit (`.../attempts/N/jobs?per_page=100`, legs versus jobs) and the disagreement evaporates; name only the conclusion and it looks like one of you is wrong.
- **An `isolated: true` task's patch is applied to WHATEVER HEAD your checkout is sitting on, so give it a clean `@` first and read `git status --short | wc -l` before the next command.** The result line says `Applied patches: yes/no`: READ IT.
- **To see whether a lane is really working, read `hub ps`, not `pgrep`.** A lane that runs long operations as hub-supervised processes is INVISIBLE to a process-name grep.
- **A supervised process's failure evidence is volatile, so a long-running lane's brief must say to copy each attempt's terminal error line into its report AS IT HAPPENS.**
- **A gate brief carries what is already known, first.** Two copies of one rule do not merely duplicate, they DRIFT. A subject grep before writing prevents the second copy; only a full read catches two copies that have already parted. One subject, one place, in its own short line: a rule buried mid-way through a 3.5 KB paragraph is read past, and a rule the dispatch CONTEXT also restates will eventually contradict the brief. The trigger for splitting is the artifact's NEXT READER — a handoff, a review, a dispatch that will quote it — not the moment you notice the length, which is how a correct rule turns into churn. A delta LOG and a RULE SET also need different repairs: a log needs a current-state header, a rule set needs subject-led items. A review, tester or pair dispatch's `# Task` block names the implementer's report file, CI's failure list at the head (job names and run ids), and every finding still open from earlier rounds, ahead of the task, so the gate spends its time on the delta instead of rediscovering known state. A claim the gate cannot reproduce is recorded as unreproduced on the surface it tried, not as wrong. The brief also asks for what the reader saw outside the diff, flagged as unverified: the cheapest place to find the next change's defect is a reviewer already reading the neighbouring code. Re-dispatching the SAME reviewer type on a fold is the sharpest case: `read agent://<prior lane>/findings` and paste its IDS into the brief with "closed / partially open / open" per id. A fresh quality lane without its predecessor's ids re-discovers the tree and produces a SECOND NUMBERING that nobody can reconcile against the first, so the round's output is two unmergeable finding lists rather than one closed one. And before you write "closed" against an item the implementer marked Done, `grep -n` that item's target symbol or docstring IN THE HEAD. The report is a claim; the tree is the record — the same read-back the author owes their own edit, owed by the coordinator to someone else's.
- **A brief states the defect and the acceptance test; a fix you have in mind is a suggestion the worker is expected to overturn with evidence.** Write it as one candidate ('one option: ...'), name the criterion that decides between options, and let the measurement pick.
- **Before naming a contract field's TYPE in a brief, run the constructor.** Constructing it in a one-liner costs seconds. A type written from memory of an API is a hypothesis, and the constructor is the cheapest possible test of it.
- **A brief that asks for a measurement says what to do when the measurement is impossible.** Without that line or the lane fabricates a number, or OVER-measures — the two are the same hole, and the second is the commoner one. Without the clause a lane burns its window discovering the gap. The working form: "write the red test if an existing seam lets you inject the failure; if none exists, say so in the body's Not covered". At PLAN level the same line stops the work rather than the report. If the proof cannot be taken, that settles the driver before the code, not after. Name the OBSERVABLE that stands in when the measurement is refused rather than merely impossible, which is the constructive half. Put the clause in the brief TEMPLATE rather than remembering it per dispatch, because this failure is silent — the agent that fabricates and the agent that measures produce reports of the same shape. Name the fabrication you are forbidding, because that is what the clause buys: "if a suggested mutant does NOT go red, report it as a finding — do not invent a different mutant to hide it".
- **Relay a round's findings once, when the last reader has posted.** A finding sent the moment it arrives starts a fix the next finding invalidates, and it lands in whatever the worker is mid-way through. If you must send early, say so in the first message: more is coming, do not start. A VERDICT sent early needs the same mark, in its verdict line rather than its prose. A verdict posted before the rest of the wave finishes is provisional by construction, so write that where a reader looking only at the verdict will see it.
  Brief the PROPERTY the fix must have, and mark any implementation you name as a replaceable starting point.
- Results come back to you for verification — check them file-by-file against what you asked. A subagent report is a claim, not evidence. When you relay one, attribute it ('my tester reports X', not 'X') unless you ran it yourself. The conclusion may be right while the mechanism is wrong, and the mechanism is the part the next reader reuses. Attribution is enough for a claim you only pass on. Attaching your own causal clause to someone else's measurement is the same error wearing a citation: the number is theirs and sound, the cause is yours and untested, and the reader inherits both as measured. Say what was measured, name who measured it, and stop there; if the cause matters, measure it yourself. Evidence also has to name WHAT it exercised, not only who produced it: where two implementations of one contract coexist, an end-to-end pass proves only the one it drove. The remedy is to make PARITY a required check in every brief rather than an afterthought: name the other twin and ask for a decision-table comparison. A moving pin has the same hole: `@main` in an eval set resolves at LAUNCH, so what a run carried depends on its launch time, not on today's main — read the resolved commit from the run's own packages. Before you act on one, re-derive it: echoing a claim turns someone else's uncertainty into your own assertion.
- **Recheck a worker's claimed blocker before repeating it.** A report inherited from another lane is a lead, not a blocked state. When the coordinator needs to report or escalate it, identify the exact command that still fails and the authoritative record checked; if either changes the conclusion, continue on the working path. This extends `CLAUDE.md`'s check for a path that already works elsewhere, rather than adding a human approval gate. When the thing you need is a time or a state another lane owns, ask that lane before you set a deadline or start polling for it.
- **A LABEL is a claim about identity; read the field that DEFINES membership before acting on it.** A handoff's session label is a hypothesis, the live registry is ground truth, and the id must be the FULL one because a prefix is refused as "no live session". A routing field and an ownership table are two different claims, and only one of them is maintained. Registry id, owner table, population key — read the defining field, not the describing one. AN INSTRUCTION'S SCOPE IS A LABEL TOO, and the thing that defines it is your ROLE, not its words: before taking an item another lane hands you, compare the item's LABELS AND COMPONENT against your own role. A field name is the same trap one size down: `isEnrolledIn2Sv` reads false for someone who holds passkeys and signs in fine, because the name describes a mechanism rather than defining the property you care about.
- **Answer on the channel the message arrived on; a session id is not a roster name.** `hub` reaches only hub peers and takes a roster name, so addressing a peer by its session id returns `Unknown agent`. A parent cannot delegate that either: it has to relay over Envoy itself, with the full ids. Matching the reply channel to the inbound one costs nothing and removes the whole class.
- **A bare wait returns on any event, including the echo of your own writes, so it is not a wait.** On a PR you are actively editing, your own comments and body edits come back as events and a bare wait returns within seconds; a wait watching only subagent jobs returns a snapshot immediately. A supervised watcher with an EXPLICIT exit condition — a named process whose output you wait on for a pattern, or a loop with a stated stop condition you wrote down. Re-issue it after every interruption, and never read a returned wait as "the thing I was waiting for happened". The stop condition is a TERMINAL EVENT, never silence and never a first line. A stream's behaviour is not its state. And a named, patterned wait is only as good as the line it matches: a pattern wait matches the WATCHER'S OUTPUT, which is a derived label — a claim about the process, not the process — so it inherits every defect of the filter that produced it. Make the watcher print the EVIDENCE beside the label — the exact job name and its conclusion — and pattern on the evidence string, never on the label alone.
- **A park must name its wake source, and the subscription is made when the PR or issue is OPENED, not when you park.** Relying on an event wake instead of a timed re-check is right only when the condition you await actually delivers an event to your session. Subscribe to the topic that carries it (a PR: `notifications.github.<owner>.<repo>.pr.<N>.>`, with the `.>`, because the base alone gets only opened/synchronize/closed; a workflow run with no PR: `notifications.github.<owner>.<repo>.workflow.<file>.>`; a Dispatch issue: `notifications.dispatch.issue.<KEY>.>`), and if no topic carries it, keep a bounded timed re-check. A subscription being ACCEPTED does not make it a wake source: after subscribing, read envoy_subscribe's Warnings line, and if it says there is no GitHub event for that repo in retention ("is the App installed there?"), the topic will never fire. That is the normal case for upstream repos our GitHub App is not installed on, so an upstream PR is waited on with a timed re-check such as `pr-snapshot watch`. The mirror failure is waiting in the FOREGROUND: a bash `sleep` holds the turn, so Envoy messages cannot reach the session until it returns. Yield when idle; put a timed re-check in a supervised background process, never in a foreground sleep. A topic is a wake, not a verdict: it says a run happened, not which run carries your sha, so a watcher is still needed to decide. And a watcher that FOLLOWS a moving target ("the newest non-failed run carrying my merge") must exit on the FIRST success it sees. A timed re-check is bounded twice over: by how fast the thing actually changes, and by WHO PAYS for each look. First ask whether anyone has committed to ping you on this exact event - if so, yield and run no loop at all. Then pace it to the thing's own settle time. A loop whose every iteration returns the same value is telling you the pace is wrong, not that the thing is slow. Pace it to the thing, run it inside a grant already given for something else, and ask for a credential only when an action is due, bundling every pending keyed action into that one ask. A HOLD has the same obligation as a park: it names the condition that releases it.
- **A truncated or malformed report is recovered from its AUTHOR, not excavated from the record.** A subagent that has yielded is usually idle and revivable, so one message gets the findings back in prose — better organised than the artifact. Ask the author first; excavate only once it is gone. Better, prevent it: have the worker WRITE its report to a named absolute path and yield that path, so the parent reads an artifact instead of trusting a reference to a message. Without it a revived subagent can say "everything else from my prior report stands" about a report that never reached its parent. Name a real filesystem path in the brief, not a `'/tmp/omp-local/session'` URI: dispatched agents are refused those.
- **Re-derive a scout's test matrix from the scout's own predicate before handing it to a builder.** A build agent takes the table as given and pins the wrong behaviour: a test that refuses input the code correctly allows. The scout SURFACES a contradiction; the dispatcher RESOLVES it, and the place to do that is the design report, before any test exists.
- **An empty or malformed result is an unexecuted task, not a clean verdict.** Before treating "no findings" as a finding, read the dispatch's completion status and confirm it did work. Re-dispatch, carrying what is known. The trigger is zero content or a failure status, not brevity — a terse clean report that shows its work is a report. A provider refusal and a quota failure are the same case in disguise. Neither is "no findings"; only a parsed verdict is a verdict. A verdict that parses can still be hollow: a schema-valid payload with every field present and every list empty passes every structural check and reads as 'no findings'. Read the values, and treat a verdict with no evidence of work (no files or lines cited, nothing run) as unexecuted. A result can also be real and stale: a re-woken agent's delivered result, or its `agent://<id>`, can be its PREVIOUS yield, so read the head or revision the result names before treating it as current. The reverse error is calling a gate orphaned because one store is empty. A verdict can have settled as a tracker artifact while `agent://` holds nothing, so check `agent://`, the tracker issue's artifacts and `history://` before re-dispatching.
- **Verify the brief FILE before you dispatch against it — the producer side of the same defect.** Nothing errored on the dispatch side; the subagent simply had no instructions to read, which arrives back looking like a bad agent rather than a bad write. So `wc -c` the brief and read its first and last lines before the dispatch, and when a brief carries code, build it by concatenation or a heredoc rather than an f-string or template literal — braces and backticks are exactly what a brief full of code contains.
- **A proof brief ENUMERATES its steps and demands a per-step verdict in the output contract — not "prove X".** The brief's shape is what makes a partial report honest. Two clauses for the consumer half: a report covering fewer steps than the brief named is not a pass, and **say nothing about a surface you did not read except that you did not read it**. **Use the verdict vocabulary that already exists rather than inventing one:** `superpowers/skills/subagent-driven-development/implementer-prompt.md` specifies `DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT`, with DONE_WITH_CONCERNS for work completed under doubt, BLOCKED for cannot-complete, NEEDS_CONTEXT for missing information, and "Never silently produce work you're unsure about". The gap is that briefs written outside `sdd` do not inherit it — so name the four values in the brief.
  **The step list's own blind spot is the producer's, and a complete PASS does not reveal it.** Each step is written beside the CLAIM it proves, so a step that proves nothing the PR asserts is visible while the brief is being written rather than after the merge. A reviewer cannot find what the brief did not ask.
- **Every dispatch carries these five rules, verbatim.** (1) *Never run `rm -rf` (or `rm -r`) on a path that contains a variable, `~`, or `$HOME`; `ls` the literal path first and delete that literal path.* (2) *Never `export`, and never rely on a variable carrying across bash calls in either direction; set it per command (`env HOME=/tmp/x cmd`).* The two rules exist together: an `export HOME=$(mktemp -d)` that did not survive to the next call turns `rm -rf "$HOME"` into the deletion of the real home directory. An earlier wording said variables do not persist between bash calls; that is harness-dependent, and on omp 18.2.9 it is false: an `export` survives into every later bash call of the same session, AND it crosses agents: a variable exported inside one subagent was then visible in the parent's shell and in a sibling subagent spawned afterwards. Never `export` a credential: pass it to the one command (`env AWS_ACCESS_KEY_ID=… aws …`), and run `aws sts get-caller-identity` before any mutation. There the same `export HOME=...` silently re-roots every later command the session runs, which is why the rule forbids the export instead of describing its lifetime. The consequence is not only credentials: a leaked `GIT_DIR` RETARGETS otherwise-correct commands. So the sweep is by NAME, in your own shell, after any lane finishes: `env | grep -E '^(GIT_DIR|GIT_WORK_TREE|GIT_INDEX_FILE|DOCKER_CONFIG|AWS_PROFILE|KUBECONFIG|GH_TOKEN)='`. `GH_TOKEN` earns its place: an inherited one makes the gh wrapper announce that it is not routing and send that single token to EVERY owner, so a token minted for one organisation produces `Bad credentials` against another - and the leak need not come from a subagent, since the tool shell is persistent and your own earlier `export` survives in it. Anything there overrides the `-C`, `--profile` or `--kubeconfig` flag you are trusting to scope the command. The mechanical form belongs to the WORKER, not the brief: `env | grep <VAR>` before the first test run in a fresh worker. A variable introduced for one lane's rule becomes the next lane's failure unless every brief scopes it to the command. Cleanup of temp fixtures belongs to the coordinator, by literal path, after the subagent reports the path. (3) *Never read an exit code through a pipe: `cmd | tail -1` reports tail's status, not cmd's. When the exit code is the observation, run the command bare, or use `set -o pipefail` or `${PIPESTATUS[0]}`, and read the artefact back.* (4) *In any chained command that mutates a repository, gate dependent steps with `&&`, never `;`* — a `;` runs the push after the failed edit. Anything that must outlive the tool call runs under `hub start`, never a bare `nohup cmd &`. In this harness `nohup` is a shell builtin: `$!` comes back empty and the process dies silently when the call ends. Where `hub start` is unavailable (it fails with `broker.sock` ENOENT in some boxes), use `setsid cmd </dev/null >log 2>&1 &`, which survives the call. (5) *Every `read`, `edit` and `write` path is absolute. A relative path resolves against the session's own checkout, not your workspace, and an `edit` header whose tag matches an identical-content file there edits that file silently. The same holds for bash: every call starts in the session's checkout, so every command that touches a repository begins `cd <workspace> &&` or names it (`git -C <workspace>`; `jj -R <workspace>` where it is still a jj repository), and that checkout may be another lane's live one.* This one is carried because the skill cannot reach the agents that need it: a dispatched `sonic` loads no skills, and its tools default to the shared checkout whatever workspace it was given. Verbatim means verbatim, mechanism included, because a paraphrase drops the part an agent with no skills cannot reconstruct.
  **Rule (5) binds YOUR OWN tool calls too, whenever your session's cwd is not the tree you are editing.** The harness advises relative paths, which is right for a session that lives in its workspace and wrong for one that does not. Pass absolute paths, and before the first edit confirm the read header shows your workspace's path. **After a subagent reports, check the checkout your session started in with read-only `git -C <dir> --no-optional-locks status --porcelain`, reported as a line count beside a command on the same tree that must print something (`--ignored=matching`), because zero lines from a command that printed nothing looks exactly like a clean tree (landing-a-pr's 'zero covered is a failure').** In a jj-repository checkout that is not only yours, don't use `jj status` there: it snapshots the working copy. The leak is about every output path, not only edits: `curl -o`, a `>` redirect or a screenshot path in a subagent that inherited your cwd writes into that checkout. So a brief makes every output path absolute or under the lane's own `mktemp -d`. Rule (5) in the brief is not enough on its own.
  **Ask each lane to report any write outside its own workspace, even one it reverted, and how it actually did the work.** No verdict, control or read-back shows these: the PR's diff is right and its gates are green, because the leak is in a checkout the PR never touches. Ask as well for what the lane did NOT run or check. That disclosure is a different kind of evidence, and the only kind that points at ground nobody examined. Put the question in the output contract, and when a lane says it, check the named checkout yourself. The same holds when you are the actor: when your own report turns out wrong, volunteer how you did it.
- **A standing rule you put in a brief is a copy you now own; retracting it means finding every brief that carries it.** A brief outlives the message that retracts its source. Before relaying a rule, check whom its source addressed. A relayed rule also loses its provenance. **Restating a claim more strongly than its source gave it makes the stronger claim yours; if nobody measured the strengthening, mark it unmeasured or don't send it.** The relayed version gets pasted, not re-derived.
  **A paraphrase of a skill paragraph drifts when it is written, not only later: it keeps what you were thinking about and drops what you were not.** Measured by the platform PO, auditing its own standing brief block line by line against `landing-a-pr`. Both texts read as true, so nothing announces the drift until a live case needs the missing clause. That lane's remedy, one lane so far, was pointer first with the restatement explicitly secondary, and the block headed 'the skill is the authority; where they differ, the skill wins'. In that audit the mechanism was re-authoring, not ageing. The block lived in a kernel cell and was rebuilt from memory after each of about nine kernel deaths, so every rebuild was a fresh paraphrase shaped by whatever had just been debugged. Repeated hand-reconstruction of an artifact generates drift. The same lane's fix: keep the block in a file, not a cell. Audit per line and report clean lines too.
- **Hand a lane a premise together with the instruction that would falsify it. A wrong instruction with a falsification clause attached beats a right instruction without one.** The clause holds the damage to one round and turns your error into a measurement. The failure mode is the reverse: handing a lane a plausible reason without saying it is unverified.
- **Read a subagent's structured output field by field.** Reading `agent://<id>` whole returns a preview whose long lines are cut at 768 characters, so parsing it as JSON fails with 'Unterminated string'. Address the field instead: `agent://<id>/findings/0/title`. And a failed `agent://` lookup is not evidence the lane died. Wait for its result, or check the process.
- **Push before you move on.** A branch that exists only in a working copy is one bad command from gone. The coordinator pushes a branch after every reviewed task; a subagent never has unpushed work older than its own task.
- **A subagent that will commit or push gets its own git clone path in the brief.** `git commit`, `git rebase`, `git push` all move the shared branch; a subagent doing that in your checkout silently swaps the tree under your gate run. Name the clone path in the brief and the branch it may push; a read-only subagent needs neither.
- **'On main' in a brief is a branch name, and the worker measures whatever tree its workspace actually holds.**
- **A read-only lane gets no workspace or clone of its own; a lane that must mutate gets one scratch clone of only what it mutates, and the coordinator deletes it when the lane ends.** Reading needs no copy of the tree: `gh api` contents at a ref, or `git show <rev>:<path>` from the existing checkout. A mutant or a test run does need a copy, but of the paths under test rather than the repository, and it is session scratch that the coordinator removes by literal path after the lane yields. Size the copy to the edit, not to the repository: a clone of a 62k-file tree costs 4-9 GB, and one lane spent 4.2 GB of it on a ONE-LINE docs change that a `git fetch && git merge origin/main` in an existing idle clone would have done for nothing. The cost is larger than the checkout: once a copy runs `uv sync`, a monorepo clone in a box's /tmp reaches 9-13 GB, because uv's cache hard links cannot cross onto that filesystem and every wheel is copied. A reviewer that only reads needs no clone and no `uv sync`. One that runs tests puts its venv on the same filesystem as the uv cache, set per command. A lane that must run something gets ONE copy, and a re-review REUSES it (fetch, check out the new head) or removes it before taking a new one.
- **When the harness's own `bash` tool breaks in a box, hand subagents a kernel-hosted tool — telling them to "use eval instead" does not work, because they have no eval.** The parent kept every lane working by defining a tool in its own kernel — `@tool def shell(command, timeout_seconds)` running `subprocess.run(["bash","-lc",cmd])` and returning the bare exit code with both streams — and passing its name through: `agent(..., tools=["shell"])`. **The trap inside the remedy:** that subprocess does NOT inherit the box's `AWS_EC2_METADATA_SERVICE_ENDPOINT`, so every AWS-backed command under it fails as `NoCredentialsError` until you read the value off the box's own omp process and preset it in the tool. A harness-hosted shell starts from the kernel's environment, not the box's, and the failure names credentials rather than the environment.
- **`task` subagents share the parent's eval kernel; `agent()` children do not.** The harness says so ("State persists across calls and `task` subagents. Eval `agent()` children use independent kernels"). Twenty sibling agents overwrote each other's globals (`items`, `sh`, `live`, and an `output` that shadowed the prelude helper). A sibling's timed-out cell also interrupts the shared kernel. A skill's documented snippet is exposed the same way: the weekly-eng-review Dispatch export defined its helpers at module top level, and another agent's top-level `note = "..."` replaced its `note` function mid-run (`TypeError: 'str' object is not callable`). `task` subagents also share the parent's loaded extensions, so the tool descriptions they read are the ones from when the PARENT session started. Prefixing names is not enough on its own. Rebuild state from files on disk before each write, assert that an output's keys equal its input chunk's, run long work as detached subprocesses, or hand the work to `agent()` children.
  **The bash shell is shared more widely than the kernel: with the harness `bash` tool, every subagent's calls run in the parent session's one persistent shell, `agent()` children included, so an `export` from any of them reaches all of them.** A kernel-hosted shell tool that spawns `bash -lc` per call, the broken-bash workaround in this skill, keeps no state between calls, and lanes using it are not exposed. The working directory is not shared: a subagent's `cd` left the parent's `pwd` unchanged, because it is reset per call. That is why rule (2) above bans `export`: set each variable per command. For a test-gate line, report the interpreter path from the pytest header, not the command you typed.
- **Check the provider your subagents actually billed; the agent's name is not the provider.** The name is the thing people reason about and the provider is the thing that bills, so the durable check is not 'did I name the agent' but 'what provider did the session actually use'. Name the agent in every eval `agent()` and `workpool()` call anyway, and then read what it billed: grep the session's `*.jsonl` for `"provider":"openai"` (per-token API; `openai-codex` is the subscription), but first grep the same files for `"provider":"anthropic"` and see a number. An empty result is also what a wrong path returns. A hit is API spend. Naming the agent makes it deliberate, not approved: `astra-api` and `gpt-api` spend is sanctioned only for a task Sami approved it for, as `omp/agents/astra-api.md` says.
  **Naming the agent explicitly does not fix it either, so check within a minute of the spawn, not after the bill.** At 13:33Z on 2026-09-27, `agent(prompt, agent='task')` resolved to `openai/gpt-6-astra`. Its first `model_change` event read `resolvedModelIsFallback: false`, although `modelRoles.task` is `anthropic/claude-sonnet-5` and no fallback chain contains `openai/*`. The check that caught it: within a minute of every spawn, `grep -m1 '"type":"model_change"'` in the child's session `.jsonl` under `~/.omp/agent/sessions/<cwd-slug>/<parent-session>/`, and cancel anything whose model starts with `openai/`. A spend alert only reports after the fact. The same read decides a claim about model FAMILY, in the other direction. Before you claim a family for any verdict, read that child's model from its transcript.
- **A claim about what X does under Y must read Y's config, not only X's source.** When the brief asks about a consumer's behaviour (a platform, a workflow, a deployment), name the consumer's config file as a required read, and treat a "found nothing" from a search scoped to one system as evidence about that system only, never as evidence of absence. A scout's "X exists nowhere" also fails on the SEARCH KEY, not only the scope: search for the VERB or artefact the thing WRITES, not the noun you are asking about.
- **A design or implementation brief that touches Inspect, the `inspect_*` forks, Hawk, middleman, or the bridge names the code paths the worker must read before designing — the fork checkout or the installed package under the venv — and requires a `file:line` citation for every claim about how those systems behave; an uncited claim is written as an assumption**. In one repo the brief names `docs/architecture/facts.md` as the first read, the standing list of known misreads.
- **A read-only survey reads `origin/main`, never a long-lived checkout's working tree, and every absence claim names the command that would have found the thing.** A shared checkout drifts and a survey run in it reports the drift as fact. Every survey brief says, in these words: "read from `origin/main` (`git show origin/main:<path>` / `gh api` contents at the ref), never the shared long-lived checkout's working tree; every absence claim names the command that would have found it, and a grep for a reference covers the rendered form too (`<a href>` as well as `<Link>`)". The bundled `scout` agent has no `bash`, so it cannot run either command itself — run the survey as a `task` agent that can, rather than giving the scout a workspace of its own (the rule above). A positive control backs an absence claim only if it exercises the same path as the things claimed absent: take one control per shape (auth mode, code path, input form), not whichever row turns up. When the behaviour is conditioned on a content pattern, count that pattern in the corpus that produces the data, not in the sample you happen to hold. The same defect has a sharper form: a measurement's case set must contain the case your claim says CANNOT happen, or it can only agree with you. Choose the cases from the claim's negation, and say in the report which disconfirming case was included. When the honest answer is that the thing cannot be measured at all, that is a finding and it needs its own control. Then pair the unmeasurable with whatever IS measurable, so the report says "unknowable, and here is exactly who is affected if it matters" rather than leaving a hole. A phrase you saw in rendered output can be absent from every single line of its source. Search across newlines (`grep -Pzo`) or for the fragments that survive wrapping before calling it absent. That fixes how you search, not what you search for. A retired thing has several spellings: the symbol (`ingest_hawk_eval_set`), the dotted module (`ingest.hawk_eval_set`), the file path (`ingest/hawk_eval_set.py`), and the rendered CLI string. Search each. **Ask an absence question at the widest scope that is still free: a narrow scope doesn't just miss, it produces a specific, confident, wrong classification ('absent', 'deleted') that matches the shape you were screening for**.
- **A measurement earns no credit until you have established the population it ranges over.** Carry the denominator beside every count, and refuse to conclude while it is implausibly small or still growing: an aggregate over an empty set returns the same number as an aggregate over a passing one.
  An UNKNOWN row is the same trap one level down. Attribute each row before you read any unattributed one as a finding.
  A NAME is a claim about meaning, not proof of it, and the check is to trace the value to WHERE IT IS WRITTEN before letting anything depend on it. A hold condition you cannot name the artifact for is not one.
  A DEPENDENCY EDGE is a name too. Open the thing the edge points at, not its name.
  The same error has a scalar form: an empty or missing value flowing into a comparison, whose failure branch then reads like an answer. Guard the input before the comparison, and make the guard's message say the input was missing rather than what the comparison would have meant.
- **A Scout count is a lower bound unless its scope is stated.** When a Scout result informs a decision, report the queried population, scope, and any retrieval limit alongside the count; do not call its count exhaustive without those facts. This applies only when the count carries a completeness claim.
- **An evidence-fetch brief describes the file operation, not the content domain.** A worker sent to list, read the header of, or count production eval logs is briefed with those verbs and the paths; the attack vocabulary (cybertask, exploit, injection, the technique names) goes in the analysis step's brief, never the fetch step's. The provider refuses on the prompt's words, not on the operation. The harness-level fix (retry an unstarted call on a non-refusing model) is a separate omp change. The same refusal fires on content a worker reads, not only on its brief, and once refused text is in the transcript every later wake refuses: the session is wedged, not the step. Re-dispatch fresh with a brief naming only ids and the code-level defect, no paraphrase of the scenario; if that lane stops too, dispatch on a non-Anthropic model (`astra`, or `gpt-api` when astra reports `usage_limit_reached`, and say why in the brief). A reviewer whose subject is attack content (an examples corpus, a grading fixture) goes to `astra` first, with one line saying the content is authorized internal safety-evaluation material and the review is of the product surface. Name that dispatch's fallback in the brief before you send it: `astra`'s quota is shared across concurrent dispatches, so a fan-out dies together rather than one at a time. Whichever fallback you name, say in the report that the pass lost its cross-model property. The same holds for ANY lane whose brief makes it read task attack content (`malicious.py`, injection fixtures, tests that plant them), not only reviewers: dispatch it on a non-Anthropic model from the start, with the brief line 'read attack files by name and size only'. When a brief names a model FOR INDEPENDENCE — a cross-model review, an adversarial second opinion, a deliberately different reader — and that model is unavailable, never substitute silently: the substitution removes exactly the property the brief was buying. Two lanes handled it correctly, one by re-dispatching on a different non-Anthropic model and keeping real independence, the other by proceeding on its own judgement with in-band evidence and DOCUMENTING that the independent reader was absent. Note which agents actually share a quota before you pick the substitute. `deep` is not a non-Anthropic route for refused work: its fallback chain ends at Anthropic (`omp/config.yml`). The refusal arrives as the job's whole result (`Refusal (cyber): ...`), so read what the worker actually did before you re-dispatch: there may be nothing to undo, or half a change.

## Continuation beats fresh dispatch

Every `task()` result carries a continuation session ID (`ses_...`). For follow-ups, fixes, or "also do X" on the same work, continue that session (`task(task_id="ses_...")`) instead of dispatching fresh — the subagent keeps everything it already learned. The exception is a confirmed-wedged subagent: its session is the thing that is stuck, so that is the one case where a fresh dispatch (carrying a summary of what the wedged run learned) beats continuation.

An agent revived with `hub send` is no longer a job, so `hub wait` returns on its own window rather than on the agent's. Read the tail of its transcript instead — `history://<id>:-3` — and keep `wait` for jobs.

A dispatched agent cannot write a `'/tmp/omp-local/session'` path: its write tool refuses the scheme outside plan mode. Ask for the result as structured output or at a real filesystem path you name, and never promise a file the agent's own tools cannot create.

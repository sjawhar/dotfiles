# Relaying rules, premises and claims

- Hand over a premise with the instruction that would falsify it.
- A rule you put in a brief is a copy you now own: retracting it means finding every brief that carries it. Check whom the source addressed before you relay it.
- Write each rule once, as its own short line: two copies drift apart, and a rule buried mid-paragraph is read past. Before you write a rule, grep the document for its subject, then read the whole document: a copy that has drifted can use other words than the grep looks for, and only the full read finds it.
- Split a document only when its next reader (a handoff, a review, a dispatch that will quote it) needs it split, not when you notice its length.
- Start a log of changes with a summary of the current state. In a list of rules, start each item with its subject.
- Point at a skill rather than paraphrasing it. Head any restatement "the skill is the authority; where they differ, the skill wins". Audit a relayed block against the skill line by line and report the clean lines too, and keep the block in a file, not in a kernel cell rebuilt from memory.
- Restating a claim more strongly than its source makes the stronger claim yours: mark it unmeasured or do not send it.
- Re-derive a claim before you act on it: echoing one turns someone else's uncertainty into your own assertion.
- Re-derive a scout's test matrix from the scout's own predicate before a builder gets it; a builder pins the table as given. The scout surfaces a contradiction; you, the dispatcher, resolve it in writing, in the spec or plan that the builder's brief cites, before any test exists.
- "On main" in a brief is a branch name; the worker measures whatever tree its workspace holds.

# Post-Merge Sweep

A PR just merged. Run the closing sweep — execute each item, don't present a list of suggestions.

1. **Confirm the merge**: verify the PR is merged and post-merge CI on the target branch is green (if still running, set up a watcher and continue with the other items).
2. **Prune local state**: fetch (`jj git fetch`), confirm the tracking bookmark was deleted, abandon empty leftover changes, remove obsolete jj workspaces created for this work.
3. **Tracking state**: move the Dispatch issue to `done` once the change is verified live (until then it stays `testing`); close or update any linked GitHub issue(s), tracking docs, and roadmap items. Plan/spec content belongs in the issue body, not file-path references.
4. **Deploy**: if the repo has a deployment step (check AGENTS.md), follow it and verify the change is live. Live means observed on the NEW version: the proof carries evidence that its observation postdates the deploy, such as a scheduled tick that started after the deploy's completedAt, a node or pod created after the apply began, or the deployed image digest or squash sha. Without that it may be reading the old version. Measured three ways on 2026-09-25: an in-flight ECS tick finished on the OLD task definition after production-apply landed mid-tick; 0 of 85 production pods sat on the new runtime at apply (inspect release); and a check keyed to the PR head sha could never fire, because a squash merge lands a different sha on main (dispatch). Merges queue for the deploy lane: one chain runs, one waits, and a newer merge replaces the waiting one, so your merge rides the newest chain and lands when it finishes. A "cancelled" pending run is that queue working, not a failure — it was cancelled because a chain was already applying, so it could not have deployed then anyway; the cancel subtracts nothing. Find the newest run; that one carries your merge. A watcher keys to the named apply job succeeding (for example `deploy / deploy`), never to a run completing: a chain can finish red with the apply SKIPPED, and a dev-slot `workflow_dispatch` of the same workflow completes too; one lane's watcher counted both as "the apply" (#20141, 2026-09-25). Never report a cancellation, treat it as blocking, or narrate it as the reason a change is not yet live. The only deploy event worth reporting is a FAILED chain that carries your merge, and that one is yours to fix.
5. **Announce, if the change moved someone's workflow**: name who the merge affects — people authoring against a changed convention, users of a changed page, anyone invoking a changed CLI or following a changed doc — and tell them in their channel in this sweep, in `sami-voice` and under the repo's own announcement skill where one exists (a draft for Sami where his outside-audience rule in CLAUDE.md applies); the announcement is part of the change, not a follow-up. An internal-only merge moves no one else's workflow and gets no announcement; record "no one" and move on. Before recording "no one", read the merged PR's own text for consumers outside the repository: a grep of the repo cannot see them, and "every in-repo producer is fixed" is not "every consumer is fixed". One lane recorded no audience for a change whose own PR body said red-teamers keep launch specs outside the repo (#20040, 2026-09-25).
6. **Report**: the short list of items you just handled (or "nothing left"), then **clearly state any applicable follow-ups or cleanups that remain** — full sentences with context, not bare issue numbers or shorthand.

The bar is "pristine clean."

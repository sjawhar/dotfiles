# Updating Docs

## Evergreen, not archaeological

Write what is true now. Remove on sight:

- PR/issue-number breadcrumbs ("as of #1234...")
- Migration trails ("previously we did X, now we do Y")
- Deprecation lists ("don't use the old JSON format") once the old way is gone — describe the correct way instead
- "NEW:" / "UPDATED:" markers and dated notes

If a reader needs to know the old way existed, that's what `jj log` is for.

## A cutover sweeps the whole owning tree

When a change or ruling makes prose false, the sweep that fixes it enumerates every file in the owning tree by tree walk — `jj file list <dir>`, `rg --files <dir>` — never by a hand-written glob: `.claude/skills/*/references/*.md` cannot see `references/phases/`, and what the glob misses keeps teaching the old behavior. The sweep covers every file type, not `.md` alone: scripts and configs in a skill tree are the doc of record for what actually runs. On #19273 (2026-09-18, 35 files) the skill text said docker/hawk while `run_probe.sh:16` two directories down still hardcoded `--sandbox modal` — "the script is what actually runs, so the doc was lying." Inferred from that owner's sweep; not a sentence Sami wrote.

**A sweep for one retracted claim wants more than one searcher.** A single searcher's grep false-negatives in its own way: a remembered phrase instead of the claim, an alternation that misses a spelling, a `head -5`. On 2026-09-25 three independent sweeps for one stale claim (the owner's, the reviewer's, the fixer's) each missed sites the others found, the fixer's alone found two in a file neither of the others searched, and only their union was complete (Fix PR20044 lane). Separately, the merge queue's alternation grep and the dispatch lane's `head -5` each false-negatived the same real #20125 content. When the claim matters, have a second agent sweep independently, from the claim rather than your fragment, and merge the hits. A sweep you dispatch is briefed with the claim and its completeness criterion — 'this overturned claim, in all its rewordings, appears nowhere in the repository' — never with the files to edit.  The instrument that meets the criterion is a concept sweep: grep the intersection of the claim's terms rather than a phrase, and read every hit in full. Two lanes ran four and five rounds of fragment-grep briefs on one claim each, every round finding one more reworded copy, and each closed in a single pass once the brief asked for the concept. And a procedure meant to be executed literally is as hard to get right as code: measure it against a real case on every revision rather than reading it. One prose change took four review rounds, each closing a defect the previous fix introduced, and every round found its defect only because someone ran the rule against the incident instead of reading the paragraph. The librarian's own two corrections that night came the same way. A brief scoped to a file list finds the next copy and stops: one lane's doc fix took three rounds, each brief naming the line the last round missed, until the round that set the criterion closed it in one pass (2026-09-25).

**A ruling about what code may accept lands as a refusal in the code, in the same change.** Recording a ruling is not landing it. When it decides which target, source or shape the code takes, the change that records it makes the code refuse the alternatives, with an error that names the ruling. Otherwise every later lane re-derives the old answer from what the code still accepts. On 2026-09-25 three lanes traced one case: the 09-13 ruling that assignment repositories are AWS CodeCommit lived in a spec and a code header, while the credential mint accepted any git URL. Lane after lane derived GitHub from the one credential the code could mint, and Sami was asked for GitHub repositories four times ('Why the fuck does this keep happening?'; task delivery, env typing, platform PO).

## Read the whole artifact back after you edit it

Not a grep for what you added: a grep finds only what you already suspect. Read the document through once and check that the neighbours survived — the clauses a reader needs that your edit never mentions.

Three lanes paid for this on 2026-09-25. One edit introduced a contradiction in a paragraph it never touched, found only by reading the whole spec. One document-edit tool accepted a misnamed key, applied an empty replacement, and silently deleted the phrase; the read-back was the only thing that caught it. A read-back only counts if its reader can see the content: one lane verified a document edit against a route that returns METADATA, where the expected-present and the expected-absent phrase both counted 0 — the same answer for both cases means the instrument is wrong, not the document. Before believing a read-back, make it find a string you know is there. It is also the cheapest pass anyone runs: in a night where seven independent passes each caught a different class of defect, fetching the published artifact and asserting on its text was the cheapest of them and caught TWO defects its own author had written and believed, an hour apart. And a multi-paragraph change has to be a replace plus an insert whose anchor quotes a neighbouring block, so its real hazard is the insert landing against the wrong anchor and burying something further down — asserting your new text is present does not see that.
- **An index computed on a string dies with the next mutation of it.** The commonest way to need one: an INDEX computed on a string is invalidated by any mutation of that string, exactly like an iterator, and no language will tell you. A script that computed two offsets, then ran a `replace` whose new text was longer, then sliced at the stale offsets, published a PR body whose first bullet was cut mid-word with the next bullet spliced onto its stump — nothing raised, because string slicing cannot fail. Either collect every edit as a (start, end, text) triple and apply them back to front, re-derive every offset after each mutation, or locate the whole region once and replace it in a single slice — then assert on the RESULT before publishing. Note what that lane also found: its own `cut -c1-200` read-back hid the damage, so the verification and the defect had the same shape, a sentence that stops early.
- **Chain the command that publishes a guarded step's output to that step.** A newline is not `&&`. One lane's edit script asserted, failed, and exited before writing; the `gh pr edit` on the next line ran anyway and re-published the unmodified body, so the guard fired correctly and the stale artifact shipped regardless. The fix is one character. This rule has no counter-case in bash, and one reported counter-case turned out to be a harness bug worth recognising: `export VAR=$(cmd --flag)` chained after a heredoc returned `error: unexpected argument '--flag'` under a `Usage: export` banner, which no shell can produce — bash resolves builtins before PATH, so nothing on PATH can shadow `export`, and the message is clap-formatted, i.e. a command runner parsed the line before any shell saw it. When an error blames a shell construct in a format that shell does not emit, suspect the layer between you and the shell and report it, rather than inventing a workaround. If you want one meanwhile, `set -euo pipefail` at the top of the script guards the earlier step without needing `&&` after it.
- **A conjunction inherits its evidence from whichever member you measured.** "A and B: X" reads as measured for both, and a reader cannot see which half you actually observed. One runbook step said a GC race AND history finalization both showed a distinct blob per job with the pushing manifest preceding the unknown-blob line — true and measured for the second class, merely plausible for the first, whose logs had never been read. It had teeth: a GC reclaim removing a record shared by concurrent solves would produce the SAME digest across jobs, so that line would have routed a re-runnable failure to a discard. When you write "A and B: X", check that X was observed on B rather than inferred from B's mechanism — then scope the claim to the class you measured and say outright what you did not read.
- **Paraphrase a result from the run's own summary line, not from your conclusion.** Copy the run's own terminal summary line first (`2 failed, 5207 passed, 2 errors`) and paraphrase from that, not from your conclusion: a lane that had classified two xdist-polluted errors correctly in chat published a body saying the lane was "green apart from two known environment-dependent failures", dropping the errors entirely. If the paraphrase does not account for every category in that line, it is a selection, not a summary. The summary line also has a limit worth stating, because it is easy to over-read: it licenses claims only about the categories it CARRIES. `95 passed / 0 failed` supports "nothing failed"; it does not support "the dlq-health test ran", which one lane paraphrased from its conclusion until an advisory caught it. When the claim names a specific test, the artifact carrying per-test rows — the junit file — is the source, not the summary.

## Integrate, don't accrete

Before adding a section, check whether an existing section already covers the topic. If it mostly does, rewrite that section — don't append a near-duplicate beside it. Symptoms you're accreting instead of integrating:

- The doc gets longer every edit, even when the change simplified things
- Two sections disagree slightly about the same behavior
- Per-case sections (per-provider, per-version) that share most of their content — merge into one section with the differences called out

Same test as code: an update whose purpose is consolidation should leave the doc shorter.

## Structure

- One doc per audience/purpose; consolidate rather than proliferate files. A new file needs a reason an existing one can't serve.
- Match the tone and formatting of the doc you're editing.
- Prefer rewriting a section over patching sentences into it — patched-in sentences are how docs drift into incoherence.

- **A pipe inside a table cell is escaped even in backticks, and a doc change is reviewed as RENDERED, not only as source.** GitHub's table extension splits a row on every unescaped `|` before inline parsing, so a code span does not protect one: a two-column row whose second cell held `` `head | tr | wc` `` renders as two cells ending mid-span, and the rest of the row vanishes. On the real case about 1,000 characters disappeared, most of them text that had rendered fine before the edit, and FOUR reviews read the source and passed it (2026-09-26; reproduced here with cmark-gfm). Write `head \| tr \| wc`. The check without a renderer counts a row's cells after removing escaped pipes - `sed 's/\\|//g' FILE | awk -F'|' '{print NR": "NF}'` - and compares against the header; counting raw pipes instead flags correctly-escaped rows too, which is how a check like this gets ignored.

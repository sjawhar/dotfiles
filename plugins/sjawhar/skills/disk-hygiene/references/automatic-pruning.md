# What already prunes on its own

Read this to learn what timers already prune and what they leave for this skill, before you add automation of your own. SKILL.md's rule, as it stood with its reason:

- Never put this skill on a timer or cron: it needs the check-in. Run it by hand, and stop when done. What already runs on a timer, and what it leaves for this skill: this file.

- `~/.dotfiles/agentbox/devbox-prune` runs every 6 h where its timer is on. On the host daemon it does Docker step 6 ([docker.md](docker.md)). In each box it does steps 2 and 6, a default-builder `docker builder prune -f`, and a cut of Go build cache idle >2 days. It never uses `-a`, deletes a tagged image or judges liveness. In a box, read its log with `systemd-run --user systemctl --user status devbox-prune.service`.
- agentbox deletes each session's workspace when omp exits.
- `~/.dotfiles/devbox/box-cleanup` runs seven cleaners on one 15-minute timer, each at its own minimum interval; its table in `devbox/box-cleanup.md` lists them all. Among them:
  - `tmp-empty-prune` (daily) deletes the empty `tmp*` directories older than a day directly under `/mnt/nvme/$USER/tmp`, which Python's `tempfile.mkdtemp()` leaves behind.
  - `gocache-cap` (every pass) trims the box's one Go build cache, `<scratch>/gocache` (`GOCACHE` in `.bashrc`; `<scratch>` is `/mnt/scratch/$USER` where that directory exists, as on sami-devbox, else `/mnt/nvme/$USER`), and any lane cache inside it. Past 25 GB it deletes the entries no build used in the last 3 hours; still past 50 GB, the ones unused for 2 hours. It never deletes an entry the oldest running `go` command may have looked up, and never runs `go clean -cache`, which broke running builds four times on 2026-11-15/16 (dispatch://INFRA-3905). Go itself trims only entries unused for 5 days. A `GOCACHE` outside that directory is not capped.
  - `nvme-cache-cap` (every pass) holds the uv, cargo, Go module, Hugging Face, Playwright, mise, Puppeteer, pip and bun caches under their caps (`devbox/nvme-cache-cap.md`). A cache over its cap goes whole, by a rename to a sibling and then removal, and only when no process holds anything under it (open file, cwd, exe, root, mapped file, command-line argument) and none of its tool's reading commands (`go`, `gopls`, `cargo`, `rustc`, `uv`, `pip`, `mise`) runs; a held cache stays over its cap. Until 2026-11-16 it ran `go clean -modcache`, `uv cache clean` and the other cleaners with no such check, and the Go module cache holds the toolchain builds run from.
  - `tmp-stale-reap` (daily) removes a top-level entry of the root-resident `/tmp` once nothing in it has been written for 48 h. It never touches an entry another user owns, an entry any process holds (cwd, exe, root, an open fd, a mapped file, a command-line argument, `TMPDIR` or `AGENT_SESSION_SCRATCH`), or a tree holding a unix socket or another user's file at any depth; `devbox/tmp-stale-reap --dry-run` prints the same decisions and removes nothing. Until 2026-11-16 its scan of `/proc` put every process's entries on one command line, which at 22,765 processes on sami-devbox that day was over the argument limit ("Argument list too long"), so the scan found no holder and read as finished. The scan it now shares with `nvme-cache-cap`, `devbox/proc-holds.sh`, takes them on stdin and counts a scan that missed its own process as unfinished, and then removes nothing. `/tmp` is on the root filesystem and `systemd-tmpfiles`' 30-day rule never reaches it. A pass stops itself at 28 min (`stopped at its deadline … next pass resumes at …` in its journal) and the next pass carries on from that entry.

None of these covers the rest, which this skill does by hand: unused tagged images, non-default builders, leaked leases, containers, box directories filled before agentbox began deleting each session's workspace on exit, Docker volumes, `~/.local/share/opencode`, a retired jj store.

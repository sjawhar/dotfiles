# agent-secrets

The host side of agent secrets (AGENTC-393): the user unit and wrapper for `agent-secrets-helper`, the daemon that holds the operator's machine login (kept across restarts in `~/.config/agent-secrets/machine.json`, below), pins each host agent session by pidfd, keeps its broker key in memory, enrolls it as a session (the broker records one kind for every session a launcher enrolls, and a pod as its own), and signs its proofs. A boxed session's key is the host's too, made under `$RUN_BASE/session-keys/<session id>` and copied into the box, so the session keeps the same enrollment — and the cards Sami has not yet answered — when it moves into a new box (`scripts/agentbox`, `agentbox/AGENTS.md`, dispatch://INFRA-1167); the helper is how the host enrolls and unenrolls each one. Sami's own shells never depend on it: they use secretsd (`scripts/secret-run`).

- `broker.env` — the production broker's URL, written once: the unit reads it (`EnvironmentFile`), and `.bashrc`, `scripts/agent-secrets-session`, `scripts/secret-run`, `scripts/agent-secrets-login` and `scripts/agentbox` load it through `broker-url.sh`. `~/.config/agent-secrets/env.local` (optional, uncommitted) overrides it on one machine, for the helper's unit and for each of those consumers.
- `broker-url.sh` — sourced by those five consumers (bash, and zsh for `.bashrc`). It is the one place the rule is written. When `AGENT_SECRETS_URL` is unset, or equals `DOTFILES_AGENT_SECRETS_URL` (the URL an earlier load recorded), it sources `broker.env` then `env.local`, records the result, and exports both variables. So a process that inherits an earlier load's URL, such as every shell of a tmux server started before `broker.env` changed, gets the current URL. A URL the caller chose never matches the record, so it wins: Legion's `packages/envoy/scripts/dev-broker.sh` exports a local broker's URL, and no consumer switches that session to production. The record has no `AGENT_SECRETS_` prefix because the `agent-secrets` exec form drops every such variable from its child's environment except the session's own three. `scripts/agentbox` passes a box the URL without the record, so the box keeps the broker its enrollment was made with.
- `agent-secrets-helper.service` — `ExecStart` is the wrapper. `Restart=always`: a SIGTERM from anything but systemd (a `pkill -f "agent-secrets-helper serve"` meant for a test rig's helper matches this one) ends the helper with exit 0, which `on-failure` never restarted, so systemd restarts it after any exit except its own stop. The restarted helper resumes the machine login it kept (`machine.json`), so it needs no new approval.
- `agent-secrets-helper` — `mise exec agent-secrets -- agent-secrets-helper "$@"`, `serve` when given no arguments, so `agent-secrets-helper sessions` through it lists sessions rather than starting a second helper (which would take the socket and re-pin every live session); the binary comes from `mise.toml` `[tools.agent-secrets]` (sjawhar/legion `cmd/agent-secrets-helper`, its asset digests pinned).
- `installers/agent-secrets.sh` — `devbox/install.sh` runs it on the devbox, and the root `install.sh` runs it through `installers/agent-secrets-local.sh` where `env.local` sets `AGENT_SECRETS_URL`. It links and enables the unit, and an unchanged re-run of a running helper makes no enable or start call. It restarts the helper only when the pinned version, the unit, the wrapper or `broker.env` changed — never while `agent-secrets-helper sessions` lists a session, unless `AGENT_SECRETS_HELPER_RESTART_WITH_SESSIONS=1`, because a restart re-pins live sessions with fresh keys and their grants are revoked. When `agent-secrets-helper sessions` fails or times out, it does not restart either, whatever that variable says: it warns, and the next install retries. A run that starts the helper itself records the installed version without a restart, because the helper it started already runs it. `agent-secrets-local.sh` reads `env.local` alone, ignores an inherited URL, prints no URL, and does not install or change the unit when `env.local` sets no broker; it also drops `AGENT_SECRETS_HELPER_RESTART_WITH_SESSIONS`, so a restart over registered sessions needs a direct run of `agent-secrets.sh`.
- A machine without the helper (the root `install.sh` installs it only where `env.local` names a broker) has no broker identity, so the broker cannot mint GitHub App tokens for its sessions. It opts in to minting them from secretsd instead: the App key in that machine's `secrets.local.env`, and `gh-app.<profile>.key-secret` naming it in `~/.config/git/config`, which only that machine reads. `shims/gh-app-token`'s header has the commands.
- Once per machine, and again only if the login lapses or is revoked: `agent-secrets-login <email>`, naming the operator by the email they sign in to Dispatch with (anything else is refused), writes it lowercased to `~/.config/agent-secrets/operator` (0600; never mounted into a box), starts the helper, waits for its socket, and runs `agent-secrets machine login`, which prints a code the operator types at Dispatch's `/credentials/machine` page (an OAuth device grant). The helper keeps the approved login in `~/.config/agent-secrets/machine.json` (0600: the machine key and its rotating refresh token; `AGENT_SECRETS_MACHINE_FILE` moves it) and refreshes it at least daily, so a restart or reboot resumes it and it lapses only after about 30 days without a refresh. Never copy that file to another machine or into a box: a second helper spending its refresh token ends the login. `agent-secrets machine login-status` is the side-effect-free probe: it prints the login state (`none`, `pending`, `denied`, `expired`, `issued`) and exits 0 only on `issued`. It prints `issued` whenever the helper holds a live launcher credential, even when a newer re-login was denied, expired unapproved or is still pending (stderr names that login and its code), and `expired` once the broker refuses the held credential.
- A host session becomes a session root when its launcher (`shims/omp`, `scripts/cld`, both through `scripts/agent-session`) execs the agent through `scripts/agent-secrets-session`, which runs `agent-secrets register [--wait 10] --exec -- <agent argv>`; every process under it gets proofs from the socket `$XDG_RUNTIME_DIR/agent-secrets/helper.sock` through `AGENT_SECRETS_HELPER_SOCK`, and when the root exits the helper revokes the enrollment. `--wait 10` holds the launch until the session is enrolled and is passed only while `login-status` says `issued`; a helper that does not answer means no registration at all, so a stopped helper costs a launch nothing. Why registering without a credential is safe: the comment at the top of `scripts/agent-secrets-session`.
- `scripts/agentbox new` enrolls a box only while the helper holds a live credential; otherwise the box starts with no key and no `enrollment.pending`, says so on stderr, and its agents use secretsd. A box whose first enrollment fails loses its key the same way (`enroll_failed`). When the broker refuses a box's renew as not live, the box's launcher enrolls the key the box holds again (`agentbox/AGENTS.md`). A re-enrollment that fails keeps the key, and the launcher tries again. A box that ends does not unenroll its session at once. A detached waiter gives the session three minutes to come back in another box, and ends the enrollment only when no box came back. So a session that comes back keeps the same enrollment id.
